7.  Doll name OCR errors baked into projection templates

   STATUS: OPEN / Requires manual correction per doll
   SCOPE: MAIN

   FIRST OBSERVED: Session adding doll_name_ocr.py (June 2026).

   SYMPTOM: Three doll names are consistently misread by Tesseract and then
   stored as mislabelled templates in assets/doll_names/templates.json and
   as mislabelled portrait files in assets/dolls/:

      Tesseract reads    Correct name
      ────────────────   ────────────
      Sharkty            Sharkry
      soringfele         Springfield   (OCR garble; dist=3, borderline fuzzy)
      aiongjiN           QiongJiu      (OCR garble; dist too large for fuzzy)

   ROOT CAUSE: The projection classifier is built from OCR-labelled crops.
   When Tesseract misreads a name, the template is stored under the wrong
   name.  fuzzy_correct() can snap some errors (e.g. "soringfele" → dist=3
   → "Springfield" if the portrait is named correctly), but only when the
   correct name exists in assets/dolls/.

   FIX (per doll):
      1. Rename assets/dolls/_<wrong>.png → _<correct>.png
      2. In assets/doll_names/templates.json, rename the key accordingly.
      3. Re-run main.py — fuzzy correction and projection classifier
         will now produce the correct name.

   STATUS OF EACH:
      Sharkty → Sharkry     : dist=1 — fuzzy will fix once portrait renamed
      soringfele → Springfield : dist=3 — fuzzy will fix once portrait renamed
      aiongjiN → QiongJiu   : dist=7 — fuzzy CANNOT fix; portrait rename +
                               template rename required, THEN rebuild templates
                               from good crops (--build gm_d_*.png).


11. daily_gunsmoke: top-bottom panel stacking not supported

   STATUS: OPEN / Not yet observed in the wild
   SCOPE: MAIN

   The current panel-discovery logic (_find_all_frames + _group_frames_into_panels)
   clusters portrait frames by x-proximity, which correctly handles left-right
   side-by-side panels.  If a future screenshot stacks two reports vertically
   (top panel / bottom panel), the frames from both panels would share nearly
   the same x and be merged into one group, producing a single malformed report
   instead of two separate ones.

   IDEA TO RESOLVE: After x-clustering, check whether a group's y-span exceeds
   ~1.5× the expected 5-row height.  If so, split the group at the y-gap between
   rows 5 and 6 (the expected inter-panel gap would be larger than inter-row gaps).


14. stat_ocr: Hu moment tiebreaker should be disabled

   STATUS: OPEN
   SCOPE: MAIN

   OBSERVED: Timing reports show 117 val and 20 pct genuine Hu fallback calls
   per ~3300-cell run (after the logging bug fix in §_read_line that was
   previously inflating the count to 3296×).

   PROBLEM: The Hu tiebreaker is reached only when projection confidence falls
   below PROJ_CORR_MIN — the genuinely hard, ambiguous cases.  Hu moments have
   been shown during classifier development to be unreliable on exactly these
   cases (training data showed misclassifications that Hu made worse, not better).
   Keeping it risks silently wrong answers on ~137 cells per run.

   IDEA TO RESOLVE: In _classify(), replace the Phase 3 block with a plain
   return '?' when projection cannot reach PROJ_CORR_MIN.  The caller already
   handles '?' via Tesseract fallback for val, and the pct fallback chain.
   This makes the uncertainty explicit rather than masking it with an unreliable
   tiebreaker.

   BLOCKED ON: Validation cost.  Removing Hu will definitively increase Tesseract
   fallback count (those 137 cells currently get an answer from Hu; returning '?'
   instead routes them all to Tesseract).  Whether that is a net improvement
   depends on whether Hu's answers are more or less correct than Tesseract's —
   and Tesseract is not 100% reliable either, making ground-truth comparison
   time-consuming.


19. stat_ocr_fft: vrun -> vstroke + hbar_top/hbar_bottom (2D-sliding,
    punished matched filters) promoted into compute_features()

   STATUS: OPEN / Promoted, measured, §17's confusion pattern REDUCED not
           RESOLVED -- do not treat this as closing §17 (§17 itself was
           later found stale/resolved a different way, see its own entry).
           SCOPE NOTE (2026-07-10): this describes the FLAT classifier's
           compute_features() (Agent A's gpr vector), still what --build
           trains from. It is no longer what runs by default at
           CLASSIFY time: HIERARCHICAL_DEFAULT=True (§25) plus
           LINE_SPLIT_MODE_DEFAULT="sobel" (§28) mean neither vstroke nor
           hbar's 2D-sliding search (_hbar_features) executes in the
           default hierarchical path -- both are only reached via the
           flat classifier (enable_hierarchical=False) or an explicit

   SCOPE: EXPLORE (gfl2/stat_ocr_fft.py only -- not selectable via main.py
           --stat-ocr-engine, no production behavior changed by this entry)

   FIRST OBSERVED: 2026-07-05, same-day follow-up session to §17/§18 above,
   working entirely outside this file (a live conversation, not scratch
   scripts) via two new disposable prototyping scripts:
   debugs/debug_vstroke_feature.py and debugs/debug_hbar_feature.py.

   CONTEXT: §17 flagged that the gabor_0->vrun swap raised overall accuracy
   but introduced a '1'/'7' + '0'/'8' confusion pattern, not root-caused at
   the time.  This entry is that follow-up: a from-scratch redesign of the
   vertical-stroke feature (vrun's replacement, "vstroke") plus a new
   horizontal-bar feature ("hbar"), developed and validated in the two
   debug scripts above before touching gfl2/stat_ocr_fft.py at all --
   per this repo's own "unit debug before integration" convention.

   DESIGN ITERATION SUMMARY (vstroke) -- four rejected designs before the
   promoted one, each a real, measured dead end, not a guess:
     1. Fixed, centered, background-flanked-on-both-sides kernel, full
        glyph height: '1' only narrowly beat '7' (+0.083 gap); a fixed
        ink-column width silently assumes a stroke thickness.
     2. Sliding-in-x-only, single-sided, full-height, with a bottom
        "don't care" band: '1'/'7' gap widened to +0.334, but exposed (a)
        a hard reachability limit -- a single-sided kernel's ink region
        can only reach columns bounded by kernel_w-ink_w from one edge, so
        '4's vertical stroke was unreachable with ink-left; (b) flipping
        to ink-right to reach it made '4' WORSE (0.280->0.057), because
        '4's crossbar sits at MID-HEIGHT, not near the bottom where the
        "don't care" band lived -- forcing the entire height except the
        bottom few rows to read as background fails regardless of side.
     3. 2D sliding (x AND y), no "don't care" band: a short window that
        also slides vertically can dodge '4's crossbar by positioning
        itself below it. Fixed '4' (0.057->0.620) but reopened a DIFFERENT
        false-positive: a short window free to move in both axes can find
        a locally-straight-looking patch inside a curved digit's stroke
        ('3'/'7'/'9' all scored competitively with '4' this way).
     4. PROMOTED: same 2D sliding, plus a single signed "punish" cell --
        the background column immediately adjacent to the ink band,
        BOTTOM row of the window only, weighted -1 instead of 0.  Targets
        '7' specifically: its diagonal descender drifts left as y
        increases, so a window placed along it can still pass as
        "isolated vertical stroke" over a short span, but drifts furthest
        left by the window's bottom row -- into the punished cell.  A
        genuine vertical stroke ('1', '4') never drifts (same columns for
        the whole window height by construction), so '1'/'4' are
        essentially untouched (single-image prototype: '1' 1.000->0.967,
        '4' 0.620->0.621) while '7' drops (0.705->0.619).
   The punish cell's column was tried LEFT first and changed to RIGHT by
   direction before promotion: '2' and '4' (a target of the separate hbar
   feature, and '4' is a vstroke target here) both have real ink near the
   left-adjacent position in this font, so a left punish cell risked
   suppressing the very digits these features exist to detect.

   DESIGN ITERATION SUMMARY (hbar) -- new feature, targets '2'/'4'/'5'/'7'
   (each has a real horizontal stroke the other six digits lack: '2' foot,
   '4' crossbar, '5'/'7' top bar).  Same 2D-sliding, punished, single-sided
   matched filter as vstroke, transposed (split axis = height, span axis =
   width).  Went through the identical top-vs-bottom reachability argument
   as vstroke's left-vs-right: '2' (bottom bar) and '5'/'7' (top bar) are a
   genuine mirror pair, so no single orientation can reach both --
   confirmed empirically (side="bottom" alone: '7' scored 0.097, dead
   last, because it structurally cannot reach a bar at the very top).

   REJECTED FIX: per-glyph max(top, bottom) as a single merged score --
   tried, explicitly rejected by direction on BOTH vstroke (never had a
   mirror in the end) and hbar: a real feature can't pick per-glyph which
   orientation "wins" at inference time, so a max isn't a computation,
   it's hindsight.  PROMOTED FIX (matches this module's own existing
   pattern -- paren_(/paren_), loop_top/loop_bot): hbar_top and hbar_bottom
   ship as two INDEPENDENT feature dimensions; the nearest-centroid
   classifier over the full vector does the combining, not the feature
   extractor.  Per-target check (single-image prototype): every target
   clears all six non-targets on at least one of the two dims ('2' via
   bottom, '4' via top, '5' via both, '7' via top).

   INTEGRATION (this entry): _vrun_feature and its helpers (_run_since_bg,
   _horiz_segment_width, MAX_STROKE_W) are kept, unused, in
   gfl2/stat_ocr_fft.py -- same "kept, not deleted" convention as the

36. stat_ocr_dp: adaptive threshold cache is order-dependent across images
    in a single run -- a val-line reproducibility bug found while rescoping
    the daily stat-cell test harness

   STATUS: OPEN
   SCOPE: MIXED (gfl2/stat_ocr_dp.py, reachable via `--stat-ocr-engine dp`)

   FIRST OBSERVED: 2026-07-12, retargeting the daily stat-cell hard-case
   test suite from single/*.png + gfl2.stat_ocr.StatOcr (production) to
   tests/inputs/daily/*.png + the dp/padded engines only (decisions.txt
   #95) -- tests/test_stat_ocr_dp.py's first real run against the curated
   18-image fixture showed pct at a clean 100.0% (647/647) but val at only
   97.7% (634/649), which didn't match this engine's own documented ~99.4%
   glyph accuracy closely enough to assume it was just corpus variance.

   ROOT CAUSE: StatOcrDp.__init__ creates `self._thresh_cache = {}`, keyed
   by (pct-strip height, ink-color group) -- see known_issues.txt §18(b)'s
   adaptive-threshold design -- and this cache is NEVER cleared between
   calls to `.read()`. Every real caller (main.py's folder batch, this
   engine's own --verify/--build, and the test suite's module-scoped `ocr`
   fixture) constructs exactly ONE StatOcrDp instance and reuses it across
   every image in a run, so the cache persists across images by
   construction, not by accident. For most cells this is harmless (or is
   even the point -- avoiding a fresh threshold search per cell is the
   whole design). But for at least 5 cells in the curated set, whichever
   threshold got cached FIRST for that (strip_height, ink_group) key --
   seeded by an earlier, different image -- produces a WRONG binarization
   for a later image's cell at the same key, when that same cell would
   binarize correctly under a threshold derived from its own pixels.

   CONFIRMED DIRECTLY (not inferred from the corpus number alone): each of
   the 5 affected cells was re-read two ways -- (a) in isolation, with a
   freshly-constructed engine processing only that one image, and (b) after
   the other 17 curated images, in the exact order pytest's own
   module-scoped fixture processes them. (a) reproduces the correct value
   every time; (b) reproduces the exact wrong value the test suite sees.
   The "correct" (a) answer was independently checked against the real
   rendered pixels (upscaled crop, visual read) in every case, not assumed
   from agreement alone. Example: gm_d_20250908.png::p1_r0_col2 -- real
   value (confirmed visually) and isolated read are both '250'; read after
   the other 17 images in sequence, the SAME cell returns '256'.

   Affected cells (all val-line, all xfail(strict=True) in
   tests/test_stat_ocr_dp.py, reason string points back here):
      gm_d_20250908.png::p1_r0_col2, gm_d_20260111.png::p1_r1_col3,
      ib_d_20250928.png::p1_r1_col3, ib_d_20251004.png::p1_r1_col3,
      ib_d_20251020.png::p1_r1_col3

   RELATIONSHIP TO §18(b)/§32: this is the SAME KIND of cross-cell/cross-
   image cache contamination already fixed once for the pct line's '%'-
   anchor selection (§32's PCT_ANCHOR_MIN_AREA fix, decisions.txt #83) --
   a threshold or anchor decision made for one cell leaking into a
   different cell's classification purely because of processing order --
   but it is a DIFFERENT specific mechanism (the shared `_thresh_cache`
   dict itself, not `_find_percent_x_start`'s rightmost-blob selection),
   on the val line rather than pct, and §32's fix does not touch it.

   NOT YET DONE: precisely identifying WHICH earlier image's cell seeds
   the bad threshold for each of the 5 cases (only confirmed that
   processing 17 other images first, in aggregate, reproduces the bug --
   not which single one is responsible); designing a real fix (candidates,
   not evaluated: cache eviction/refresh once real per-image variance is
   detected, per-image rather than per-run cache scope, or validating a
   cached threshold against the specific cell before reusing it).

   module uses) against 2000 random synthetic histograms and every real
   pct/val strip in tests/inputs/daily/*.png (t2, which this module never

   modest but real and repeatable improvement -- mean classify time
   3139.6us->~3025us/cell (3 repeated runs), and a much steadier per-cell
   cost (stdev 4275.4us->~1710us, cv 1.36->0.57) since a cache-miss no
   longer occasionally pays the old O(256^2) Python-loop cost. Smaller
   than the score field's ~29-51x speedup because this field's threshold
   was ALREADY cache-amortized (known_issues.txt §39: 6-10% of
   stat_cell/blob) -- there just isn't as much uncached cost left to cut.

   (b) CACHE REMOVAL: NO, measured and REJECTED, not merely riskier than
   score's case -- genuinely regresses real accuracy. Removing
   `_thresh_cache` (computing the threshold fresh from each cell's own
   pct/val strip every call, exactly mirroring decisions.txt #105) was
   implemented and checked against the curated 18-image
   tests/inputs/daily/*.png set: 15 mismatches (the documented baseline --
   14 pct skeleton abstentions + this entry's own 1 cache-order case) grew
   to 25-28. A per-image cache-reset variant (share the cache across cells
   WITHIN one image, but never across images -- one of action_items.txt
   #37's own listed candidates) was also tried and STILL regressed to 25
   mismatches, worse than the existing full-run-shared cache's 15 despite
   fully eliminating cross-image leakage.

   ROOT CAUSE OF WHY THIS DIFFERS FROM SCORE: score crops are pure digit
   strings with generous margins; a fresh-per-crop threshold works fine
   because each crop's own histogram is already a reliable estimate on
   its own. pct/val strips are smaller, include a '%' sign (pct) whose
   blob-count depends on exactly where the ink/halo boundary falls, and
   classify()'s own gates (TOP_BAND_4/7/25, etc.) measure ABSOLUTE ink-
   pixel counts calibrated against whatever threshold value happens to be
   in use (this module's own long-standing NORMALIZATION-removal
   rationale already flags this sensitivity for a DIFFERENT reason -- see
   the "Resolution- and ink-color-group-adaptive binarization threshold"
   section's own comment above §36's original entry). Direct inspection
   of one regressed cell (ib_d_20251225.png::p2_r3_col2, '23.21'->None)
   found the mechanism concretely: this cell's own per-cell-derived t1
   (113) is measurably darker/tighter than the shared cache's typical
   value (~170-180 for this key), which splits the '%' sign into 3
   fragments instead of the 1-2 `_find_percent_x_start` expects, breaking
   the digit-blob-count match. The cross-cell cache isn't just amortizing
   a cost here -- it's supplying a more representative, less noisy
   threshold than most individual cells can derive on their own, which is
   precisely why only ~1 real cell (of hundreds sharing a cache key) was
   ever found broken by this entry's own order-dependency in the first
   place.
