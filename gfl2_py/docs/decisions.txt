                  GFL2 Parser — Design Decisions


1.  Column detection strategy

   DECISION: Use fixed proportional column positions (width ratios) rather
   than dynamic edge-detection.

   RATIONALE: The GFL2 game UI is a fixed-layout interface. Canny-edge
   projection-based column detection proved unreliable on this UI because
   doll portraits and buff icons create noise that confuses the detector.
   The proportional approach is simpler, faster, and handles width
   variations correctly.

   CALIBRATION: Ratios were derived from a 1485px-wide reference screenshot
   by scanning horizontal brightness transitions. The buff column (0.350,
   0.421) was discovered to be ~90px LEFT of the initial estimate; the
   initial crop landed in the gap between the owner name and the buff icon.


2.  Row detection strategy

   DECISION: Scan horizontal brightness profiles to find dark separator bands.

   RATIONALE: The game UI uses dark bands between rows and between date
   sections. Mean row brightness < 70 reliably identifies these bands.
   Thick bands (>= 40px) carry date labels; thin bands (~9px) are plain
   row dividers.


3.  Date OCR

   DECISION: Use two tesseract PSM modes (11 then 6) in sequence; return
   first match for pattern \d{1,2}/\d{2}.

   RATIONALE: PSM 11 (sparse text) correctly reads the thin top date band
   (40px) which PSM 6 misreads. PSM 6 correctly reads the taller date
   separator bands (64px) which PSM 11 sometimes misses. Running both in
   sequence covers all cases.

   PREPROCESSING: Brightness threshold (>100) to isolate light date text
   on dark background, then 6x NEAREST upscale + 1-iteration dilation.


4.  Asset matching pipeline

   DECISION: Three-pass matching: pHash (strict) → HSV histogram → unknown.

   RATIONALE:
   - pHash (threshold=6): catches same-session re-runs at near-zero cost.
     Threshold deliberately strict (6 vs initial 10/20) because borderline
     matches (dist=8-10) were causing false positives between visually
     similar characters.
   - HSV histogram (threshold=0.92): robust across screenshots because
     character color distributions are distinctive even when the Lv. badge
     color changes (Lv.60 vs Lv.90) or icons are present. Achieves 95%+
     accuracy cross-screenshot.
   - pHash + template matching were tested first but both failed at cross-
     screenshot matching due to the Lv. badge color change and the
     Sharkry reference image coincidentally matching many characters.


5.  Histogram mask design

   DECISION: Mask out optional overlay icons during histogram computation
   while keeping the element icon.

   RATIONALE: Optional icons (buff arrows, borrowed indicator) alter the
   color histogram and cause false negatives. The element icon is retained
   because it genuinely distinguishes same-appearance dolls of different
   elements.

   MASK REGIONS (fractions of cell dimensions):
   - Exclude: left strip x=0-25%, y=20-58%  (optional buff arrows)
   - Exclude: top-right x=48-100%, y=0-26%  (borrowed indicator)
   - Exclude: bottom y=75-100%               (Lv. badge)
   - Keep:    left strip x=0-25%, y=0-20%   (element icon)
   - Keep:    rest of face                    (character appearance)


6.  Keep-cleanest reference upgrade

   DECISION: When a histogram match is found, replace the stored reference
   if the current frame has fewer optional icons (lower icon score).

   RATIONALE: References are initially cropped from whatever screenshot is
   processed first. Later screenshots may show the same doll without buff
   arrows or borrowed indicator. A cleaner reference improves future
   matching and makes the assets folder easier to inspect manually.

   ICON SCORE: Counts optional icon regions where mean HSV saturation > 90.
   The icon graphics are highly saturated; the face/background is not.


7.  Asset naming convention

   DECISION: Prefix asset filenames with '_' to mark known-mapped assets
   (e.g. '_QiongJiu.png'). Strip the prefix in CSV output.

   RATIONALE: The underscore makes it visually easy to distinguish labeled
   assets from unlabeled GUIDs in a file browser without needing a separate
   index file.


9.  OCR-based buff matching

   DECISION: Replace HSV histogram buff matching with OCR text recognition
   (buff_ocr.py).

   RATIONALE: Buff icons use dark backgrounds with monochromatic (single-
   color) artwork. HSV histograms on monochromatic images are nearly
   identical across different buffs — the color distribution carries no
   distinguishing information. Text labels within the buff icon area are
   always rendered clearly and are reliably machine-readable, making OCR
   the correct signal.


10. CHECKED_HASH .pyc invalidation

   DECISION: Use py_compile with invalidation_mode=CHECKED_HASH when
   pre-compiling gfl2 modules (compile_gfl2.py).

   RATIONALE: Python's default mtime-based .pyc invalidation fails silently
   when source files are written from a different platform (e.g., Linux
   sandbox writing to a Windows NTFS mount). The mtime visible to Python on
   Windows may not change, causing stale bytecode to be loaded even after
   the source was modified. CHECKED_HASH mode embeds a hash of the source
   content in the .pyc header and re-validates on every import, making
   cross-platform edits safe.


11. Batched score and buff-name OCR before any asset saves

   DECISION: In parse(), run all _ocr_score() and buff_ocr() calls for
   every row before any new buff PNG files are written to disk.

   RATIONALE: On Windows, writing a new asset file during parsing was
   observed to cause Tesseract to return empty strings for score OCR on
   subsequent rows (cross-row contamination). Batching all OCR work in a
   first pass and deferring all filesystem writes to a second pass
   completely decouples the two operations, eliminating the interaction.


12. MIN_WORD_LEN=4, MIN_THRESHOLDS=1 for buff OCR filtering

   DECISION: Accept a buff OCR result only if every extracted word has at
   least 4 characters and at least 1 threshold run produced the result.

   RATIONALE: Short fragments (1-3 characters) are overwhelmingly OCR noise
   (stray pixels read as letters, punctuation misread as letters). Genuine
   buff name words are always multi-character English words. MIN_THRESHOLDS=1
   is intentionally permissive to maximise recall on first-encounter buffs
   while still requiring the result to come from a real threshold pass.


13. Y-position word ordering in buff OCR

   DECISION: Sort extracted words by their Tesseract-reported Y-coordinate
   before joining into a final buff name.

   RATIONALE: Tesseract returns words in reading order within its detected
   text blocks, but multi-line buff icon labels can be returned out of
   top-to-bottom order depending on block detection. Sorting by Y ensures
   the assembled name matches the visual top-to-bottom layout of the label.


14. Daily Gunsmoke OCR approach

   DECISION: Use PSM 6 at 8× upscale as the primary mode for stat cells,
   with a PSM 4 retry for values whose digit count is <= 2, and trim the
   bottom 15% of every stat cell before OCR.

   RATIONALE — PSM 6 as primary:
   The stat table uses two text elements per cell (a percentage and a raw
   value) laid out as a mini two-line block. PSM 6 (assume a uniform block
   of text) correctly captures both lines in a single pass and is the
   natural mode for small structured regions at high upscale.

   RATIONALE — PSM 4 fallback for short values:
   When the raw value is a small number (1–2 digits, e.g. "64"), it sits
   at the right edge of the cell with very little surrounding whitespace.
   PSM 6's block assumption causes it to merge or drop such values. PSM 4
   (assume a single column of text) is more tolerant of narrow text and
   recovers these cases reliably.

   RATIONALE — 15% bottom trim:
   Each stat cell contains a horizontal progress bar occupying roughly the
   bottom 15% of its height. The bar's coloured pixels are read by Tesseract
   as digit-like glyphs (especially "1", "I", "l"), corrupting the numeric
   extraction. Trimming the bottom 15% before OCR removes the bar entirely
   without clipping any digit baseline.


15. Daily Gunsmoke portrait extraction via bounding-box detection

   DECISION: Replace fixed-ratio column cropping (x=0.000–0.083) for
   portrait extraction with contour-based bounding-box detection.

   RATIONALE: The fixed ratio was calibrated to the horizontal position of
   the portrait column but did not account for the vertical position of the
   portrait square within each row. Because rows vary in height across
   captures and the portrait frame does not always start at the top of the
   row, fixed-ratio crops produced inconsistent framing — sometimes clipping
   the portrait, sometimes including excessive background.

   The contour-based approach is self-localising:
     1. Search the left 15% of each row (generous enough to always contain
        the portrait regardless of minor positional drift).
     2. Binarize against the local background colour (most-common pixel)
        with a delta=30 tolerance.
     3. Find the largest roughly-square external contour.
     4. Crop to that contour's tight bounding box.
   This yields a consistent, tight crop regardless of row height or vertical
   offset, and requires no per-resolution recalibration.


8.  GUID deduplication

   DECISION: Use a looser pHash threshold (20) for dedup checks against
   existing GUIDs, separate from the match threshold (6).

   RATIONALE: When the same unknown doll appears in multiple rows or
   multiple screenshots, it should only be saved once. A looser threshold
   handles slight crop size differences (e.g. 128px vs 129px row height)
   that would otherwise generate duplicate GUIDs.


16. _split_panels guard: require ≈50/50 split

   DECISION: Tighten the panel-split guard from 0.2–0.8 to 0.4–0.6.

   RATIONALE: A legitimate 2-panel "Challenge Points" layout always
   produces two equal-width panels (split ≈50% of image width). A bright
   vertical UI element inside a single-panel image (e.g. the column
   separator at x≈33%) can fall inside the old 0.2–0.8 range and trigger
   a spurious split. The tighter range safely rejects these while still
   accepting any real 2-panel layout (which is always within 40–60%).


18. Blob pipeline for stat-cell OCR (stat_ocr.py)

   DECISION: Implement a contour + projection-correlation classifier
   (stat_ocr.py) as Pass 0 for Daily Gunsmoke stat cells, falling back
   to Tesseract only when the blob pipeline returns None.

   RATIONALE: Tesseract is ~250ms/cell on small (~30×50px) crops. With
   40 cells per image and two images typical per run, Tesseract-only stat
   OCR costs ~20s. The blob pipeline (contour detection → normalize →
   feature match) handles 35–40/40 cells in ~10ms total, a 25× speedup.

19. Projection-based doll name classifier (doll_name_ocr.py)

   DECISION: Implement a 1-D column-projection nearest-neighbour classifier
   for doll names as a fast path before Tesseract in daily_gunsmoke.py.
   Use a fixed high-brightness threshold (≥200) rather than Otsu/adaptive
   binarization to isolate the white name text.

   RATIONALE: Tesseract runs at ~176ms per name cell.  With 5 dolls per
   panel and 2 panels per image, that is ~1.76s in name OCR alone.
   The projection classifier runs in ~1ms.  Otsu binarization was attempted
   first but rejected: it captures the surrounding game-UI decoration (which
   is similar across all doll rows), producing near-identical feature vectors
   that cannot discriminate between names.  A fixed high threshold isolates
   only the bright white text pixels that differ per name.


20. Projection templates are self-bootstrapping via EMA update

   DECISION: After each batch of daily gunsmoke images, flush OCR-confirmed
   name crops to templates using an exponential moving average (alpha=0.3)
   rather than a full rebuild.

   RATIONALE: A full rebuild from scratch would require running Tesseract on
   every image every time.  The EMA approach allows the template library to
   grow incrementally: first run uses Tesseract for all dolls, subsequent
   runs use projection for already-seen dolls, with templates converging
   toward more accurate centroids over time.  Build from a folder of images
   (--build) is available for an explicit cold start.


21. Projection result passes through fuzzy correction

   DECISION: Apply _fuzzy_correct() to the projection classifier result as
   well as to the Tesseract slow-path result.

   RATIONALE: Templates may carry stale mislabelled names (e.g. "Sharkty"
   built from OCR data before the portrait was renamed).  Fuzzy correction
   provides a second chance to snap a near-correct projection result to the
   true name once the portrait file is correctly named, without requiring a
   full template rebuild.



24. Extract Daily Gunsmoke output utilities into gfl2/dg_output.py

   DECISION: Move JS model (DollRow, ReportEntry, save_js), portrait-save
   helpers (_crop_portrait, _save_doll_portrait), and name-OCR utilities
   (_get_doll_name_ocr, _known_doll_names, _fuzzy_correct, flush_name_templates)
   from daily_gunsmoke.py into a separate gfl2/dg_output.py module.

   RATIONALE: Separating I/O from parsing keeps daily_gunsmoke.py focused on
   image analysis.  The interface boundary is explicit: the parser produces
   DollRow / ReportEntry objects; dg_output handles all I/O.


25. Migrate daily_gunsmoke.py from flat timing to TimerStack

   DECISION: Replace the flat _T dict / _record() / print_timing_summary()
   pattern with gfl2.timing.TimerStack, matching the approach already used
   in daily_gunsmoke2.py.

   RATIONALE: The flat pattern required manual bookkeeping and could not
   represent nested calls (e.g. stat_cell/blob called inside extract_doll_rows).
   TimerStack uses context managers and builds a Span tree automatically,
   producing hierarchical output that makes hot spots obvious at a glance.
   Migrating dg1 also means both parsers now share the same timing API,
   so batch_summary() in main.py works uniformly for either parser.


27. stat_ocr: K-suffix detection via rightmost-'?' heuristic, not template classification

   DECISION: K and M are not classified by the projection/Hu pipeline at inference
   time. Instead, _reconstruct_val applies a post-classification heuristic: if
   the rightmost glyph is '?' and the value has ≥ 4 items (3+ digits + K), substitute
   'K'. Templates for K/M are still built (for future use) but the classifier
   deliberately uses PROJ_VERY_LOW=0.35 to return '?' for glyphs with very low
   projection confidence, letting the heuristic handle them.

   RATIONALE: K glyphs in ib_d images have projection scores ~0.27 against all
   digit templates — too low for reliable classification, and Hu moments misfire
   (gave '2'). The heuristic is safe because K always appears as the rightmost
   character in a K-suffixed value, and only fires when preceded by ≥ 3 digits.


28. stat_ocr: partial val results with '?' markers instead of None

   DECISION: _reconstruct_val returns strings containing '?' (e.g. '44?', '1??1K')
   when some glyphs cannot be classified, rather than returning None. The downstream
   _v() in dg_output.py treats any value containing '?' as null in JS output.

   RATIONALE: Returning None for the whole val when one glyph fails discards useful
   partial information and makes the verify output harder to read (you can't tell
   whether it was a near-miss or a total failure). '44?' makes it clear that 2 of 3
   digits were classified correctly. The '?' marker is propagated rather than
   silently dropped so callers can decide how to handle uncertainty.


29. stat_ocr: GT override file for Tesseract ground-truth errors

   DECISION: stat_gt_overrides.json (project root) maps {source_key: {pct, val}}
   and is auto-loaded by BOTH --build and --verify, in gfl2/stat_ocr.py and
   gfl2/stat_ocr_padded.py, and by build_templates() itself (so
   assets/builders/build.py, which calls build_templates() directly and
   bypasses both CLIs, is covered too).  Entries override Tesseract GT for
   specific cells where Tesseract is known to be wrong.

   RATIONALE: Tesseract ground truth for ib_d images contains occasional reading
   errors (e.g. '5143' read as '8143', '197' read as '191'). Without overrides
   these appear as pipeline mismatches even when the blob pipeline is correct.
   A separate file keeps corrections out of the source code and makes them
   auditable.

   UPDATE (2026-07-03): originally --verify-only, per docs/known_issues.txt
   §15.  A --verify-only override can correct the accuracy *report* but
   cannot stop --build (or assets/builders/build.py's independent
   stat-cell training pass) from baking the same bad Tesseract label into
   the template it's building.  That gap let a mislabeled '2'→'3' glyph
   contaminate assets/fonts/stat_val.py across every rebuild until this
   session, invisible because the eval ground truth was generated by the
   same contaminated pipeline (see decision 46 below).  Moving the
   override application into build_templates() — the one function every
   build path shares — closes the gap for any future caller, not just the
   two known today.


30. stat_ocr: inner-blob count as a structural discriminator for digit confusion

   DECISION: Count enclosed holes (RETR_CCOMP hierarchy) in each normalised
   glyph as a pre-filter and reverse-check inside _classify.  Modal hole count
   is stored per template character in templates.json as "inner_blobs".

   Pre-filter: if query has >0 holes, restrict candidates to templates whose
   modal hole count matches.  Reverse check: if projection selects a template
   with ≥2 holes (i.e. '8') but the query has 0 holes, redirect to the best
   zero-hole candidate instead.

   RATIONALE: Projection and Hu features for '5' and '8' are too similar at
   8×13 px (NORM_W_VAL × NORM_H_VAL) to distinguish reliably.  Hole count is
   a categorical discriminator: '8' always has 2 holes; '5' always has 0.
   Adding more training images (the alternative) would not help if the shape
   features are inherently ambiguous at this resolution.


31. stat_ocr: VAL_STRIP_Y raised to 0.50 to prevent pct-line bleed

   DECISION: Changed VAL_STRIP_Y from (0.44, 0.82) to (0.50, 0.82).

   RATIONALE: The pct and val strips were overlapping by ~4 rows.  Bottom
   fragments of pct-line digits (rows 36–40 of the 84 px cell) appeared in
   the val strip as y=0 noise blobs.  _filter_y_outliers could not clean them
   because they outnumbered the real val blobs, dragging the median to y≈0
   and incorrectly evicting the real glyphs.  Raising the val-strip start to
   0.50 clears all pct-line content with ≥4 rows of margin while keeping the
   real val glyphs (absolute y≈0.58–0.74) well within the strip.


32. stat_ocr: _filter_y_outliers applied per-strip in _read_line and build

   DECISION: Apply _filter_y_outliers to blob lists in _read_line (inference)
   and in build_templates (training) immediately after _find_blobs.

   RATIONALE: The strip-based read() path introduced in the previous session
   omitted the _filter_y_outliers call that _split_lines used to perform.
   Residual noise blobs (y-outliers from strip boundary bleed or adjacent UI)
   can corrupt glyph extraction.  The filter is a cheap defence that was
   always intended for this purpose.


33. Header stats-row crops use dedicated binarization threshold and min-height filter

   DECISION: In daily_gunsmoke._read_stat_crop and build_header_templates._collect_samples,
   use HDR_THRESH=155 (not stat_ocr's THRESH_BIN=180) and HDR_BLOB_MIN_H=12 (not
   DOT_MAX_DIM=8) when binarizing and filtering blobs from header stats crops.

   RATIONALE:
   - THRESH_BIN=180 causes adjacent digits to merge: at that threshold '4'+'8' in the
     header font produce one 24 px blob instead of two 11 px blobs, making them
     unclassifiable. Threshold 155 cleanly separates all digit pairs observed.
   - DOT_MAX_DIM=8 is designed to catch decimal-point blobs (w≤8 AND h≤8). Comma
     thousand-separator blobs (from "48,500") have h≈5–7 (below 8) and w≈6 but their
     h can reach 10, slipping through as "digit" blobs and corrupting alignment.
     A minimum height of 12 filters all comma/noise blobs (h<10) while keeping all
     real digit glyphs (h≈16–17).
   - Both constants must match between build_header_templates.py and
     _read_stat_crop; a mismatch causes templates built at one threshold to be
     matched against blobs extracted at a different threshold, producing systematic
     misclassification.

34. _find_percent_x_start: aspect-ratio guard for merged-% detection

   DECISION: In Case A (merged '%' blob detection), accept blobs that satisfy
   either the classic width threshold (w ≥ PCT_MERGED_W=18) OR are nearly square
   (w ≥ h * 0.90), provided h ≥ LARGE_H_MIN.

   RATIONALE: The merged '%' glyph is roughly square (w/h ≈ 1.0) while pct-line
   digit blobs are taller than wide (w/h ≈ 0.7). At some screenshots/resolutions
   the fused '%' renders at w=17 (just below PCT_MERGED_W=18), causing Case A to
   fail and the '%' to be misidentified as a digit, producing a spurious trailing
   digit in the pct result. The aspect-ratio guard catches these near-square blobs
   without risk of false-positives on digit blobs.

35. _classify: clear-winner shortcut for robust but sub-threshold projections

   DECISION: After the PROJ_VERY_LOW guard and before the Hu tiebreaker, add a
   "clear-winner" shortcut: if the best combined score ≥ 0.55 AND the gap to the
   second-best ≥ 0.10, return the best candidate (with the same reverse inner-blob
   check as the main confidence path).

   RATIONALE: val '0' crops consistently score combined ≈ 0.58–0.67 — just below
   PROJ_CORR_MIN=0.70 — but win decisively over all other candidates. The Hu
   tiebreaker is useless for these crops (all Hu distances >> HU_HALF_DIST_MAX).
   The gap guard (≥ 0.10) prevents near-tie cases from misfiring while still
   catching val '0' cases whose gap ranged from 0.101 to 0.248 in the test set.

36. _read_line: tighter _filter_y_outliers threshold for val strips

   DECISION: Pass threshold=8 to _filter_y_outliers for val strips, vs 12 for pct.

   RATIONALE: Val digits sit on a single tight baseline (observed cy spread < 5 px).
   Pct-line fragments that bleed into the top of the val strip have cy ≈ 5 while
   legitimate val blobs have cy ≈ 14 (gap = 9 px). The existing threshold=12 kept
   these fragments; threshold=8 removes them without touching any legitimate glyph.
   Pct strips are more dispersed (bottom-circle of '%' sits lower), so they retain
   the looser threshold=12.

38. Auto-configure Tesseract path in gfl2/__init__.py

   DECISION: When `tesseract` is not found on PATH and the Windows default
   install path exists, set `pytesseract.pytesseract.tesseract_cmd` at
   package import time in gfl2/__init__.py.

   RATIONALE: The same pattern existed in stat_ocr.py but only for the
   --build/--verify code path. layout.py, buff_ocr.py, weekly_gunsmoke.py,
   and daily_gunsmoke.py all import pytesseract at module level and would
   raise TesseractNotFoundError if the executable was not in PATH (common
   on Windows where the Tesseract installer does not add itself to PATH by
   default). Centralising the configuration in __init__.py means it runs
   once before any submodule imports pytesseract, so no individual module
   needs to handle it.


39. Weekly doll crops normalised to 128×128 before asset matching

   DECISION: In weekly_gunsmoke._parse_row, pass each doll column crop through
   normalize_portrait() (dg_output.py) before calling AssetMapper.translate().
   normalize_portrait extracts a fw×fw square centred at y0=(h−fw)//2 and
   resizes to PORTRAIT_NORM (128×128) using LANCZOS4.

   RATIONALE: The weekly column crop has width fw (portrait width) but height
   equal to the full row height. Without normalisation, a 90×128 weekly crop is
   compared against a 128×128 daily portrait asset, producing HSV histogram
   scores of ~0.49 (threshold=0.88) — no match possible.  After normalisation,
   cross-image matching between screenshots at different resolutions (90×128 vs
   75×106) reaches 0.96+ histogram correlation.

   The fw×fw square crop is geometry-derived: the portrait fills the detected
   column width exactly (confirmed by hair-blob width-fraction measurement, which
   is identical — 0.578 — in both daily and weekly crops).  Background subtraction
   was rejected because the row background and portrait background share similar
   brightness, making the most-common-pixel estimate unreliable.

   conftest._seed_doll_assets also applies normalize_portrait when writing test
   seeds so seeds use the same 128×128 format as production queries.


37. _reconstruct_pct: strip leading/trailing dot noise

   DECISION: Apply result.strip('.') after assembling the pct string.

   RATIONALE: Tiny noise blobs at the left edge of the pct strip (e.g. x=8, w=3,
   h=2) pass blob-size and y-outlier filters and are classified as '.' (both dims
   ≤ DOT_MAX_DIM). A valid pct value always starts and ends with a digit, so
   stripping edge dots removes this artefact without risk of corrupting real values
   (the decimal point in "30.49" is interior, not at position 0 or -1).

40. Panel image slices use _split_panels(), not frame-position midpoints

   DECISION: In parse(), use _split_panels() (brightness-based midpoint in the
   header bar top third) to determine where to slice the image into left/right
   sub-images.  Frame-based detection (_find_all_frames + _group_frames_into_panels)
   is used only to assign frame lists to panels, not to compute slice boundaries.

   RATIONALE: Portrait frames are anchored at the LEFT EDGE of each panel.  The
   midpoint between the rightmost frame of panel N and the leftmost frame of panel
   N+1 therefore falls somewhere inside panel N's content, not at the visual boundary.
   _split_panels() finds the actual boundary by locating the brightest column in the
   centre of the header bar — a reliable proxy for the visual gap between panels.
   Using frame positions for slicing produced crops that read empty dark background
   instead of the actual header/stats content.


41. Adaptive threshold retry for merged digit pairs in header score

   DECISION: _header_isolate_blobs() tries binarization thresholds at THRESH_VAL+5,
   +10, +15, +20 and uses the minimum increment that yields more blobs than at the
   primary THRESH_VAL=150. Wide blobs (> NORM_W × 1.3 ≈ 26 px) are split using
   sub-blob positions from the higher threshold and normalised from that same image.

   RATIONALE: Adjacent digit strokes sometimes merge at the primary threshold
   (THRESH_VAL=150 causes "4"+"6" to merge into a single 27 px blob).  At a higher
   threshold strokes thin enough to separate.  Using the minimum effective increment
   keeps digit shapes as close as possible to the templates (built at THRESH_VAL=150)
   while resolving the merge.  Splitting post-hoc using a projection minimum on the
   merged blob was rejected: the split halves inherit the original blob height, and
   when normalized to NORM_H=30 they may not match templates built from taller digits.


42. Inner-hole count disambiguates '5' vs '6' in header score reading

   DECISION: _header_isolate_blobs() counts interior contours (RETR_CCOMP hierarchy)
   per blob and returns n_inner alongside (x, norm, w, h).  _read_bright_number()
   applies an override: if the best projection match is a no-hole digit
   ('1','2','3','5','7') but n_inner ≥ 1, redirect to the best-scoring hole-digit
   ('0','6','8','9') when its score ≥ 90% of PROJ_CORR_MIN.

   RATIONALE: At the higher binarization threshold needed to separate merged digit
   pairs, stroke shapes change enough that "6" (0.798 projection) scores below "5"
   (0.833 projection) despite being the correct answer.  This is a template-font
   mismatch: templates were built from a different font/size.  The inner-hole count
   is resolution-independent and categorical: "6" always has 1 interior hole
   (its bottom loop); "5" always has 0.  The same principle was already used in
   stat_ocr for '5'/'8' disambiguation; applying it here avoids rebuilding score
   templates from the header font.

   The ≥ 90% leniency on the hole-digit's score prevents the override from firing
   when the hole-digit is wildly implausible (score < 0.63 given PROJ_CORR_MIN=0.70).


43. Accumulator-based sub-timing for tight classifier loops

   DECISION: _classify() accumulates per-phase timing into a caller-supplied
   list[float] (acc) using time.perf_counter() deltas rather than
   with timer.timed() context managers inside the glyph loop.  _read_line()
   injects synthetic Span children after the classify block closes.

   RATIONALE: _classify() is called ~12 times per stat cell (one per glyph).
   Each with timer.timed() call allocates a Span object, appends to a list, and
   calls perf_counter() twice.  At ~40k classify calls per batch run, the per-call
   overhead adds up.  The accumulator approach makes only 4-6 perf_counter()
   calls per _classify() invocation (one at each phase boundary) and zero object
   allocations inside the loop.  The resulting synthetic Spans are identical to
   real Spans from the pipeline_summary aggregation perspective — they appear
   under the correct parent and are rolled up by name across all calls.


44. Weekly Gunsmoke output redirect: folder-sniffing over mandatory --output

   DECISION: main.py's weekly Gunsmoke CSV output keeps its existing
   "<image>.csv next to the image" default, EXCEPT when image_path resolves
   under tests/inputs/ (a committed test fixture) -- there
   _default_weekly_output() redirects to tests/outputs/weekly_gunsmoke/
   instead.  Rejected alternative: always require --output for anything
   outside a designated "production input" root.

45. Generated-report timestamps record run START, not run END

   DECISION: score_detect.py, stat_ocr.py verify(), and pct_fft_predict.py
   each stamp their generated reports with "Generated: <ISO 8601 local
   time>  (run start)" — captured once at the top of the run and threaded
   through to every report-writing call.  Rejected alternative: stamp at
   run END (when results were finalized).

   RATIONALE: the timestamp's use case is telling whether a report
   predates a template/asset rebuild --
   answered by comparing the report's timestamp against the template
   file's mtime.  START serves that comparison exactly as well as END
   would (a rebuild that happened after the run started but before it
   finished is not a real scenario in practice — rebuilds and benchmark
   runs are not interleaved), and START is simpler to implement: capture
   the clock once, pass one string down, done.  END would require either
   re-querying the clock at each report-writing call (multiple slightly
   different timestamps for outputs of the same run) or restructuring
   each script to defer all writes to a single point at the end.


46. stat_ocr: bottom-row width as a structural discriminator for '2'/'3'

   DECISION: Measure the foreground pixel span of a normalised glyph's LAST
   row, as a fraction of NORM_W, and use it as a categorical pre-filter in
   _classify() (same insertion point as decision 30's hole-count filter,
   applied right after it): fraction >= TWO_BOTTOM_FULL_MIN (0.80) rules
   out '3'; fraction <= THREE_BOTTOM_CURL_MAX (0.70) rules out '2'.
   Implemented identically in gfl2/stat_ocr.py and gfl2/stat_ocr_padded.py
   as `_bottom_row_width_frac()`.

   RATIONALE: decision 30's hole-count discriminator can't separate '2'
   from '3' — neither digit has an enclosed hole.  But the two are still
   categorically different in outline: '2' always ends in a full-width
   flat bottom stroke, '3' always curls inward.  Measured directly on
   confirmed samples at the 8×13 val canvas: '2' = 0.875, '3' <= 0.625 — a
   clean, wide gap, chosen because a specific font rendering of '2' in this
   corpus scored a razor-thin projection-correlation margin against '3'
   (0.726 vs 0.750) that plain projection scoring could not reliably win.
   See docs/known_issues.txt §15 for the investigation that surfaced this
   (a corrupted ground truth, not the classifier, was the original
   symptom) and docs/takeaways.txt for the broader methodological lesson.

   ADDENDUM 4 (2026-07-04): restructured _classify() from a single
   nearest-centroid lookup over the full 77d feature vector into two
   independent agents -- Agent A (gabor+paren+ring, unnormalized, margin
   gate 0.15) tried first, Agent B (the 64-bin histogram, z-score
   normalized with its own independently-tuned margin gate 0.05) consulted
   only when A is unsure.  Prompted by a direct question: why should any
   change to the histogram regress gabor/paren/ring's contribution at all,
   given they measure unrelated things?  It shouldn't -- the earlier
   regression (full-vector z-normalization collapsing '6'/'9', Addendum 2's
   "open question") was an artifact of forcing both feature blocks to share
   one Euclidean distance metric, not a real conflict.  Splitting them into
   independent agents with independently-tuned confidence thresholds (the
   first attempt reused Agent A's 0.15 for Agent B and found ZERO
   complementary coverage -- itself a miscalibration, not evidence of
   redundancy; 0.05 revealed real coverage) resolved it cleanly.

   RESULT: the best outcome in this exploration's history by a wide margin.
   Cell-level pct accuracy on the 87-image corpus: 77.3% (prior best,
   single vector) -> 90.1%, at essentially unchanged timing (~1.09ms/cell,

   docs/known_issues.txt Sec15's TWO-AGENT CLASSIFIER entry; general lesson

   ADDENDUM 5 (2026-07-04): added a PAIR TIEBREAK override to _classify(),
   DISABLED BY DEFAULT (PAIR_TIEBREAK_DEFAULT=False, opt-in via
   --enable-pair-tiebreak / StatOcrFft.load(enable_pair_tiebreak=True)).
   Per-digit error analysis showed '4' carrying 23 of 52 held-out errors,
   all misclassified as '7' -- both digits fit '-' and '/' by construction,
   so no line feature can separate them; paren_( is the only Agent A
   dimension that argues for '4', but it has 6x the within-class variance
   of any other dimension specifically for '4', and dominates the actual
   error cases by >4x over every other dimension combined.

   Two more general approaches were tried and rejected before this one:
   globally excluding paren_( from '4' comparisons fixed '4' but opened a
   worse '9'->'4' confusion (fewer dimensions mechanically shrinks a
   centroid's apparent distance to everything, not just '7'); a universal
   lines-first candidate-narrowing cascade fixed '4' and slightly helped
   '9' but broke '3' and '0', confirming a UNIVERSAL per-class feature
   exclusion or cascade is a dead end -- the same "features leak across
   digit families" argument that explains why '4'/'7' collide on arcs
   implies lines can just as easily leak into arc-dominant digits.

   The fix that worked: scope the override to trigger ONLY when the flat
   classifier's own top-2 nearest centroids are exactly a registered pair
   (219/1982 held-out glyphs for {'4','7'}).  Every other digit's
   classification is provably unaffected.  '4' improved from 135/197
   correct (23 as '7') to 188/197 (0 misclassified); cell-level pct
   accuracy 90.1% -> 93.2% with it enabled.  Shipped disabled by default
   because it's validated on exactly one pair and one dataset -- a second
   independent corpus would justify defaulting it on.  Full investigation
   trail (including the two dead ends) in docs/known_issues.txt §15's
   PAIR TIEBREAK entry.

   ADDENDUM 6 (2026-07-04): added debugs/calibrate_gabor.py, a reusable
   CLI tool that re-tunes the Gabor kernel's (lambda, sigma, gamma) --
   never tuned for this font specifically, only inherited from an earlier
   general-purpose sweep -- as a ROOT-CAUSE alternative to ADDENDUM 5's
   downstream PAIR TIEBREAK patch.  gfl2/stat_ocr_fft.py gained
   set_gabor_params() so a candidate's kernels can be swapped in-process.

   Two proxy-metric scoring attempts were tried and rejected before one
   that worked: (1) leave-one-out nearest-centroid accuracy on the 3 Gabor
   dims alone found a candidate that dominated the default on every
   isolated metric yet regressed the real classifier (90.1%->86.5% pct
   accuracy) because Agent A never uses Gabor without paren+ring; (2) the
   same LOO metric recomputed on the full 13-dim gabor+paren+ring vector
   still regressed the real classifier (90.1%->88.2%) because a
   nearest-centroid proxy has no way to model Agent B, the confidence-
   margin gating between the two agents, or '?' no-read behavior -- a
   third instance of "looks better in isolation, worse in combination."
   The fix that worked: score every candidate by calling the REAL
   `_classify()` two-agent decision function over every training glyph
   (in-sample, matching this project's own --build/--verify convention),
   not any feature-space proxy.

   RESULT: lambd=5.0/sigma=2.0/gamma=0.5 (default was 4.0/2.0/1.0).

   direct payoff of fixing the root cause instead of patching around it);

   target the same '4'/'7' confusion, so they overlap rather than stack,

   either).  PAIR TIEBREAK is kept, still disabled by default -- it is not

   configuration's tiebreak run reaches alone.  Full investigation trail

50. Shared Tesseract ground-truth cache across all three stat_ocr engines

   DECISION: gfl2.stat_ocr._collect_cells() gained an optional gt_cache
   parameter ({source: {"pct","val"}}, consulted before calling Tesseract
   when tess_only=True; a miss falls back to live Tesseract for that cell
   only).  Mirrored into gfl2/stat_ocr_padded.py's own duplicate
   _collect_cells (same source-key format, so one cache file serves both).
   gfl2/stat_ocr_fft.py, which already imports _collect_cells rather than
   duplicating it, picked up the parameter automatically.  All three
   engines' verify() gained a matching gt_cache parameter (None auto-loads
   the cache, {} forces live Tesseract) and their CLIs gained --no-gt-cache.
   A new script, debugs/build_tess_gt_cache.py, runs the Tesseract pass
   once over a chosen image set and writes tests/inputs/daily/tess_gt_cache.py.

   RATIONALE: building/verifying decision 49's stat_ocr_fft.py end to end
   meant running --build then --verify back to back, each independently
   re-collecting pure-Tesseract labels for the same 87-image, 3216-cell
   single/*.png corpus (~1200s / 20 min per call) — two calls, ~40 minutes,
   for labels that cannot have changed between them.  This is true of every
   --build/--verify call across all three engines, not just this one pair:
   the corpus is static and Tesseract's output on it is exactly
   reproducible, so re-running it every time is pure waste with no
   corresponding correctness benefit — these commands are not testing
   Tesseract, they use it as a fixed oracle.  Caching the oracle's output
   once and reusing it turns a ~20-minute step into a sub-second dict
   lookup for every subsequent call against the same images.

   Kept as an explicit opt-out (--no-gt-cache) rather than removing live
   Tesseract collection entirely: the cache is a plain snapshot with no
   staleness detection, so anyone who has re-cropped or replaced images in
   single/ needs a way to bypass it and confirm live Tesseract still
   agrees, or to regenerate it via debugs/build_tess_gt_cache.py.  A cache
   miss (image or cell not present in the file) already falls back to live
   Tesseract automatically, so adding new images without regenerating the
   cache degrades to "slower for the new images only," not silent
   staleness.

   DECISION: added `_pct_strip_bottom(ch)` to gfl2/stat_ocr_fft.py:
   `min(ch, int(ch * PCT_STRIP_Y[1]) + 5, int(ch * VAL_STRIP_Y[0]))`.
   Extends the pct-line extraction strip by a fixed 5px, capped so it can
   never cross into where the val line starts.  Wired into both
   `_extract_pct_digit_glyphs` and debugs/debug_stat_ocr_fft_failures.py's

   re-deriving the arithmetic, so the debug images can't silently drift
   from what build/verify actually see).

   RATIONALE: docs/known_issues.txt §21 found that PCT_STRIP_Y's fixed
   0.46 fraction clips digit blobs with ZERO slack on this corpus's

   inspecting debugs/debug_stat_ocr_fft_failures.py's raw/binarized crop

59. gabor_45's degenerate-normalization fix was reverted from production
    after real-pipeline measurement, despite fixing a genuine bug

   DECISION: gfl2/stat_ocr_fft.py's compute_features() computed Gabor as a
   self-fraction (resp/(sum(resps)+eps)) that collapses to a constant ~1.0
   once N_ORIENT dropped to 1 (known_issues.txt §24). Replaced it with the
   raw response magnitude, z-scored against pooled training mu/sigma (the
   same convention Agent B's histogram already uses) before folding it
   into Agent A's gpr vector -- a real fix, confirmed non-degenerate
   (per-digit centroid values went from a constant 1.0 to real variation,
   -1.60 to +1.18). Rebuilt and re-verified: glyph-level accuracy dropped
   from 100.0% (10327/10327) to 87.12% (375 misclassified, 955 unknown).
   REVERTED both gfl2/stat_ocr_fft.py and debugs/calibrate_gabor.py (which
   had been updated in lockstep to keep its calibration scoring faithful
   to production, per decision 47's "keep duplicated build math in sync"
   discipline) back to the exact pre-fix code. Confirmed byte-identical to
   the documented 100.0% baseline afterward.

   RATIONALE: Agent A's gpr block is unnormalized BY DESIGN -- paren,
   ring, loop, vstroke, hbar all live on a comparable [-1,1]-ish
   correlation/fraction scale. A z-scored dimension's typical per-glyph
   swing (roughly -3..+3, with real measured within-class noise up to
   std~0.4-0.5 for some digits after z-scoring) is large enough to
   dominate Agent A's L2 distance and confidence-margin gate on its own,
   rather than contributing proportionately alongside the other 15 raw
   dims. This is the same "different feature blocks need their own scale,
   don't force one shared distance metric" failure mode already
   documented twice in calibrate_gabor.py's own IMPORTANT CORRECTION #1/#2
   dead ends and in the original Agent A/Agent B split (known_issues.txt
   §15's TWO-AGENT CLASSIFIER section) -- now confirmed a third time, at
   the single-dimension level instead of a whole feature block.

   FIX KEPT, NOT DELETED, JUST NOT WIRED IN: the corrected raw-response
   computation is preserved as a standalone measurement primitive in
   debugs/debug_gabor_45_zscore_verify.py (mirrors this project's

   but-not-integrated capability documented rather than discarding the
   work). That script went on to find gabor_45's raw value is a strong

   Full test suite unaffected throughout (1287 passed / 14 skipped /
   2 xfailed) -- stat_ocr_fft.py has no dedicated test file and this

60. The {1,4,7} vstroke gate controls WHETHER a feature runs, never WHAT
    it's compared against -- a structurally different (and safer) kind of
    change than decision 59's reverted attempt

   DECISION: implemented gfl2/stat_ocr_fft.py's validated {1,4,7}
   pass-through gate (known_issues.txt §24) as enable_vstroke_gate, an
   opt-in parameter (DISABLED BY DEFAULT, same convention as
   PAIR_TIEBREAK_DEFAULT) threaded through compute_features()/_classify()/
   _reconstruct_pct()/StatOcrFft.__init__/.load()/verify()/verify_glyphs(),
   with a --enable-vstroke-gate CLI flag.

   DESIGN CHOICE, and why it's safe where decision 59's attempt wasn't:
   decision 59 regressed accuracy by inserting a z-scored gabor value AS A
   NEW DIMENSION into Agent A's shared L2 distance -- it changed what
   every classification decision was comparing against. This gate does the
   opposite: it changes whether vstroke's expensive 2D-sliding search runs
   at all, never what's compared. compute_features() decides internally
   using resps[0] (the Gabor response already computed for the gabor
   block's own feature -- reused, not recomputed) against a validated
   interval (VSTROKE_GATE_LO/HI); when the glyph is judged outside
   {1,4,7}, vstroke's slot is NaN instead of a computed value.
   _sorted_distances() and _pair_tiebreak() were made NaN-safe: a NaN in
   the query drops that ONE dimension from the L2 distance for BOTH the
   query and every centroid, reusing the exact "exclude an unreliable
   dimension" technique PAIR_TIEBREAK_RULES already established, just
   triggered by "wasn't computed" instead of a hardcoded per-pair rule.
   build_templates() is completely untouched -- training always computes
   the full vector, so centroids and existing shipped templates are
   byte-identical; no rebuild was required for this change.

   VERIFIED: --verify-glyphs with the gate at its default (off) reproduces
   the pre-existing 100.0% (10327/10327) baseline byte-for-byte -- the
   parameter's mere existence changes nothing for any caller that doesn't
   opt in.

   MEASURED WHEN ENABLED (87-image corpus, both glyph- and cell-level):
      glyph accuracy   100.0% -> 99.78%   (23 new misclassifications)

    wholesale alternative to the flat two-agent nearest-centroid path --
    inner-blob hole count is the feature that made this shape work

   DECISION: implemented _classify_hierarchical() in gfl2/stat_ocr_fft.py,
   an opt-in (enable_hierarchical / HIERARCHICAL_DEFAULT = False, same
   convention as every other flag in this file) alternative ALGORITHM to
   the flat TWO-AGENT CLASSIFIER, proposed directly (not discovered by this
   module's own exploration) on the observation that every weak classifier
   already documented here (gabor_45's {1,4,7} gate, vstroke, hbar, paren)
   works better as a BRANCHING decision tree than as one more dimension in
   a shared L2 distance -- the same lesson decision 59 already learned the
   hard way for gabor_45 specifically. The new ingredient is production's
   existing inner-blob hole-count discriminator (gfl2.stat_ocr.
   _count_inner_blobs, §9/§14 -- reused as-is, not reimplemented), which
   roots the arc-dominant half of the tree exactly the way it already roots
   part of production's own classifier.

   TREE (see module docstring's HIERARCHICAL CLASSIFIER section for the
   full diagram and per-node rationale):
     gabor_45 (the §24 {1,4,7} gate) splits line-dominant from arc-dominant.
     Line-dominant: vstroke cleanly isolates '1' (cheap, reliable); {4,7}
       falls through to the FULL feature cost + the already-validated
       PAIR_TIEBREAK_RULES exclusion for that exact pair.
     Arc-dominant: inner-blob hole count splits 3 ways -- 2 holes = '8'
       (categorical, free); 1 hole = {0,6,9} via paren+loop together;
       0 holes = {2,3,5}, NOT resolved by a dedicated node (no cheap 1-2
       dim feature reliably separates them) -- falls back to the FULL flat
       two-agent _classify() rather than a weaker stand-in.
     Every non-root decision is nearest-centroid on a CANDIDATE-SET- and
     DIMENSION-restricted slice of the SAME already-trained "gpr"
     centroids the flat path uses -- no separate training, no rebuild.

   TWO DESIGN ASSUMPTIONS FAILED WHEN MEASURED, BOTH FIXED THE SAME WAY:
   the first version used vstroke ALONE to split '7' from {1,4}, and paren
   ALONE to split {0,6,9} -- both looked plausible from the tree's own
   motivating structure. Measured on the real corpus: vstroke alone
   misclassified 262/993 '4' glyphs as '7' (centroids only 0.09 apart,
   '4' std 0.057 -- wide enough to drift past the midpoint); paren alone
   misclassified 119/859 '6' glyphs as '9' (known_issues.txt §15 already
   documented paren landing near-neutral on '9', which is EXACTLY why
   loop_top/loop_bot were built as a follow-up feature for this pair).
   Both fixes reused ALREADY-VALIDATED existing mechanisms instead of
   inventing new ones: the {4,7} leaf now pays full compute_features()
   cost and resolves via PAIR_TIEBREAK_RULES's own paren_(-exclusion; the
   {0,6,9} leaf now uses paren+loop together (4 dims, matching what
   already resolves this trio in the flat path). A third fix improved the
   {2,3,5} fallback from Agent B alone (weak: measured 82.4%/86.1% overall
   accuracy in two earlier iterations) to the FULL flat _classify() --
   free to wire up (module-level functions resolve at call time, so
   _classify_hierarchical calling _classify is a plain forward reference,
   not a refactor) and strictly better than a weaker stand-in.

      metric                     flat (baseline)        hierarchical
      glyph accuracy             10327/10327 (100.0%)   10325/10327 (99.98%)

   sequence on shrinking candidate sets, not when they're flattened into

   DECISION: added a real hbar_mode parameter to gfl2/stat_ocr_fft.py's
   compute_features()/build_templates()/_classify()/_classify_hierarchical()/

   CLI flag. "sliding" (HBAR_MODE_DEFAULT, unchanged) is the original 2D-

   TEMPLATE FILE SEPARATION: sobel-mode centroids are trained/saved to a
   SEPARATE file (assets/fonts/stat_pct_fft_hbar_sobel.py), not merged
   into the existing stat_pct_fft.py -- the two modes' hbar dimension
   VALUES are not comparable (different feature entirely), so a shared
   file storing both would risk silently loading mismatched centroids.
   Same reasoning as decision 47's padded-pipeline template separation.

   MEASURED (87-image corpus, hbar_mode="sobel" vs "sliding" baseline):
      cell accuracy    98.9% -> 47.6%   (SEVERE regression)
      cell classify    5558.5us -> 3592.8us/cell   (-35%, real speedup)
      glyph accuracy   100.0% -> 66.9%
      glyph classify   1654.5us -> 1192.3us/glyph   (-28%, real speedup)

   ROOT CAUSE: the sobel feature's raw magnitude (~1e7) is ~7 orders of
   magnitude larger than every other Agent A dimension (all ~O(1)), so it
   completely dominates the unnormalized L2 distance regardless of what
   any other dimension says.

   NORMALIZATION TRIED, DID NOT FIX IT: implemented the standard fix --
   z-score the sobel hbar values against the pooled training distribution
   (hbar_mu/hbar_sigma, computed in build_templates(), applied via a new
   _apply_hbar_norm() at inference), exactly matching Agent B's own
   histogram z-score convention. Rebuilt and re-verified: BYTE-IDENTICAL
   result to the unnormalized version, even though the centroids
   themselves are now genuinely O(1)-scaled (confirmed by direct
   inspection: -1.4 to +2.1, not millions). Z-score normalization fixes a
   dimension's WITHIN-class variance scale; it does nothing about
   BETWEEN-class separation scale. The other gpr dimensions are weak,
   noisy discriminators whose centroids cluster tightly (spans of
   ~0.1-0.6); sobel-hbar, even z-scored, has a much wider between-digit
   spread (~3.5 z-units) because it is simply a stronger signal --
   rescaling a feature's units doesn't equalize its decisive weight
   against neighbors that were never that discriminative to begin with.

   SHIPPED DISABLED BY DEFAULT (HBAR_MODE_DEFAULT="sliding"), kept as a
   real, working, documented negative result rather than reverted -- same
   "kept, not deleted" convention as the disabled wedge feature. This is
   the THIRD time this file's own history has hit the identical lesson
   (§15's original TWO-AGENT CLASSIFIER redesign; decision 59's reverted
   z-scored-gabor attempt; now this): a feature that is a fundamentally
   different KIND of signal -- here, dramatically more discriminative,
   not just differently scaled -- should not be flattened into one shared
   distance at all. The properly-fixed approach would be a real third
   "Agent C" with its own margin gate and dispute-resolution logic
   (matching how Agent A/B themselves were separated) -- not attempted,
   out of scope for this pass. See decision 66 for the SAME underlying
   feature used correctly (an isolated comparison, sidestepping this
   exact problem) in the new {2,3,5} hierarchical leaf.

   Full test suite unaffected throughout (1287 passed / 14 skipped /
   2 xfailed) -- the default hbar_mode="sliding" path is byte-identical to
   before this change (confirmed via --verify-glyphs: 100.0%, 10327/10327,
   matching the pre-existing baseline exactly). EXPLORE-scope only.

71. Root-caused decision 70's remaining gap: the Gabor KERNEL itself was
    stale, not just the threshold on top of it -- recalibrating it closes
    §27's regression almost completely (98.8% cell / 99.99% glyph)

   CONTEXT: decision 70 left a real, acknowledged gap -- vstroke_gate
   (the interval-style constant that decides {1,4,7}-vs-rest routing)
   could not be safely recalibrated from the atlas, and was shipped
   excluded from the config, still falling back to its ORIGINAL hardcoded
   value (464.5, 672.0). That original value was itself derived

   ORIGINAL kernel (lambd=5.0, sigma=2.0, gamma=0.5) -- generated
   2026-07-04, predating §27's no-resize glyph-representation change by
   five days. Direct feedback identified the actual root cause: the gate
   threshold isn't the problem in isolation -- the RAW GABOR SIGNAL it
   thresholds is computed by a kernel that was never recalibrated against
   the current glyph representation at all. No threshold placement on top
   of a stale kernel can fix a signal that no longer cleanly separates the
   groups it needs to.

   PER-GLYPH CONFIRMATION (not inferred) that this is exactly what was
   happening: tracing decision 70's own widened-atlas-gate regression
   found 100% of the misrouted '0'/'3'/'5'/'6'/'9' failures went through
   line_1/line_47_sobel (forced into '1' or a '4'/'7' choice with no
   "neither" option) -- ZERO through the arc-dominant leaves, which
   classified every glyph that actually reached them correctly. A single
   upstream routing decision, not a cascading feature failure -- exactly
   the shape of problem a stale kernel produces.

   gate47/gate147, alongside the original flat_accuracy) that retunes
   (lambd, sigma, gamma) for the HIERARCHICAL classifier's raw-gabor gate

   specifically for the tightest achievable target ("segregate 4,7 from
   the rest") with the broader {1,4,7} group as an explicit, acceptable
   fallback if the tighter target isn't cleanly achievable.

   bled into that narrower target. At the strongest {4,7}-only kernel
   found (lambd=1.5, sigma=0.75, gamma=0.30): 100.0% recall, 3.68% false-

   for a gate that still isn't perfectly clean. The SAME kernel's {1,4,7}
   gate, by contrast: 99.97% recall / 0.00% false-trigger (finer step=1.0
   sweep) -- essentially perfect, and the existing tree already resolves
   '1' vs {4,7} downstream via vstroke with near-total reliability
   (centroids 0.961 vs 0.550/0.642, std 0.02 -- known_issues.txt §25).
   {1,4,7} is not a fallback settled for lack of a better option here --
   it is measurably the better target for THIS tree architecture, and
   happens to be achievable by the SAME kernel that's also the best (or
   tied-best) {4,7}-only candidate, so no trade-off was actually needed.

   GRID WIDENED, MEASURED NOT ASSUMED: the original flat_accuracy grid
   (_LAMBD_GRID=[2..8], _SIGMA_GRID=[1..2], _GAMMA_GRID=[0.25,0.5,1.0])
   does not contain the gate objective's real optimum. A first sweep at
   that range found gamma=0.5 outscoring every gamma<0.5 candidate tried,
   seemingly contradicting the "lower gamma should help" intuition
   directly raised in the request -- but a wider follow-up sweep (lambd
   down to 1.0, sigma down to 0.5, gamma down to 0.1) found the TRUE
   optimum at lambd=1.5, sigma=0.75, gamma=0.30, beating every gamma=0.5
   candidate once lambd/sigma were searched jointly with the lower gamma

   closed the gap was recalibrating the KERNEL (the actual root cause),

   distinction this project has hit before (known_issues.txt §15's PAIR

   upstream fix there too) -- worth checking explicitly, as a first step,
   whenever a threshold/gate stops working: is the THRESHOLD wrong, or is
   the SIGNAL it's measuring no longer what it used to be?

   single biggest cost center in the tree. Revisiting whether a cheaper
   feature could replace it (direct instruction: reconsider the {1,4,7}

      hypothesis was a real, measured NO.

      ITSELF only reaches 90.4% forced-choice / 8.22% false-trigger when

   ANY None from the blob engine (rare, for production/padded; ALWAYS,
   for dp's val) triggered a ~300-600ms whole-cell Tesseract pass. For
   dp specifically, this meant every single cell's val paid that cost,
   every time, turning a ~0.4s image into 15-19s for zero accuracy
   benefit over leaving val null -- not because the no-op was slow (it
   measured ~0.5-0.9ms, unchanged), but because the pipeline's EXISTING
   response to "no value" treated "engine hasn't implemented this at
   all" identically to "engine tried its best and failed," when only the
   second case is worth an expensive last resort.

   DECISION: rather than special-casing dp inside daily_gunsmoke.py
   (which would break that module's own explicit engine-agnostic
   contract -- it never imports or special-cases a concrete engine
   class, by design, per its own docstring), make the fallback itself a
   real, explicit, configurable choice: gfl2/patterns/daily_gunsmoke.py's
   `_extract_stat_cell()`/`_extract_doll_rows()`/`parse()` all gained a
   `tess_fallback: bool` parameter, LIBRARY-level default True (preserves
   existing behavior for every caller that doesn't pass it explicitly --
   direct parse() use, existing tests). main.py gained
   `--stat-tess-fallback`/`--no-stat-tess-fallback`
   (argparse.BooleanOptionalAction), CLI-level default FALSE, threaded
   into both daily-gunsmoke call sites (_process_daily_single,
   _process_daily_folder).

   THIS IS A REAL DEFAULT-BEHAVIOR CHANGE FOR PRODUCTION/PADDED TOO, NOT
   JUST DP -- accepted deliberately, not as a side effect. By default,
   `python main.py <img> --pattern daily_gunsmoke` (no flags at all) no
   longer calls Tesseract as a stat-cell fallback for ANY engine's rare
   genuine miss; a cell production/padded can't read now stays null
   unless `--stat-tess-fallback` is passed. The alternative -- keeping
   the CLI default on for production/padded and only defaulting dp to
   off -- would have required exactly the per-engine special-casing this
   decision explicitly avoided (daily_gunsmoke.py has no concept of
   "which engine is this" to condition on; main.py's own
   _get_stat_ocr_engine() is the one place that knows, and it doesn't
   see individual cell reads). A single global default, explicit and
   documented, was judged cleaner than an implicit per-engine one a
   future reader would have to reverse-engineer.

   ALSO FIXED: StatOcrDp.load() gained an accepted-but-ignored
   `tmpl_variant` parameter (main.py's _get_stat_ocr_engine() calls
   `_Engine.load(tmpl_variant)` uniformly across all three engines;
   StatOcrDp previously took no parameter at all, which would have
   raised TypeError the moment "dp" was added to STAT_OCR_ENGINES).

   VALIDATION: real-fixture end-to-end run both ways --

   SCOPE CHANGE THIS CAUSES: gfl2/stat_ocr_dp.py moves from pure EXPLORE

   NOT DONE: --stat-ocr-engine dp is still not a real alternative to

79. Rewrite gfl2.stat_ocr._find_percent_x_start's Case B from a fixed-
    pixel-offset heuristic to a scale-invariant right-to-left scan
    (docs/known_issues.txt §18's 2026-07-11 UPDATE)

   CONTEXT: investigating why gm_d_20250908.png drags corpus-wide cell
   accuracy down (open since long before this session, §18) finally
   checked the one thing every prior pass had skipped -- the image's own
   file dimensions. It is 2047x652; every other two-panel image in the
   corpus is ~2280x690-700 (checked all 23 siblings) -- a genuinely
   different, ~10% smaller capture resolution, not a corrupted/mid-
   animation capture (§23's carried-forward leading hypothesis, which
   turned out to be the wrong lead here).

   Tracing one failing cell exactly (gm_d_20250908_p1_r0_col1, '39.65'
   read as '39.6') found the real last digit's blob ('5') being
   incorrectly classified as part of the '%' sign and dropped.
   _find_percent_x_start's Case B (split '%' rendering: top circle +
   diagonal slash + bottom circle) computed the digit/percent boundary as
   bottom_circle.x MINUS A FIXED 25px (or rightmost.x minus a fixed 10px
   for the merged-% case) -- a magic-number margin sized for this
   corpus's typical (larger) resolution's '%'-cluster width and
   inter-glyph spacing. At this image's smaller scale, that same fixed
   backup overshoots past the true boundary and swallows the genuine
   trailing digit.

   VALIDATED THE REPLACEMENT BEFORE TRUSTING IT: hypothesized that '%'s
   three sub-parts, though genuinely separate blobs/contours, have
   OVERLAPPING bounding boxes (the diagonal slash's box spans wide enough
   in x to overlap both small circles' boxes, even though the actual ink
   never touches -- two regions whose ink DOES touch would already be one
   contour, not two blobs with a "negative gap"). Swept every real Case-B
   '%' split across the full 87-image corpus (1466 cells): a plain rule

   against the ENTIRE corpus's existing behavior, not just the one
   failing cell that motivated it.

   FIX: Case B now scans right-to-left from the rightmost blob, merging
   into the '%' group while the gap to the next blob leftward is
   negative, stopping at the first non-negative gap -- the boundary is
   the SIGN of a relative gap, not any absolute pixel distance, so it
   does not need per-resolution recalibration the way the old magic

80. Resolution- and ink-color-group-adaptive binarization threshold for
    gfl2/stat_ocr_dp.py, via a hand-implemented 3-class (multi-level)
    Otsu, for the EXPLORE-scope engine only

   CONTEXT: decision #79 fixed one of decisions.txt #18's two component
   bugs; the other (THRESH_BIN=180 bridging adjacent black-ink digit
   blobs into one merged blob at gm_d_20250908.png's ~10%-smaller capture
   resolution, for 8 col3 cells) was left open pending a real
   resolution-adaptive design. A proposed lookup table keyed by
   resolution, populated via Otsu-style adaptive
   thresholding sampled from an early representative cell, with separate
   entries for column 1's orange ink vs. columns 2-4's black/gray ink
   (both confirmed real, corpus-wide traits by decision #79).

   FIRST ATTEMPT, MISDIAGNOSED AS A REGRESSION: standard binary (2-class)
   cv2.THRESH_OTSU, sampled per (pct-strip height, ink-color group) and
   cached, DID fix gm_d_20250908 (8->1 mismatches) but appeared to
   introduce 31 NEW mismatches elsewhere, all a systematic '1'->'7'
   misread (e.g. '27.17'->'27.77'). Investigating why revealed classify()
   has two gates -- TOP_BAND_7_GATE/TOP_BAND_25_GATE -- that measure an
   ABSOLUTE ink-pixel count over a FIXED few rows of the tight crop
   (unlike TOP_BAND_4, which already measures a PROPORTION of the glyph's
   own height). Since this engine has no normalization at all (decision
   #77), a glyph's crop origin IS wherever binarization draws its ink
   boundary -- changing the threshold shifts what "row 0" physically is
   on the glyph, invalidating any absolute-row gate regardless of whether
   the new threshold is itself "more correct." This same pattern
   reproduced identically across THREE different threshold-derivation
   methods (plain 2-class Otsu, 3-class multi-Otsu's darker boundary,
   3-class multi-Otsu's brighter boundary) -- strong evidence the problem
   was never about picking a better threshold VALUE.

   A first attempt at making TOP_BAND_7/TOP_BAND_25 proportional (a grid
   sweep over (p0,p1) mirroring TOP_BAND_4's own calibration) did NOT
   reproduce a clean margin for the {1,7} pair on a first attempt (best
   found: gap=-1.0, i.e. real overlap) and was not pursued further this
   session -- proportional bands are not a free substitute for the
   {1,7}/{2,5} gates the way they were for '4'.

   CORRECTED DIAGNOSIS: re-running the SAME "31 regressions" comparison
   with stat_gt_overrides.json properly applied (the real verify()
   function layers overrides on top of the raw Tesseract GT cache; the
   ad-hoc validation script used during this investigation did not)
   found nearly all 31 were comparisons against STALE ground truth, not
   real classifier failures -- e.g. fb_d_20251004_p2_r1_col1's raw
   tess_gt_cache label is '27.17', but stat_gt_overrides.json's corrected
   value is '27.77', exactly what the classifier produced. With overrides
   applied, the multi-Otsu approach (darker boundary, t1) is a NET
   IMPROVEMENT: 99.5% -> 99.59% (3145 -> 3148/3161), gm_d_20250908 fully
   resolved (8 -> 0 mismatches, glyph-level 100% across all previously-
   affected glyphs), with only 5 genuinely NEW mismatches -- all col4, all
   a '5'->'3' confusion. col4 was checked and confirmed to share col2/
   col3's black/gray ink color (mean BGR ~[110,104,91] across all three)
   -- this is NOT a color-group-detection miss, root cause not yet
   investigated (filed as a fresh action item rather than blocking on it).

   See docs/takeaways.txt for the general lesson this mis-diagnosis
   produced: an ad-hoc validation script that doesn't mirror the real
   harness's ground-truth handling can manufacture a false "regression"
   signal indistinguishable from a real one until checked.

   WHY MULTI-LEVEL (3-CLASS) OTSU, NOT STANDARD (2-CLASS): standard
   binary Otsu forces the strip's histogram into exactly 2 classes
   (background vs. everything darker), which necessarily collapses
   anti-aliasing halo together with solid ink -- landing at the valley
   between background and that combined dark region, which is more
   halo-inclusive (i.e. numerically LOWER, a stricter cutoff on darkness)
   than THRESH_BIN=180's hand-tuned value. A 3-class split (background /
   halo / solid ink) via the classic Otsu multi-threshold generalization
   (Liao, Chen & Chung, 2001 -- the same algorithm scikit-image's
   threshold_multiotsu implements) lets the darker (t1, ink/halo) and
   brighter (t2, halo/background) boundaries be evaluated separately.
   Measured directly: t2 is far too inclusive (92.6% corpus accuracy);
   t1 is the one that works. cv2 has no built-in multi-level Otsu (only
   THRESH_OTSU/THRESH_TRIANGLE, both binary) and this project has no
   scikit-image dependency -- hand-implemented via the same
   cumulative-histogram-moment trick the "fast" part of the 2001 paper
   uses (O(256^2) candidate (t1,t2) pairs instead of the naive O(256^3)),
   rather than adding a dependency for one function.

   ONE GROUP IS NOT ENOUGH, TWO IS: confirmed directly (not assumed) that
   column 1 (Damage Dealt) is the ONLY pct column with distinct ink color
   -- col2/col3/col4 all measured the same black/gray BGR across three
   unrelated images. A cache keyed by (pct-strip height, ink-color group)
   with a simple mean-ink-color heuristic ("rest" if too little ink to
   measure, else "col1" if red channel exceeds blue by a real margin) is
   sufficient; no per-column table is needed.

   SCOPE: gfl2/stat_ocr_dp.py (EXPLORE) ONLY. gfl2/stat_ocr.py's/
   gfl2/stat_ocr_padded.py's shared THRESH_BIN=180 is UNCHANGED -- both
   remain MAIN-scope production engines with no per-resolution
   adaptivity, and known_issues.txt §18's 8 xfail-marked cells in
   tests/test_stat_ocr_hard_cases.py/tests/test_stat_ocr_padded.py are
   still correctly failing (those test the production engines, not
   stat_ocr_dp). Porting this design to production, if ever done, is a
   separate MAIN-scope decision with its own risk profile (touching the
   THRESH_BIN every other engine also depends on).

   IMPLEMENTATION: _multi_otsu_2thresh() (cumulative-moment 3-class
   sweep), _detect_ink_group() (mean-ink-color heuristic),
   _adaptive_pct_threshold()/_binarize_pct_adaptive() (cache-backed
   lookup + binarize) added to gfl2/stat_ocr_dp.py. StatOcrDp gained
   self._thresh_cache, populated lazily across a run (one engine
   instance = one shared cache); _extract_pct_digit_glyphs() gained an
   optional thresh_cache parameter (defaults to a fresh dict if omitted,
   for backward-compatible single-cell callers); verify_glyphs() and
   gfl2/calibration/calibrate_dp.py's collect_corpus_glyphs() both thread
   one shared cache across their whole corpus loop, matching how
   StatOcrDp's own instance-level cache behaves in production use.
   Full suite unaffected (1279 passed / 14 skipped / 18 xfailed --
   unchanged, since this change is scoped to gfl2/stat_ocr_dp.py, which
   has no xfail-marked test entries of its own).


81. Replace gfl2/stat_ocr_dp.py's {2,3,5} leaf's paren_close cross-
    correlation gate with spread_x + a bottom-anchored ink count --
    removes the last non-circular use of template correlation in this
    engine, and also fixes decision #80's col4 '5'->'3' regression

   CONTEXT: direct feedback that the paren_close cross-correlation
   template (a hand-drawn ')' ellipse, normalized cross-correlated
   against the glyph) was a "smelly" mechanism for the {2,3,5} leaf --
   every other leaf in this tree is a plain spatial primitive (contour
   ratio, ink count, reflex-vertex spread); paren/loop template matching
   is otherwise used only for the circular {0,6,9} centroid lookup, where
   it is genuinely load-bearing (that leaf needs a 4-dimensional
   nearest-of-3 comparison, not a single scalar gate).

   Checked directly (not assumed) whether spread_x -- the SAME reflex/
   concave contour points already computed for spread_y, just its x-axis
   extent instead of y-axis -- could substitute. It does NOT cleanly
   isolate '3' the way it was first proposed (only ~11% of real '3'
   glyphs read spread_x==0; the rest overlap '2's own [3,4] range, and a
   looser threshold to catch the rest would swallow '2' too, confirmed by
   direct corpus measurement). But it DOES cleanly separate '5' from
   {2,3}: '5' min=5.0, {2,3} max=4.0, a real 1-unit corpus-wide gap ('5'
   is measurably wider between its reflex points than either '2' or '3').

   DESIGN: spread_x gates '5' vs {2,3} first. A top-band ink count (same
   mechanism as TOP_BAND_4/TOP_BAND_7) CONFIRMS the spread_x '5' candidate
   ('5' has a strong top bar like '7'; {2,3} don't) rather than trusting
   spread_x alone -- if the two disagree, classify() returns '?' instead
   of guessing, directly addressing action_items.txt #28's confidence-
   abstention concern (this is the first leaf in the tree with an actual
   reachable abstention path, not just the dead defensive
   circular_holes0_unexpected branch). Never observed firing on the real
   corpus (recall=1.0000 at this confirmation gate too), but costs
   nothing extra since spread_x's reflex_pts were already computed for
   the {1,7}-vs-{2,3,5} split above it. The remaining {2,3} split uses a
   BOTTOM-anchored ink count -- '2' always ends in a full-width flat
   bottom stroke (high ink count in its own last row(s)); '3' curls
   inward (lower count) -- the same shape gfl2.stat_ocr's own
   _bottom_row_width_frac discriminator targets for a different digit
   pair (known_issues.txt §15), expressed here as a plain count rather
   than a width fraction: '3' max=9, '2' min=11, a real 2-unit gap.

   IMPLEMENTATION: _spread_x() (mirrors _spread_y(), same reflex_pts
   input) and _bottom_band_count() (mirrors _band_count()'s top-anchored
   convention, anchored to the glyph's own last row instead) added to
   gfl2/stat_ocr_dp.py. paren_close/PAREN_CLOSE_3_GATE/TOP_BAND_25_HEIGHT/
   TOP_BAND_25_GATE removed from classify() and from _CALIB_DEFAULT
   entirely (not kept-but-unused -- this design was superseded within the
   same session it was calibrated, before it had the kind of shipped
   history this project's "kept, not deleted" precedent is meant to
   protect). _paren_features() itself is UNCHANGED and still imported --
   still load-bearing for the circular {0,6,9} centroid lookup.
   gfl2/calibration/calibrate_dp.py's calibrate_paren_close_3/
   calibrate_top_band_25 replaced with calibrate_spread_x_5/
   calibrate_top_band_5/calibrate_bottom_band_23, same _gap_bounds/
   smallest-clearing-height-preference methodology as every other gate in
   that script. debugs/debug_stat_ocr_dp_5_vs_7_robustness.py (imports
   these constants directly for its own perturbation-sweep mirror of
   classify()) updated to match -- its own robustness FINDINGS are
   against the now-superseded Sobel/paren-based leaves and have not been

   A FULL RECALIBRATION (not just the three new constants) was run after
   wiring this in, because decision #80's resolution-adaptive threshold

   other gate's derived value shifted somewhat from its pre-threshold-

   RESULT (single/*.png, 87 images, fresh --build not needed -- this
   engine trains nothing, only calibrates):
      metric              before (paren_close)   after (spread_x)
      glyph accuracy       10433/10433 (100.0%)    10433/10433 (100.0%)

83. Fix stat_ocr_dp's remaining 8 hard-case mismatches: 7 were Tesseract
    GT phantom-digit mislabels, 1 was a noise-speck / cache-order bug in
    _find_percent_x_start (docs/known_issues.txt §32)

   DECISION: correct the 7 ground-truth entries via stat_gt_overrides.json
   (no code change -- dp's own answers were already right); fix the 8th
   by adding a corpus-measured minimum-blob-area floor
   (PCT_ANCHOR_MIN_AREA=9) to gfl2.stat_ocr._find_percent_x_start, applied
   BEFORE it picks its rightmost-blob anchor -- rather than (a) fixing the
   threshold-cache sharing/order-dependence itself, or (b) a gap-based
   isolation check on the rightmost blob.

   RATIONALE:

   Investigating known_issues.txt §31's "8 pre-existing, unrelated hard
   cases" tail with direct pixel/blob inspection (rather than trusting the
   aggregate --verify number, which is all any prior pass had checked)
   found it was two unrelated problems, not one -- see §32 for the full
   symptom/root-cause write-up. This entry covers why each was fixed the
   way it was.

   FINDING A (7 cells): visually confirmed against the actual rendered
   image that dp's shorter answer was correct in every case and
   Tesseract's cached GT had hallucinated an extra '1' digit with no
   corresponding ink. No design decision needed beyond "trust the pixels
   over the cache" -- corrected via the existing stat_gt_overrides.json
   mechanism, the same path every prior GT correction in this project has
   used.

   FINDING B (1 cell): three designs were considered for the noise-speck
   problem once traced to its root cause (a stray sub-pixel-scale
   artifact hijacking _find_percent_x_start's rightmost-blob anchor):

   1. Fix the threshold cache itself (e.g. re-validate per cell instead of
      trusting the first-seen value for a given (height, group) key, or
      stop sharing the cache across images). REJECTED as the primary fix:
      a much larger, riskier change to a mechanism every other cell's
      correctness already depends on (the cache exists specifically
      because per-cell multi-Otsu computation is not free -- see gfl2/
      stat_ocr_dp.py's own _adaptive_pct_threshold docstring), and it
      would not address the deeper issue that _find_percent_x_start's
      rightmost-blob anchor has no defense against noise regardless of
      why a spurious blob appears (a cache fix only patches the ONE way a
      speck happened to appear here; a differently-thresholded pipeline,
      or a different corpus, could still produce a stray blob some other
      way entirely).

   2. A gap-based isolation check (if the rightmost blob is separated from
      its neighbor by an anomalously large gap relative to the corpus's
      normal inter-glyph spacing, treat it as noise and retry with the
      next-rightmost blob). Considered but NOT pursued: requires picking a
      second threshold (how large a gap is "anomalous"), and the existing
      Case B scan (decision #79) already has its own gap-based logic for
      a DIFFERENT purpose (merging '%' sub-blobs) -- stacking a second,
      differently-motivated gap heuristic on top risks the same kind of
      resolution-specific miscalibration decision #79 had to rewrite away
      from.

   3. CHOSEN: a plain minimum-blob-AREA floor, applied once, before any
      anchor selection happens at all -- directly matching a design
      suggestion to add "a speck removal pipeline before deciding the
      rightmost blob." Simpler than either alternative: one number,
      derived directly from measured corpus data (not guessed), doesn't
      touch the cache or the existing Case A/B logic, and generalizes to
      ANY mechanism that could produce a stray speck (not just this one
      cache-order path) -- any future source of spurious tiny blobs is
      caught by the same filter.

   MEASUREMENT (not guessed): scanned every pct-strip blob across
   single/*.png (22,864 blobs total) using FRESH per-cell thresholds
   (deliberately not the shared cache, so the measurement isn't
   contaminated by the very bug being fixed) -- the smallest blob found
   anywhere in the real corpus is a 3x3=9-area '.' dot; nothing genuine is
   ever smaller. The pathological speck that triggered this investigation
   was 2x2=4 area -- a clean, real gap (4 vs 9), not a boundary call.
   PCT_ANCHOR_MIN_AREA=9 sits exactly at that measured floor (blobs with
   area < 9 are dropped).

   WHY THIS DOESN'T NEED TO TOUCH THE CALLER: _find_percent_x_start only
   returns an x-boundary (pct_x); the caller (_extract_pct_glyphs /
   _extract_pct_digit_glyphs) still iterates over the FULL, unfiltered
   blob list afterward and marks anything at x >= pct_x as 'skip'. Once
   pct_x is computed correctly (immune to the speck), the speck itself --
   still present in the full list -- is skipped anyway, since its own x
   is >= the correct boundary. No downstream code needed to change.

   APPLIED: gfl2/stat_ocr.py directly; ported by hand to gfl2/
   stat_ocr_padded.py's own full duplicate of the function (decision 47's
   policy -- confirmed, as always, that this doesn't propagate
   automatically). gfl2/stat_ocr_fft.py and gfl2/stat_ocr_dp.py both
   import the shared function and received the fix with no changes of
   their own.

   RESULT (single/*.png, pct-line accuracy, all four engines):
      gfl2/stat_ocr_dp.py       99.7% -> 100.0%  (3153->3161/3161)
      gfl2/stat_ocr.py          99.6% (3149/3161, unchanged)
      gfl2/stat_ocr_padded.py   99.6% (3148/3161, unchanged)
      gfl2/stat_ocr_fft.py      99.6% (3147/3161, unchanged)
   The three engines besides dp were never exposed to this exact speck-
   order pathology (they don't share dp's adaptive per-cell threshold
   cache), so their numbers hold steady -- the fix is a pure addition
   with no observed downside for any engine. Full suite: 1279 passed / 14
   skipped / 18 xfailed (unchanged).

85. Multi-Otsu score threshold: ATTEMPTED as a direct swap-in for
    score_ocr.THRESH_VAL in the shared score pipeline, THEN REVERTED --
    net regression (docs/known_issues.txt §33)

   DECISION: do NOT replace score_ocr.THRESH_VAL with a per-crop
   multi-Otsu threshold inside gfl2.patterns.daily_gunsmoke's shared
   _header_isolate_blobs()/_read_bright_number() (used by every
   --stat-ocr-engine selection). Reverted the attempt cleanly (`git
   checkout`) rather than shipping it behind a flag -- unlike this
   project's usual "kept, disabled by default" convention for a validated-
   but-costly tradeoff (e.g. decision #60's vstroke-gate), this is a
   stronger, unconditional accuracy loss with no redeeming tradeoff to gate
   behind a flag for. See decision #86 for what was built instead.

   RATIONALE:

   known_issues.txt §33 root-caused a real, confirmed production bug: the
   shared score pipeline's THRESH_VAL+delta escalation ladder can silently
   DROP an adjacent-digit merge (e.g. "44") with no '?' marker, because it
   stops at the first delta whose blob count increases at all -- which can
   reflect an unrelated partial separation, not the genuinely merged pair
   splitting. A per-crop multi-level (3-class) Otsu threshold (copied from
   gfl2.stat_ocr_dp._multi_otsu_2thresh) was validated to correctly
   isolate all digit blobs in 156/157 score crops in single/*.png,
   including every known "44"-drop case -- a strong, corpus-validated
   result for SEGMENTATION specifically.

   Direct feedback flagged an important caveat before this was trusted
   further: the one multi-Otsu segmentation failure (gm_d_20250908.png)
   is the corpus's OWN known different-capture-resolution outlier (§18) --
   meaning even the validated 156/157 result doesn't yet demonstrate real
   multi-resolution robustness, just that this one corpus's typical scale
   happens to work. This flagged the SAME broader concern §18/decision
   #79-#80 already established: an approach validated on a corpus's
   typical scale can still fail at a genuinely different one, and
   shouldn't be treated as "solved" just because it beat the previous
   heuristic on most of the corpus.

   ATTEMPT: wired the validated multi-Otsu threshold directly into
   _header_isolate_blobs() as the base threshold for BOTH blob-boundary
   detection AND the crop each blob is classified from (replacing
   THRESH_VAL entirely, ladder kept on top as a refinement). Validated via
   a real before/after A/B run: gfl2.patterns.daily_gunsmoke.parse()
   invoked across the full single/*.png corpus (161 score crops) with the
   padded stat-cell engine injected (chosen as a realistic full end-to-end
   run, not just a blob-classifier-level check), before and after the
   change, diffed against Tesseract ground truth for every changed cell.

   RESULT: 88 of 161 score reads changed.
      FIXED     (was wrong, now matches GT):        7
      REGRESSED (was correct, now wrong):           68
      LATERAL   (wrong both ways, different wrong): 12
      GT unreadable:                                 1
   Net: -61 correct reads -- a decisive regression, not a mixed result.
   Confirmed via direct per-digit confidence inspection: a cleanly-
   separated '0' blob (from a correctly-split "44+0+7" crop) scored only
   0.2493 projection-correlation confidence against assets/fonts/
   score_digits.py's trained templates (vs. 0.86+ for digits that still
   matched well) -- ROOT CAUSE: those templates were trained on glyphs
   extracted at THRESH_VAL=150 specifically. THRESH_VAL=150 and the
   templates are a matched, MUTUALLY CONSISTENT pair -- not because 150 is
   objectively correct, but because the templates learned to expect
   glyphs binarized at exactly that level. Swapping only the segmentation
   side to a per-crop-optimal (but different) threshold breaks that match
   for most digits, not just the merged ones this change targeted --
   confirmed no OTHER field (dmg_dealt_total, dmg_taken_total,
   combat_turns, dolls) changed in the same run, isolating the damage
   entirely to score classification. This is a real "double negative"
   situation (docs/takeaways.txt #78): the fixed threshold's own
   arbitrariness was silently compensated by templates trained against
   that exact same arbitrariness, and disturbing only one side of the
   pair surfaces both as a regression.

   Notably, even the ORIGINAL target case (fb_d_20251019.png panel 2,
   real score "4407") did NOT come out fixed by this attempt -- it moved
   from "07" (before) to "4467" (after), still wrong against GT: cleanly
   separating the blobs was necessary but not sufficient, since
   classification against the mismatched templates then misread the
   correctly-isolated '0' as '6'.

   ACTION: reverted `gfl2/patterns/daily_gunsmoke.py` to its pre-attempt
   state via `git checkout` -- the shared pipeline used by production/
   padded/fft is untouched, confirmed byte-identical via a repeat of the
   same before/after A/B script (161/161 identical). See decision #86 for
   the design that replaced this attempt.

87. gfl2/score_ocr_dp.py's classification gap (decision #86): a real

   engine's own already-established properties: no normalization of any
   kind (every glyph classified at its native tight-crop size), and no
   internal Tesseract fallback tier -- every leaf either decides or
   abstains to '?' directly, matching the user's explicit direction for
   this work ("no tesseract fallback; let it return '?' on uncertainty,

   ratio, paren/loop templates, reflex-vertex spread, band-ink-count

   stat_ocr_dp.py -- continuing that module's own "peer dp-family modules

   --stat-ocr-engine dp`; gfl2/patterns/daily_gunsmoke.py, the MAIN module

   (gfl2/configs/daily_score_dp_calib.json vs. daily_pct_dp_calib.json) --
   since the score font renders at a different absolute scale and (as the
   {2,3,5} finding below shows) can need a differently-shaped tree even

   CORPUS, NOT ATLAS: assets/fonts/glyph_daily_score.png (docs/decisions.txt
   #84) is a real, curated one-sample-per-digit atlas, and was the
   resource named when this work was requested -- but known_issues.txt
   §27/decisions.txt #70 already measured, for the pct-line engine's own
   hierarchical classifier, that an INTERVAL-style gate derived from a
   single atlas sample can look perfectly clean in isolation while still
   misrouting real corpus glyphs whose within-class spread that one
   sample cannot represent (centroid-style constants, like the {0,6,9}
   leaf's reference vectors, are the exception -- a single representative
   point is a legitimate centroid). Every gate this tree needs (iso_gate,

   centroid, so gfl2/calibration/calibrate_score_dp.py collects real,

   correctly paired -- no confidence-abstention fallback was needed for

   backlog (CLAUDE.md: "not a permanent record... trim... or delete
   it"), unlike the four permanent docs above. A citation to a closed
   item is a dangling pointer from the moment it closes -- concretely,
   gfl2/stat_ocr_fft.py named "action_items.txt #18" for a real finding
   even though action item #18 had already been deleted outright
   (folded into the "#16-18 removed" tombstone). Roughly 100 such stale

   numbering conventions already stating the underlying rule, and
   despite a prior, narrower cleanup (docs/takeaways.txt #72) -- that
   prior pass only verified DELETIONS from action_items.txt were safe
   (checking incoming references before removing an entry, fixed by an
   unconditional tombstone policy); it never addressed items that closed
   via the ordinary DONE/STATUS lifecycle without ever being deleted,
   which is the far more common case and was never swept before now.
   See docs/takeaways.txt #80 for the generalized lesson.
