                  GFL2 Parser — Design Decisions


1.  Column detection strategy

   DECISION: Use fixed proportional column positions (width ratios) rather
   than dynamic edge-detection.

   RATIONALE: The GFL2 game UI is a fixed-layout interface. Canny-edge
   projection-based column detection proved unreliable on this UI because
   doll portraits and buff icons create noise that confuses the detector.
   The proportional approach is simpler, faster, and handles width
   variations correctly.

   CALIBRATION: Ratios were derived from a 1485px-wide reference screenshot
   by scanning horizontal brightness transitions. The buff column (0.350,
   0.421) was discovered to be ~90px LEFT of the initial estimate; the
   initial crop landed in the gap between the owner name and the buff icon.


2.  Row detection strategy

   DECISION: Scan horizontal brightness profiles to find dark separator bands.

   RATIONALE: The game UI uses dark bands between rows and between date
   sections. Mean row brightness < 70 reliably identifies these bands.
   Thick bands (>= 40px) carry date labels; thin bands (~9px) are plain
   row dividers.


3.  Date OCR

   DECISION: Use two tesseract PSM modes (11 then 6) in sequence; return
   first match for pattern \d{1,2}/\d{2}.

   RATIONALE: PSM 11 (sparse text) correctly reads the thin top date band
   (40px) which PSM 6 misreads. PSM 6 correctly reads the taller date
   separator bands (64px) which PSM 11 sometimes misses. Running both in
   sequence covers all cases.

   PREPROCESSING: Brightness threshold (>100) to isolate light date text
   on dark background, then 6x NEAREST upscale + 1-iteration dilation.


4.  Asset matching pipeline

   DECISION: Three-pass matching: pHash (strict) → HSV histogram → unknown.

   RATIONALE:
   - pHash (threshold=6): catches same-session re-runs at near-zero cost.
     Threshold deliberately strict (6 vs initial 10/20) because borderline
     matches (dist=8-10) were causing false positives between visually
     similar characters.
   - HSV histogram (threshold=0.92): robust across screenshots because
     character color distributions are distinctive even when the Lv. badge
     color changes (Lv.60 vs Lv.90) or icons are present. Achieves 95%+
     accuracy cross-screenshot.
   - pHash + template matching were tested first but both failed at cross-
     screenshot matching due to the Lv. badge color change and the
     Sharkry reference image coincidentally matching many characters.


5.  Histogram mask design

   DECISION: Mask out optional overlay icons during histogram computation
   while keeping the element icon.

   RATIONALE: Optional icons (buff arrows, borrowed indicator) alter the
   color histogram and cause false negatives. The element icon is retained
   because it genuinely distinguishes same-appearance dolls of different
   elements.

   MASK REGIONS (fractions of cell dimensions):
   - Exclude: left strip x=0-25%, y=20-58%  (optional buff arrows)
   - Exclude: top-right x=48-100%, y=0-26%  (borrowed indicator)
   - Exclude: bottom y=75-100%               (Lv. badge)
   - Keep:    left strip x=0-25%, y=0-20%   (element icon)
   - Keep:    rest of face                    (character appearance)


6.  Keep-cleanest reference upgrade

   DECISION: When a histogram match is found, replace the stored reference
   if the current frame has fewer optional icons (lower icon score).

   RATIONALE: References are initially cropped from whatever screenshot is
   processed first. Later screenshots may show the same doll without buff
   arrows or borrowed indicator. A cleaner reference improves future
   matching and makes the assets folder easier to inspect manually.

   ICON SCORE: Counts optional icon regions where mean HSV saturation > 90.
   The icon graphics are highly saturated; the face/background is not.


7.  Asset naming convention

   DECISION: Prefix asset filenames with '_' to mark known-mapped assets
   (e.g. '_QiongJiu.png'). Strip the prefix in CSV output.

   RATIONALE: The underscore makes it visually easy to distinguish labeled
   assets from unlabeled GUIDs in a file browser without needing a separate
   index file.


9.  OCR-based buff matching

   DECISION: Replace HSV histogram buff matching with OCR text recognition
   (buff_ocr.py).

   RATIONALE: Buff icons use dark backgrounds with monochromatic (single-
   color) artwork. HSV histograms on monochromatic images are nearly
   identical across different buffs — the color distribution carries no
   distinguishing information. Text labels within the buff icon area are
   always rendered clearly and are reliably machine-readable, making OCR
   the correct signal.


10. CHECKED_HASH .pyc invalidation

   DECISION: Use py_compile with invalidation_mode=CHECKED_HASH when
   pre-compiling gfl2 modules (compile_gfl2.py).

   RATIONALE: Python's default mtime-based .pyc invalidation fails silently
   when source files are written from a different platform (e.g., Linux
   sandbox writing to a Windows NTFS mount). The mtime visible to Python on
   Windows may not change, causing stale bytecode to be loaded even after
   the source was modified. CHECKED_HASH mode embeds a hash of the source
   content in the .pyc header and re-validates on every import, making
   cross-platform edits safe.


11. Batched score and buff-name OCR before any asset saves

   DECISION: In parse(), run all _ocr_score() and buff_ocr() calls for
   every row before any new buff PNG files are written to disk.

   RATIONALE: On Windows, writing a new asset file during parsing was
   observed to cause Tesseract to return empty strings for score OCR on
   subsequent rows (cross-row contamination). Batching all OCR work in a
   first pass and deferring all filesystem writes to a second pass
   completely decouples the two operations, eliminating the interaction.


12. MIN_WORD_LEN=4, MIN_THRESHOLDS=1 for buff OCR filtering

   DECISION: Accept a buff OCR result only if every extracted word has at
   least 4 characters and at least 1 threshold run produced the result.

   RATIONALE: Short fragments (1-3 characters) are overwhelmingly OCR noise
   (stray pixels read as letters, punctuation misread as letters). Genuine
   buff name words are always multi-character English words. MIN_THRESHOLDS=1
   is intentionally permissive to maximise recall on first-encounter buffs
   while still requiring the result to come from a real threshold pass.


13. Y-position word ordering in buff OCR

   DECISION: Sort extracted words by their Tesseract-reported Y-coordinate
   before joining into a final buff name.

   RATIONALE: Tesseract returns words in reading order within its detected
   text blocks, but multi-line buff icon labels can be returned out of
   top-to-bottom order depending on block detection. Sorting by Y ensures
   the assembled name matches the visual top-to-bottom layout of the label.


14. Daily Gunsmoke OCR approach

   DECISION: Use PSM 6 at 8× upscale as the primary mode for stat cells,
   with a PSM 4 retry for values whose digit count is <= 2, and trim the
   bottom 15% of every stat cell before OCR.

   RATIONALE — PSM 6 as primary:
   The stat table uses two text elements per cell (a percentage and a raw
   value) laid out as a mini two-line block. PSM 6 (assume a uniform block
   of text) correctly captures both lines in a single pass and is the
   natural mode for small structured regions at high upscale.

   RATIONALE — PSM 4 fallback for short values:
   When the raw value is a small number (1–2 digits, e.g. "64"), it sits
   at the right edge of the cell with very little surrounding whitespace.
   PSM 6's block assumption causes it to merge or drop such values. PSM 4
   (assume a single column of text) is more tolerant of narrow text and
   recovers these cases reliably.

   RATIONALE — 15% bottom trim:
   Each stat cell contains a horizontal progress bar occupying roughly the
   bottom 15% of its height. The bar's coloured pixels are read by Tesseract
   as digit-like glyphs (especially "1", "I", "l"), corrupting the numeric
   extraction. Trimming the bottom 15% before OCR removes the bar entirely
   without clipping any digit baseline.


15. Daily Gunsmoke portrait extraction via bounding-box detection

   DECISION: Replace fixed-ratio column cropping (x=0.000–0.083) for
   portrait extraction with contour-based bounding-box detection.

   RATIONALE: The fixed ratio was calibrated to the horizontal position of
   the portrait column but did not account for the vertical position of the
   portrait square within each row. Because rows vary in height across
   captures and the portrait frame does not always start at the top of the
   row, fixed-ratio crops produced inconsistent framing — sometimes clipping
   the portrait, sometimes including excessive background.

   The contour-based approach is self-localising:
     1. Search the left 15% of each row (generous enough to always contain
        the portrait regardless of minor positional drift).
     2. Binarize against the local background colour (most-common pixel)
        with a delta=30 tolerance.
     3. Find the largest roughly-square external contour.
     4. Crop to that contour's tight bounding box.
   This yields a consistent, tight crop regardless of row height or vertical
   offset, and requires no per-resolution recalibration.


8.  GUID deduplication

   DECISION: Use a looser pHash threshold (20) for dedup checks against
   existing GUIDs, separate from the match threshold (6).

   RATIONALE: When the same unknown doll appears in multiple rows or
   multiple screenshots, it should only be saved once. A looser threshold
   handles slight crop size differences (e.g. 128px vs 129px row height)
   that would otherwise generate duplicate GUIDs.


16. _split_panels guard: require ≈50/50 split

   DECISION: Tighten the panel-split guard from 0.2–0.8 to 0.4–0.6.

   RATIONALE: A legitimate 2-panel "Challenge Points" layout always
   produces two equal-width panels (split ≈50% of image width). A bright
   vertical UI element inside a single-panel image (e.g. the column
   separator at x≈33%) can fall inside the old 0.2–0.8 range and trigger
   a spurious split. The tighter range safely rejects these while still
   accepting any real 2-panel layout (which is always within 40–60%).


18. Blob pipeline for stat-cell OCR (stat_ocr.py)

   DECISION: Implement a contour + projection-correlation classifier
   (stat_ocr.py) as Pass 0 for Daily Gunsmoke stat cells, falling back
   to Tesseract only when the blob pipeline returns None.

   RATIONALE: Tesseract is ~250ms/cell on small (~30×50px) crops. With
   40 cells per image and two images typical per run, Tesseract-only stat
   OCR costs ~20s. The blob pipeline (contour detection → normalize →
   feature match) handles 35–40/40 cells in ~10ms total, a 25× speedup.

19. Projection-based doll name classifier (doll_name_ocr.py)

   DECISION: Implement a 1-D column-projection nearest-neighbour classifier
   for doll names as a fast path before Tesseract in daily_gunsmoke.py.
   Use a fixed high-brightness threshold (≥200) rather than Otsu/adaptive
   binarization to isolate the white name text.

   RATIONALE: Tesseract runs at ~176ms per name cell.  With 5 dolls per
   panel and 2 panels per image, that is ~1.76s in name OCR alone.
   The projection classifier runs in ~1ms.  Otsu binarization was attempted
   first but rejected: it captures the surrounding game-UI decoration (which
   is similar across all doll rows), producing near-identical feature vectors
   that cannot discriminate between names.  A fixed high threshold isolates
   only the bright white text pixels that differ per name.


20. Projection templates are self-bootstrapping via EMA update

   DECISION: After each batch of daily gunsmoke images, flush OCR-confirmed
   name crops to templates using an exponential moving average (alpha=0.3)
   rather than a full rebuild.

   RATIONALE: A full rebuild from scratch would require running Tesseract on
   every image every time.  The EMA approach allows the template library to
   grow incrementally: first run uses Tesseract for all dolls, subsequent
   runs use projection for already-seen dolls, with templates converging
   toward more accurate centroids over time.  Build from a folder of images
   (--build) is available for an explicit cold start.


21. Projection result passes through fuzzy correction

   DECISION: Apply _fuzzy_correct() to the projection classifier result as
   well as to the Tesseract slow-path result.

   RATIONALE: Templates may carry stale mislabelled names (e.g. "Sharkty"
   built from OCR data before the portrait was renamed).  Fuzzy correction
   provides a second chance to snap a near-correct projection result to the
   true name once the portrait file is correctly named, without requiring a
   full template rebuild.



24. Extract Daily Gunsmoke output utilities into gfl2/dg_output.py

   DECISION: Move JS model (DollRow, ReportEntry, save_js), portrait-save
   helpers (_crop_portrait, _save_doll_portrait), and name-OCR utilities
   (_get_doll_name_ocr, _known_doll_names, _fuzzy_correct, flush_name_templates)
   from daily_gunsmoke.py into a separate gfl2/dg_output.py module.

   RATIONALE: Separating I/O from parsing keeps daily_gunsmoke.py focused on
   image analysis.  The interface boundary is explicit: the parser produces
   DollRow / ReportEntry objects; dg_output handles all I/O.


25. Migrate daily_gunsmoke.py from flat timing to TimerStack

   DECISION: Replace the flat _T dict / _record() / print_timing_summary()
   pattern with gfl2.timing.TimerStack, matching the approach already used
   in daily_gunsmoke2.py.

   RATIONALE: The flat pattern required manual bookkeeping and could not
   represent nested calls (e.g. stat_cell/blob called inside extract_doll_rows).
   TimerStack uses context managers and builds a Span tree automatically,
   producing hierarchical output that makes hot spots obvious at a glance.
   Migrating dg1 also means both parsers now share the same timing API,
   so batch_summary() in main.py works uniformly for either parser.


27. stat_ocr: K-suffix detection via rightmost-'?' heuristic, not template classification

   DECISION: K and M are not classified by the projection/Hu pipeline at inference
   time. Instead, _reconstruct_val applies a post-classification heuristic: if
   the rightmost glyph is '?' and the value has ≥ 4 items (3+ digits + K), substitute
   'K'. Templates for K/M are still built (for future use) but the classifier
   deliberately uses PROJ_VERY_LOW=0.35 to return '?' for glyphs with very low
   projection confidence, letting the heuristic handle them.

   RATIONALE: K glyphs in ib_d images have projection scores ~0.27 against all
   digit templates — too low for reliable classification, and Hu moments misfire
   (gave '2'). The heuristic is safe because K always appears as the rightmost
   character in a K-suffixed value, and only fires when preceded by ≥ 3 digits.


28. stat_ocr: partial val results with '?' markers instead of None

   DECISION: _reconstruct_val returns strings containing '?' (e.g. '44?', '1??1K')
   when some glyphs cannot be classified, rather than returning None. The downstream
   _v() in dg_output.py treats any value containing '?' as null in JS output.

   RATIONALE: Returning None for the whole val when one glyph fails discards useful
   partial information and makes the verify output harder to read (you can't tell
   whether it was a near-miss or a total failure). '44?' makes it clear that 2 of 3
   digits were classified correctly. The '?' marker is propagated rather than
   silently dropped so callers can decide how to handle uncertainty.


29. stat_ocr: GT override file for Tesseract ground-truth errors

   DECISION: stat_gt_overrides.json (project root) maps {source_key: {pct, val}}
   and is auto-loaded by BOTH --build and --verify, in gfl2/stat_ocr.py and
   gfl2/stat_ocr_padded.py, and by build_templates() itself (so
   assets/builders/build.py, which calls build_templates() directly and
   bypasses both CLIs, is covered too).  Entries override Tesseract GT for
   specific cells where Tesseract is known to be wrong.

   RATIONALE: Tesseract ground truth for ib_d images contains occasional reading
   errors (e.g. '5143' read as '8143', '197' read as '191'). Without overrides
   these appear as pipeline mismatches even when the blob pipeline is correct.
   A separate file keeps corrections out of the source code and makes them
   auditable.

   UPDATE (2026-07-03): originally --verify-only, per docs/known_issues.txt
   §15.  A --verify-only override can correct the accuracy *report* but
   cannot stop --build (or assets/builders/build.py's independent
   stat-cell training pass) from baking the same bad Tesseract label into
   the template it's building.  That gap let a mislabeled '2'→'3' glyph
   contaminate assets/fonts/stat_val.py across every rebuild until this
   session, invisible because the eval ground truth was generated by the
   same contaminated pipeline (see decision 46 below).  Moving the
   override application into build_templates() — the one function every
   build path shares — closes the gap for any future caller, not just the
   two known today.


30. stat_ocr: inner-blob count as a structural discriminator for digit confusion

   DECISION: Count enclosed holes (RETR_CCOMP hierarchy) in each normalised
   glyph as a pre-filter and reverse-check inside _classify.  Modal hole count
   is stored per template character in templates.json as "inner_blobs".

   Pre-filter: if query has >0 holes, restrict candidates to templates whose
   modal hole count matches.  Reverse check: if projection selects a template
   with ≥2 holes (i.e. '8') but the query has 0 holes, redirect to the best
   zero-hole candidate instead.

   RATIONALE: Projection and Hu features for '5' and '8' are too similar at
   8×13 px (NORM_W_VAL × NORM_H_VAL) to distinguish reliably.  Hole count is
   a categorical discriminator: '8' always has 2 holes; '5' always has 0.
   Adding more training images (the alternative) would not help if the shape
   features are inherently ambiguous at this resolution.


31. stat_ocr: VAL_STRIP_Y raised to 0.50 to prevent pct-line bleed

   DECISION: Changed VAL_STRIP_Y from (0.44, 0.82) to (0.50, 0.82).

   RATIONALE: The pct and val strips were overlapping by ~4 rows.  Bottom
   fragments of pct-line digits (rows 36–40 of the 84 px cell) appeared in
   the val strip as y=0 noise blobs.  _filter_y_outliers could not clean them
   because they outnumbered the real val blobs, dragging the median to y≈0
   and incorrectly evicting the real glyphs.  Raising the val-strip start to
   0.50 clears all pct-line content with ≥4 rows of margin while keeping the
   real val glyphs (absolute y≈0.58–0.74) well within the strip.


32. stat_ocr: _filter_y_outliers applied per-strip in _read_line and build

   DECISION: Apply _filter_y_outliers to blob lists in _read_line (inference)
   and in build_templates (training) immediately after _find_blobs.

   RATIONALE: The strip-based read() path introduced in the previous session
   omitted the _filter_y_outliers call that _split_lines used to perform.
   Residual noise blobs (y-outliers from strip boundary bleed or adjacent UI)
   can corrupt glyph extraction.  The filter is a cheap defence that was
   always intended for this purpose.


33. Header stats-row crops use dedicated binarization threshold and min-height filter

   DECISION: In daily_gunsmoke._read_stat_crop and build_header_templates._collect_samples,
   use HDR_THRESH=155 (not stat_ocr's THRESH_BIN=180) and HDR_BLOB_MIN_H=12 (not
   DOT_MAX_DIM=8) when binarizing and filtering blobs from header stats crops.

   RATIONALE:
   - THRESH_BIN=180 causes adjacent digits to merge: at that threshold '4'+'8' in the
     header font produce one 24 px blob instead of two 11 px blobs, making them
     unclassifiable. Threshold 155 cleanly separates all digit pairs observed.
   - DOT_MAX_DIM=8 is designed to catch decimal-point blobs (w≤8 AND h≤8). Comma
     thousand-separator blobs (from "48,500") have h≈5–7 (below 8) and w≈6 but their
     h can reach 10, slipping through as "digit" blobs and corrupting alignment.
     A minimum height of 12 filters all comma/noise blobs (h<10) while keeping all
     real digit glyphs (h≈16–17).
   - Both constants must match between build_header_templates.py and
     _read_stat_crop; a mismatch causes templates built at one threshold to be
     matched against blobs extracted at a different threshold, producing systematic
     misclassification.

34. _find_percent_x_start: aspect-ratio guard for merged-% detection

   DECISION: In Case A (merged '%' blob detection), accept blobs that satisfy
   either the classic width threshold (w ≥ PCT_MERGED_W=18) OR are nearly square
   (w ≥ h * 0.90), provided h ≥ LARGE_H_MIN.

   RATIONALE: The merged '%' glyph is roughly square (w/h ≈ 1.0) while pct-line
   digit blobs are taller than wide (w/h ≈ 0.7). At some screenshots/resolutions
   the fused '%' renders at w=17 (just below PCT_MERGED_W=18), causing Case A to
   fail and the '%' to be misidentified as a digit, producing a spurious trailing
   digit in the pct result. The aspect-ratio guard catches these near-square blobs
   without risk of false-positives on digit blobs.

35. _classify: clear-winner shortcut for robust but sub-threshold projections

   DECISION: After the PROJ_VERY_LOW guard and before the Hu tiebreaker, add a
   "clear-winner" shortcut: if the best combined score ≥ 0.55 AND the gap to the
   second-best ≥ 0.10, return the best candidate (with the same reverse inner-blob
   check as the main confidence path).

   RATIONALE: val '0' crops consistently score combined ≈ 0.58–0.67 — just below
   PROJ_CORR_MIN=0.70 — but win decisively over all other candidates. The Hu
   tiebreaker is useless for these crops (all Hu distances >> HU_HALF_DIST_MAX).
   The gap guard (≥ 0.10) prevents near-tie cases from misfiring while still
   catching val '0' cases whose gap ranged from 0.101 to 0.248 in the test set.

36. _read_line: tighter _filter_y_outliers threshold for val strips

   DECISION: Pass threshold=8 to _filter_y_outliers for val strips, vs 12 for pct.

   RATIONALE: Val digits sit on a single tight baseline (observed cy spread < 5 px).
   Pct-line fragments that bleed into the top of the val strip have cy ≈ 5 while
   legitimate val blobs have cy ≈ 14 (gap = 9 px). The existing threshold=12 kept
   these fragments; threshold=8 removes them without touching any legitimate glyph.
   Pct strips are more dispersed (bottom-circle of '%' sits lower), so they retain
   the looser threshold=12.

38. Auto-configure Tesseract path in gfl2/__init__.py

   DECISION: When `tesseract` is not found on PATH and the Windows default
   install path exists, set `pytesseract.pytesseract.tesseract_cmd` at
   package import time in gfl2/__init__.py.

   RATIONALE: The same pattern existed in stat_ocr.py but only for the
   --build/--verify code path. layout.py, buff_ocr.py, weekly_gunsmoke.py,
   and daily_gunsmoke.py all import pytesseract at module level and would
   raise TesseractNotFoundError if the executable was not in PATH (common
   on Windows where the Tesseract installer does not add itself to PATH by
   default). Centralising the configuration in __init__.py means it runs
   once before any submodule imports pytesseract, so no individual module
   needs to handle it.


39. Weekly doll crops normalised to 128×128 before asset matching

   DECISION: In weekly_gunsmoke._parse_row, pass each doll column crop through
   normalize_portrait() (dg_output.py) before calling AssetMapper.translate().
   normalize_portrait extracts a fw×fw square centred at y0=(h−fw)//2 and
   resizes to PORTRAIT_NORM (128×128) using LANCZOS4.

   RATIONALE: The weekly column crop has width fw (portrait width) but height
   equal to the full row height. Without normalisation, a 90×128 weekly crop is
   compared against a 128×128 daily portrait asset, producing HSV histogram
   scores of ~0.49 (threshold=0.88) — no match possible.  After normalisation,
   cross-image matching between screenshots at different resolutions (90×128 vs
   75×106) reaches 0.96+ histogram correlation.

   The fw×fw square crop is geometry-derived: the portrait fills the detected
   column width exactly (confirmed by hair-blob width-fraction measurement, which
   is identical — 0.578 — in both daily and weekly crops).  Background subtraction
   was rejected because the row background and portrait background share similar
   brightness, making the most-common-pixel estimate unreliable.

   conftest._seed_doll_assets also applies normalize_portrait when writing test
   seeds so seeds use the same 128×128 format as production queries.


37. _reconstruct_pct: strip leading/trailing dot noise

   DECISION: Apply result.strip('.') after assembling the pct string.

   RATIONALE: Tiny noise blobs at the left edge of the pct strip (e.g. x=8, w=3,
   h=2) pass blob-size and y-outlier filters and are classified as '.' (both dims
   ≤ DOT_MAX_DIM). A valid pct value always starts and ends with a digit, so
   stripping edge dots removes this artefact without risk of corrupting real values
   (the decimal point in "30.49" is interior, not at position 0 or -1).

40. Panel image slices use _split_panels(), not frame-position midpoints

   DECISION: In parse(), use _split_panels() (brightness-based midpoint in the
   header bar top third) to determine where to slice the image into left/right
   sub-images.  Frame-based detection (_find_all_frames + _group_frames_into_panels)
   is used only to assign frame lists to panels, not to compute slice boundaries.

   RATIONALE: Portrait frames are anchored at the LEFT EDGE of each panel.  The
   midpoint between the rightmost frame of panel N and the leftmost frame of panel
   N+1 therefore falls somewhere inside panel N's content, not at the visual boundary.
   _split_panels() finds the actual boundary by locating the brightest column in the
   centre of the header bar — a reliable proxy for the visual gap between panels.
   Using frame positions for slicing produced crops that read empty dark background
   instead of the actual header/stats content.


41. Adaptive threshold retry for merged digit pairs in header score

   DECISION: _header_isolate_blobs() tries binarization thresholds at THRESH_VAL+5,
   +10, +15, +20 and uses the minimum increment that yields more blobs than at the
   primary THRESH_VAL=150. Wide blobs (> NORM_W × 1.3 ≈ 26 px) are split using
   sub-blob positions from the higher threshold and normalised from that same image.

   RATIONALE: Adjacent digit strokes sometimes merge at the primary threshold
   (THRESH_VAL=150 causes "4"+"6" to merge into a single 27 px blob).  At a higher
   threshold strokes thin enough to separate.  Using the minimum effective increment
   keeps digit shapes as close as possible to the templates (built at THRESH_VAL=150)
   while resolving the merge.  Splitting post-hoc using a projection minimum on the
   merged blob was rejected: the split halves inherit the original blob height, and
   when normalized to NORM_H=30 they may not match templates built from taller digits.


42. Inner-hole count disambiguates '5' vs '6' in header score reading

   DECISION: _header_isolate_blobs() counts interior contours (RETR_CCOMP hierarchy)
   per blob and returns n_inner alongside (x, norm, w, h).  _read_bright_number()
   applies an override: if the best projection match is a no-hole digit
   ('1','2','3','5','7') but n_inner ≥ 1, redirect to the best-scoring hole-digit
   ('0','6','8','9') when its score ≥ 90% of PROJ_CORR_MIN.

   RATIONALE: At the higher binarization threshold needed to separate merged digit
   pairs, stroke shapes change enough that "6" (0.798 projection) scores below "5"
   (0.833 projection) despite being the correct answer.  This is a template-font
   mismatch: templates were built from a different font/size.  The inner-hole count
   is resolution-independent and categorical: "6" always has 1 interior hole
   (its bottom loop); "5" always has 0.  The same principle was already used in
   stat_ocr for '5'/'8' disambiguation; applying it here avoids rebuilding score
   templates from the header font.

   The ≥ 90% leniency on the hole-digit's score prevents the override from firing
   when the hole-digit is wildly implausible (score < 0.63 given PROJ_CORR_MIN=0.70).


43. Accumulator-based sub-timing for tight classifier loops

   DECISION: _classify() accumulates per-phase timing into a caller-supplied
   list[float] (acc) using time.perf_counter() deltas rather than
   with timer.timed() context managers inside the glyph loop.  _read_line()
   injects synthetic Span children after the classify block closes.

   RATIONALE: _classify() is called ~12 times per stat cell (one per glyph).
   Each with timer.timed() call allocates a Span object, appends to a list, and
   calls perf_counter() twice.  At ~40k classify calls per batch run, the per-call
   overhead adds up.  The accumulator approach makes only 4-6 perf_counter()
   calls per _classify() invocation (one at each phase boundary) and zero object
   allocations inside the loop.  The resulting synthetic Spans are identical to
   real Spans from the pipeline_summary aggregation perspective — they appear
   under the correct parent and are rolled up by name across all calls.


44. Weekly Gunsmoke output redirect: folder-sniffing over mandatory --output

   DECISION: main.py's weekly Gunsmoke CSV output keeps its existing
   "<image>.csv next to the image" default, EXCEPT when image_path resolves

45. Generated-report timestamps record run START, not run END

   DECISION: score_detect.py, stat_ocr.py verify(), and pct_fft_predict.py
   each stamp their generated reports with "Generated: <ISO 8601 local
   time>  (run start)" — captured once at the top of the run and threaded
   through to every report-writing call.  Rejected alternative: stamp at
   run END (when results were finalized).

   RATIONALE: docs/action_items.txt #2's stated use case for the timestamp
   is telling whether a report predates a template/asset rebuild --
   answered by comparing the report's timestamp against the template
   file's mtime.  START serves that comparison exactly as well as END
   would (a rebuild that happened after the run started but before it
   finished is not a real scenario in practice — rebuilds and benchmark
   runs are not interleaved), and START is simpler to implement: capture
   the clock once, pass one string down, done.  END would require either
   re-querying the clock at each report-writing call (multiple slightly
   different timestamps for outputs of the same run) or restructuring
   each script to defer all writes to a single point at the end.


46. stat_ocr: bottom-row width as a structural discriminator for '2'/'3'

   DECISION: Measure the foreground pixel span of a normalised glyph's LAST
   row, as a fraction of NORM_W, and use it as a categorical pre-filter in
   _classify() (same insertion point as decision 30's hole-count filter,

   from '3' — neither digit has an enclosed hole.  But the two are still

   nearest-centroid lookup over the full 77d feature vector into two

   gate 0.15) tried first, Agent B (the 64-bin histogram, z-score

   regression (full-vector z-normalization collapsing '6'/'9', Addendum 2's
   "open question") was an artifact of forcing both feature blocks to share
   one Euclidean distance metric, not a real conflict.  Splitting them into
   independent agents with independently-tuned confidence thresholds (the
   first attempt reused Agent A's 0.15 for Agent B and found ZERO
   complementary coverage -- itself a miscalibration, not evidence of
   redundancy; 0.05 revealed real coverage) resolved it cleanly.

   RESULT: the best outcome in this exploration's history by a wide margin.
   Cell-level pct accuracy on the 87-image corpus: 77.3% (prior best,

   ADDENDUM 5 (2026-07-04): added a PAIR TIEBREAK override to _classify(),
   DISABLED BY DEFAULT (PAIR_TIEBREAK_DEFAULT=False, opt-in via
   --enable-pair-tiebreak / StatOcrFft.load(enable_pair_tiebreak=True)).
   Per-digit error analysis showed '4' carrying 23 of 52 held-out errors,
   all misclassified as '7' -- both digits fit '-' and '/' by construction,
   so no line feature can separate them; paren_( is the only Agent A
   dimension that argues for '4', but it has 6x the within-class variance
   of any other dimension specifically for '4', and dominates the actual
   error cases by >4x over every other dimension combined.

   Two more general approaches were tried and rejected before this one:
   globally excluding paren_( from '4' comparisons fixed '4' but opened a
   worse '9'->'4' confusion (fewer dimensions mechanically shrinks a
   centroid's apparent distance to everything, not just '7'); a universal
   lines-first candidate-narrowing cascade fixed '4' and slightly helped
   '9' but broke '3' and '0', confirming a UNIVERSAL per-class feature
   exclusion or cascade is a dead end -- the same "features leak across
   digit families" argument that explains why '4'/'7' collide on arcs
   implies lines can just as easily leak into arc-dominant digits.

   classifier's own top-2 nearest centroids are exactly a registered pair
   (219/1982 held-out glyphs for {'4','7'}).  Every other digit's
   classification is provably unaffected.  '4' improved from 135/197
   correct (23 as '7') to 188/197 (0 misclassified); cell-level pct
   accuracy 90.1% -> 93.2% with it enabled.  Shipped disabled by default
   because it's validated on exactly one pair and one dataset -- a second
   independent corpus would justify defaulting it on.  Full investigation
   trail (including the two dead ends) in docs/known_issues.txt §15's
   PAIR TIEBREAK entry.

   ADDENDUM 6 (2026-07-04): added debugs/calibrate_gabor.py, a reusable
   CLI tool that re-tunes the Gabor kernel's (lambda, sigma, gamma) --
   never tuned for this font specifically, only inherited from an earlier
   general-purpose sweep -- as a ROOT-CAUSE alternative to ADDENDUM 5's
   downstream PAIR TIEBREAK patch.  gfl2/stat_ocr_fft.py gained
   set_gabor_params() so a candidate's kernels can be swapped in-process.

   Two proxy-metric scoring attempts were tried and rejected before one
   that worked: (1) leave-one-out nearest-centroid accuracy on the 3 Gabor
   dims alone found a candidate that dominated the default on every
   isolated metric yet regressed the real classifier (90.1%->86.5% pct
   accuracy) because Agent A never uses Gabor without paren+ring; (2) the
   same LOO metric recomputed on the full 13-dim gabor+paren+ring vector
   still regressed the real classifier (90.1%->88.2%) because a
   nearest-centroid proxy has no way to model Agent B, the confidence-
   margin gating between the two agents, or '?' no-read behavior -- a
   third instance of "looks better in isolation, worse in combination."
   The fix that worked: score every candidate by calling the REAL
   `_classify()` two-agent decision function over every training glyph
   (in-sample, matching this project's own --build/--verify convention),
   not any feature-space proxy.

   RESULT: lambd=5.0/sigma=2.0/gamma=0.5 (default was 4.0/2.0/1.0).
   Real-pipeline pct accuracy 90.1%->91.8% without pair tiebreak (the
   direct payoff of fixing the root cause instead of patching around it);

50. Shared Tesseract ground-truth cache across all three stat_ocr engines

   DECISION: gfl2.stat_ocr._collect_cells() gained an optional gt_cache
   parameter ({source: {"pct","val"}}, consulted before calling Tesseract
   when tess_only=True; a miss falls back to live Tesseract for that cell
   only).  Mirrored into gfl2/stat_ocr_padded.py's own duplicate
   _collect_cells (same source-key format, so one cache file serves both).
   gfl2/stat_ocr_fft.py, which already imports _collect_cells rather than
   duplicating it, picked up the parameter automatically.  All three
   engines' verify() gained a matching gt_cache parameter (None auto-loads
   the cache, {} forces live Tesseract) and their CLIs gained --no-gt-cache.
   A new script, debugs/build_tess_gt_cache.py, runs the Tesseract pass
   once over a chosen image set and writes tests/inputs/daily/tess_gt_cache.py.

   RATIONALE: building/verifying decision 49's stat_ocr_fft.py end to end
   meant running --build then --verify back to back, each independently
   re-collecting pure-Tesseract labels for the same 87-image, 3216-cell
   single/*.png corpus (~1200s / 20 min per call) — two calls, ~40 minutes,
   for labels that cannot have changed between them.  This is true of every
   --build/--verify call across all three engines, not just this one pair:
   the corpus is static and Tesseract's output on it is exactly
   reproducible, so re-running it every time is pure waste with no
   corresponding correctness benefit — these commands are not testing
   Tesseract, they use it as a fixed oracle.  Caching the oracle's output
   once and reusing it turns a ~20-minute step into a sub-second dict
   lookup for every subsequent call against the same images.

   Kept as an explicit opt-out (--no-gt-cache) rather than removing live
   Tesseract collection entirely: the cache is a plain snapshot with no
   staleness detection, so anyone who has re-cropped or replaced images in
   single/ needs a way to bypass it and confirm live Tesseract still
   agrees, or to regenerate it via debugs/build_tess_gt_cache.py.  A cache
   miss (image or cell not present in the file) already falls back to live
   Tesseract automatically, so adding new images without regenerating the
   cache degrades to "slower for the new images only," not silent
   staleness.

   pct string) and tallies classified/correct/misclassified/unknown per
   digit '0'-'9', plus timing -- wired to a new `--verify-glyphs` CLI flag
   that persists its result via debugs/persist_run_result.py to
   tests/outputs/stat_ocr_fft_glyph_runs/.  A new permanent script,
   debugs/compare_stat_ocr_fft_runs.py, diffs any two persisted reports
   (explicit paths or `--latest 2`): current run's per-digit table, a
   per-digit delta table with an explicit REGRESSED/IMPROVED/unchanged
   verdict, separate REGRESSIONS/IMPROVEMENTS call-out lists, totals delta,
   and a timing delta flagged NOTABLE past a 5% threshold.  Accepts both
   the new per-digit schema and the older aggregate-only cell-level schema
   (docs/known_issues.txt §19's baseline), degrading gracefully with an
   explicit "no per-digit breakdown in this report" note rather than
   silently doing a partial job.

   RATIONALE: docs/known_issues.txt §15's own history is a long list of
   one-off per-digit ablation scripts, each written fresh for that
   session's specific question (the STANDALONE ABLATION tables, the
   two-agent classifier's held-out breakdown, etc.) -- real, valuable
   analysis, but none of it reusable, and none of it comparable against a
   later run without re-deriving the same tally loop again.  A permanent
   function + a permanent diff tool means the next "did this change help
   or hurt digit X" question is one command, not a new script.

   VALIDATED IMMEDIATELY: used to compare the vstroke/hbar promotion
   (§19) against its actual pre-change baseline for the first time (the
   §19 write-up itself only had CELL-level totals, no glyph-level
   before/after -- see §20).  A temporary `git worktree add` checkout of
   the pre-promotion commit (a93d24c) was used to generate that baseline
   report, pointing --images at the main worktree's single/*.png via an
   absolute path glob (single/*.png itself is untracked/local-only, so a
   plain worktree checkout doesn't carry it) -- removed immediately after
   via `git worktree remove --force`, leaving no trace in either worktree.
   This is the reusable pattern for "compare current code against an
   older commit" whenever the templates/feature-vector shape differs
   between them (a plain git stash / checkout of just the .py file isn't
   enough, since the persisted centroids must match the code that reads
   them).


53. Per-failing-glyph debug table with a copy-pasteable JSON manifest,
    replacing screenshot-transcription for GT-correction reporting

   DECISION: debugs/debug_stat_ocr_fft_failures.py re-runs
   gfl2.stat_ocr_fft's real classification pipeline (same StatOcrFft.load(),
   same _classify()) over every labelled pct-line glyph, keeps every one
   where the prediction was wrong or '?', and renders TWO debug tables
   (misclassified, unknown) -- one row per failing GLYPH INSTANCE, not one
   row per digit class the way debugs/debug_gabor_features.py's existing
   table works.  Each row shows the raw crop, binarized crop, normalized
   12x20 crop, and every feature this module computes (gabor_45/90deg
   heatmaps, paren_(/paren_) and loop_top/loop_bot overlays, vstroke and
   hbar_top/hbar_bottom best-window overlays, hist/ring bar charts) at one
   scale shared across the whole table (docs/takeaways.txt #49's
   convention).  Each PNG gets a companion .json manifest, same row order,
   with the exact stat_gt_overrides.json-compatible `source` key, the full
   ground-truth pct string, and both the digit-only and literal-character
   index of the failing glyph within it.

   RATIONALE: gfl2.stat_ocr_fft.verify_glyphs() (decision 52) only tallies
   aggregate misclassified/unknown COUNTS per digit -- it has no record of
   WHICH glyph instance failed, so a human reviewing a confusion pattern
   had no way to inspect one without re-deriving the extraction by hand.
   Once a table exists for a human to eyeball, the natural next question
   is "how do I report a finding back precisely" -- retyping a source
   filename (e.g. "fb_d_20251113_auto_1_p1_r0_col3") or a digit position
   from a screenshot is exactly the kind of manual transcription step this
   project's own conventions try to eliminate elsewhere (e.g. stat_data.py
   being a Python module instead of hand-edited JSON, docs/action_items.txt
   #1).  The manifest makes every row's identity copy-pasteable instead of
   re-typed.

   VALIDATED IMMEDIATELY: used to resolve the '1'/'7' portion of
   docs/known_issues.txt §17.  Visual inspection of the rendered table
   found the pattern was backwards -- the classifier's '7' answers were
   correct; the GT ('1') was a Tesseract-era mislabel.  The manifest was
   filtered programmatically (`true=='1' and pred=='7'`) to get exactly 24
   affected rows with their source keys and character indices, which were
   written directly into stat_gt_overrides.json without retyping a single
   filename by hand.  Rebuilding gfl2/stat_ocr_fft.py's templates with the
   correction dropped misclassified glyphs 33->9 and brought both '1' and
   '7' to 100% accuracy -- see §17 for the full before/after.

   ALTERNATIVE CONSIDERED: extending debug_gabor_features.py's existing
   one-row-per-digit-class table to also show failing instances.  Rejected:
   that table's entire design (and its own hard-won global-scale-sharing
   fix, docs/takeaways.txt #49) is built around exactly 10 rows, one
   canonical glyph each -- a failing-instance table needs a variable,
   potentially large row count and per-row GT-correction metadata that
   doesn't fit that shape.  Kept as two separate scripts (same duplication
   convention as decision 49) rather than parameterizing one script to do
   both jobs.
