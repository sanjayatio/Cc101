      digits classified   : 1982
      answered            : 1257  (63.4%)
      flagged '?'         : 725  (36.6%)
      accuracy on answered: 1254/1257  (99.8%)

   but note the two numbers aren't measuring the same thing, so "close" is

   corpus this size).

2.  Run reports should carry an explicit, labelled timestamp

   STATUS: DONE (2026-07-02)

   Generated reports (debugs/pct_fft_predict.py's console summary and its
   tests/inputs/daily/pct_fft_ground_truth.py output, debugs/score_detect.py's
   report_*.txt, gfl2.stat_ocr --verify output, etc.) did not record when
   they were produced.  Without a timestamp, a stale report generated
   before a template rebuild was indistinguishable from a fresh one.

   CONVENTION CHOSEN: run START (when the script began), not run END.
   Rationale: the stated use case — telling whether a report predates a
   template/asset rebuild — is best served by comparing against that
   file's mtime, and START is simpler to capture once and thread through
   to every report-writing function without re-querying the clock per
   report.  Documented once in reference.txt §5.5 rather than per-script.

   IMPLEMENTED:
   - debugs/score_detect.py: run_start captured at top of main(), printed,
     and passed into _write_report()/_write_summary() as the first line
     of report_tesseract.txt, report_blob.txt, report_summary.txt.
   - gfl2/stat_ocr.py verify(): run_start captured on entry, printed as
     the first line of the --verify console summary block.
   - debugs/pct_fft_predict.py: run_start captured at top of main(),
     printed to console, and written into the docstring header of the
     generated tests/inputs/daily/pct_fft_ground_truth.py.
   - Format: ISO 8601 local time via datetime.now().isoformat(seconds),
     labelled "Generated: <timestamp>  (run start)" in every case.

4.  Weekly Gunsmoke pipeline writes output CSVs into tests/inputs/

   STATUS: DONE (2026-07-02)

   FIRST OBSERVED: three stray, untracked CSVs found in
   tests/inputs/weekly_gunsmoke/ (gm_250730.csv, gm_250801.csv,
   gm_250818.csv) sitting next to the tracked .png test fixtures of the
   same name, during a 2026-07-01 untracked-files audit.

   ROOT CAUSE: main.py's weekly_gunsmoke output defaults to "<image>.csv
   in the same folder as the input image" (reference.txt §1.1) when
   --output is not given.  That convention is fine for production input
   folders (single/, or a user's own screenshot folder), but when someone
   runs main.py directly against a fixture image under tests/inputs/ for
   manual inspection, the default silently writes the result back into
   the test-fixtures directory — mixing generated output with committed
   input, and leaving dangling CSVs behind if not cleaned up by hand.

   ACTION: modify the weekly Gunsmoke pipeline so output never lands under
   tests/inputs/ by default.  Candidate approaches (pick one):
   - Detect when image_path resolves under tests/inputs/ and default
     output under tests/outputs/weekly_gunsmoke/ instead (mirrors the
     existing tests/outputs/daily/ convention used by daily Gunsmoke).
   - Or: change the default entirely to always require --output for
     anything outside a designated "production input" root, forcing the
     caller to be explicit rather than relying on folder-sniffing.
   Whichever approach is chosen, document it in reference.txt §1.1 next to
   the existing "Output file: defaults to <image_name>.csv" line.

   DONE: chose the first candidate (folder-sniffing redirect) over
   requiring --output everywhere, since it preserves the documented
   "just run main.py <image>" production convention (reference.txt §5.1)
   unchanged and only special-cases the known-problematic fixtures path.

   IMPLEMENTED (main.py):
   - New _default_weekly_output(image_path) helper: if image_path resolves
     under tests/inputs/, output redirects to
     tests/outputs/weekly_gunsmoke/<image_stem>.csv (creating the dir if
     needed); otherwise unchanged (<image>.csv next to the image).
   - Wired into both _process_weekly() (single image) and
     _process_weekly_folder() (folder batch) in place of the previous bare
     image_path.with_suffix(".csv").
   - tests/outputs/ is already covered by a global gitignore rule
     (**/tests/outputs/), same as the existing tests/outputs/daily/
     convention, so redirected output needs no new ignore entry.
   - Documented in reference.txt §1.1 next to the "Output file" line, and
     in main.py's own --output usage text.
   - Verified: running main.py against a tests/inputs/weekly_gunsmoke/*.png
     fixture now writes to tests/outputs/weekly_gunsmoke/, confirmed via
     both a direct CLI run and a unit-level check of the helper against
     fixture/single//arbitrary-folder paths.  Full suite still
     1273 passed / 14 skipped / 13 xfailed.

   NOT part of this fix, filed separately as a bug: while verifying this
   fix via the CLI, main.py's default weekly-gunsmoke run was found to
   crash unconditionally -- see docs/known_issues.txt §16.  Reproduced
   with --score-pipeline tesseract as a workaround to verify this action
   item; the underlying bug is untouched here to keep this change scoped
   to the output-path issue.

6.  Systematically audit stat_ocr ground truth for other Tesseract-sourced
    mislabels; protect stat_data.py's manual corrections from silent clobber

   STATUS: OPEN

   CONTEXT: docs/known_issues.txt §15 found that tests/inputs/daily/
   stat_data.py's ground truth (and, via --build, assets/fonts/stat_val.py
   itself) contained 13 wrong val-line labels: Tesseract misread a specific
   '2' rendering as '3' widely enough across single/*.png that it survived
   both the eval-set GT and the production template.  The bug was found by
   incidental, non-systematic means — manually rendering and eyeballing
   crop pixels for entries containing digit '3', then confirming with a
   post-fix full-suite regression run (which is what actually caught the
   12th and 13th instances; manual inspection missed them).  There is no
   reason this is the only digit pair or column affected — it is simply the
   one a human happened to look at closely.

   RISK: ground truth for stat_ocr is generated by re-running blob (with
   Tesseract only as a fallback when blob returns '?'), so it structurally
   cannot catch a case where blob is confidently wrong.  Any other
   confident-but-wrong digit pair would be equally invisible to the
   existing test suite, however green it looks.

   ACTION (two related follow-ups, do either or both):
   - Systematic audit: rather than spot-checking one digit pair, script a
     broader cross-check — e.g. render every training/eval crop with its
     current label overlaid, or compare Tesseract's answer against an
     independently-sourced OCR pass, and scan for other digit pairs with a
     suspiciously small combined-score gap in _classify() (the '2'/'3' bug
     showed as a ~0.02 gap — see known_issues.txt §15).
   - stat_data.py clobber protection: tests/generate_stat_inputs.py
     regenerates tests/inputs/daily/stat_data.py from scratch on every run
     (full pipeline, no override applied — see reference.txt §5.3's new
     CAUTION note).  A future re-run would silently discard the 13 hand
     corrections now tracked in stat_gt_overrides.json.  Wire
     stat_gt_overrides.json into generate_stat_inputs.py's collection step
     (mirroring the fix already applied to gfl2/stat_ocr.py's and
     gfl2/stat_ocr_padded.py's --build paths and to build_templates()
     itself) so corrections survive a regen instead of requiring a manual
     re-apply step.

   PROGRESS (2026-07-05): one concrete instance of the systematic audit
   above was performed, for gfl2/stat_ocr_fft.py's pct-line '1'/'7' pair
   (docs/known_issues.txt §17's RESOLUTION) — a new per-failing-glyph
   debug tool with a copy-pasteable JSON manifest (debugs/
   debug_stat_ocr_fft_failures.py, docs/decisions.txt #53) found 24 more
   Tesseract-sourced GT mislabels, now in stat_gt_overrides.json (39
   entries total) and rebuilt into gfl2/stat_ocr_fft.py's templates.  This
   is still a single digit pair on a single engine, not the broader
   cross-check described above — production's assets/fonts/stat_pct.py /
   stat_val.py (gfl2/stat_ocr.py, gfl2/stat_ocr_padded.py) have NOT been
   rebuilt with these 24 entries, and the '0'/'8' pattern flagged
   alongside '1'/'7' in the same §17 entry has not been audited at all.
   The debug tool itself is reusable for the next digit pair or engine
   this action item's systematic audit eventually covers.
