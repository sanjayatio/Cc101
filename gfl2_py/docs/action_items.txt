2.  Run reports should carry an explicit, labelled timestamp

   STATUS: DONE (2026-07-02)

   Generated reports (debugs/pct_fft_predict.py's console summary and its
   tests/inputs/daily/pct_fft_ground_truth.py output, debugs/score_detect.py's
   report_*.txt, gfl2.stat_ocr --verify output, etc.) did not record when
   they were produced.  Without a timestamp, a stale report generated
   before a template rebuild was indistinguishable from a fresh one.

   CONVENTION CHOSEN: run START (when the script began), not run END.
   Rationale: the stated use case — telling whether a report predates a
   template/asset rebuild — is best served by comparing against that
   file's mtime, and START is simpler to capture once and thread through
   to every report-writing function without re-querying the clock per
   report.  Documented once in reference.txt §5.5 rather than per-script.

   IMPLEMENTED:
   - debugs/score_detect.py: run_start captured at top of main(), printed,
     and passed into _write_report()/_write_summary() as the first line
     of report_tesseract.txt, report_blob.txt, report_summary.txt.
   - gfl2/stat_ocr.py verify(): run_start captured on entry, printed as
     the first line of the --verify console summary block.
   - debugs/pct_fft_predict.py: run_start captured at top of main(),
     printed to console, and written into the docstring header of the
     generated tests/inputs/daily/pct_fft_ground_truth.py.
   - Format: ISO 8601 local time via datetime.now().isoformat(seconds),
     labelled "Generated: <timestamp>  (run start)" in every case.

8.  [PRIORITY] Fix gabor_45's normalization, then use it as a cheap
    first-stage gate for {4,7} vs everything else

   STATUS: DONE (2026-07-06) -- gate IMPLEMENTED as a real, opt-in
           pre-filter (enable_vstroke_gate / --enable-vstroke-gate,
           DISABLED BY DEFAULT).  Measured trade-off: ~15-25% classify
           speedup at a real, root-caused, small accuracy cost (a new
           '0'->'8' confusion, cell-level 98.9%->98.2%) -- see
           IMPLEMENTATION RESULT below.  Kept disabled by default, same
           convention as PAIR_TIEBREAK_DEFAULT, pending the hole-count
           mitigation idea noted below.

   CONTEXT: a 2026-07-05 session investigating gfl2/stat_ocr_fft.py's
   Gabor feature found gabor_45 is currently INERT in the shipped
   templates (assets/fonts/stat_pct_fft.py) -- every digit's centroid
   equals 1.0000000000 (variance 3.6e-26 across all 10 digits), so it
   contributes exactly 0.0% to any real classification decision.  ROOT
   CAUSE: compute_features() computes the Gabor "fraction" as
   resp/(sum(resps)+eps) -- meaningful when 2+ orientations shared the
   denominator, but with N_ORIENT=1 (only 45deg survives; 0deg and 90deg
   were both removed in favor of vstroke/hbar, see known_issues.txt §15's
   2026-07-05 entries) this collapses to a self-fraction that is always
   ~1.0 regardless of digit.  Confirmed empirically on real training
   glyphs (raw response varies meaningfully by digit -- e.g. '4' ~590-660,
   '8' ~800-820 in one sample -- the signal exists, the fraction formula
   discards it).

   Decomposing what ACTUALLY classifies '7' (nearest-centroid distance to
   its real nearest neighbor, '1') confirmed gabor_45 contributes 0.0%;
   the real work is vstroke (31.2%), paren_) (24.8%), loop_top (14.6%),
   hbar_top (13.7%), hbar_bot (11.2%).

   IDEA: fix the normalization (e.g. z-score the raw response against
   training mean/std, the same convention Agent B's histogram already

   margin trick).

   GABOR_MAX_C4/C7 (decision 62), SOBEL_MEAN_C2/C5 and PAREN_CLOSE_3_GATE
   (§25/§26) -- are Python module-level constants, hand-derived from a
   one-off grid sweep or manual measurement against a SPECIFIC glyph
   representation, then typed directly into gfl2/stat_ocr_fft.py.  `--build`
   retrains the gpr/hist nearest-centroid templates but has no mechanism to
   re-derive any of these five values.  When the glyph representation
   changed underneath them (§27), they went silently stale and nothing in
   the build/verify pipeline could tell -- the same failure mode, at
   smaller scale, as §15's Tesseract-GT-contaminated templates (a bad value
   baked in and invisible until someone happens to notice the symptom).
   The same is true of every OTHER hand-picked geometry constant in this
   module (VSTROKE_KERNEL_H/W, VSTROKE_INK_FRAC, HBAR_KERNEL_H/W,
   HBAR_INK_FRAC, MAX_STROKE_W, the loop template's _LOOP_CY_TOP/BOT and
   _LOOP_RY_FRAC/RX_FRAC) and, per action_items.txt #19, of NORM_W_PCT/
   NORM_H_PCT upstream in gfl2/stat_ocr.py.  This is a repeated pattern
   across the project, not unique to this module -- every "hardcode a
   threshold from a one-off measurement" decision in known_issues.txt's
   history (§9's inner-blob thresholds, §14's Hu tiebreaker, §19's kernel
   geometry, §21-§26's various gates) has the identical shape: a real
   number, derived once by hand, with no path back to re-derive it when
   anything upstream changes.  gfl2/ itself is currently FLAT (one module
   per file, no subpackages) -- there is nowhere in the existing layout
   for a calibration step's input/output to live as anything other than
   another ad-hoc debugs/ script plus a hand-edited constant.
