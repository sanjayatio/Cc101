6.  Systematically audit stat_ocr ground truth for other Tesseract-sourced
    mislabels; protect stat_data.py's manual corrections from silent clobber

   STATUS: OPEN

   RISK: stat_ocr ground truth is generated by re-running the blob
   pipeline itself (Tesseract only as a fallback when blob returns '?'),
   so it structurally cannot catch a case where blob is confidently
   wrong.  One instance of this (a '2'/'3' val-line mislabel) was found by
   incidental, non-systematic means -- see docs/known_issues.txt §15.
   There is no reason it's the only affected digit pair or column.

   ACTION (two related follow-ups, do either or both):
   - Systematic audit: rather than spot-checking one digit pair, script a
     broader cross-check (render every training/eval crop with its
     current label overlaid, or compare against an independently-sourced
     OCR pass, and scan for digit pairs with a suspiciously small
     combined-score gap in _classify()).
   - stat_data.py clobber protection: tests/generate_stat_inputs.py
     regenerates tests/inputs/daily/stat_data.py from scratch on every
     run with no override applied (reference.txt §5.3's CAUTION note) --
     a future re-run would silently discard the corrections tracked in
     stat_gt_overrides.json.  Wire stat_gt_overrides.json into
     generate_stat_inputs.py's collection step (mirroring the fix already
     applied to gfl2/stat_ocr_v0_1_0.py's and gfl2/stat_ocr_v0_1_1.py's
     --build paths and to build_templates() itself).

   PROGRESS: one instance of the systematic audit (gfl2/stat_ocr_v0_2_0.py's
   pct-line '1'/'7' pair) was performed 2026-07-05 -- see docs/
   known_issues.txt §17's RESOLUTION for the full result (24 GT mislabels
   found and fixed).  gfl2/stat_ocr_v0_1_1.py has not been rebuilt with
   those overrides yet.  stat_data.py clobber protection is still
   unimplemented.

   PROGRESS (2026-07-12): a SECOND, distinct GT-corruption pattern found
   and fixed while investigating gfl2/stat_ocr_v0_3_0.py's remaining hard
   cases -- not a digit CONFUSION like every prior finding in this item,
   but Tesseract hallucinating an extra digit (always '1') with no
   corresponding ink at all, 7 instances, all pct-line, all adjacent to a
   '%' sign (plausibly misreading its diagonal slash).  Visually confirmed
   against the real rendered image for all 7 before correcting.  See
   docs/known_issues.txt §32 and decisions.txt #83.  Still not a
   scripted/systematic sweep -- found via targeted investigation of one
   engine's specific mismatch list, same "incidental, non-systematic
   means" caveat this item's RISK paragraph already flags.

   PROGRESS (2026-07-12): a THIRD, distinct GT-corruption pattern found
   while validating gfl2/header_ocr_v0_3_0.py's new classify_header() tree --
   this one on the header STATS ROW (dealt/taken/turns), a different
   corpus/collection path from every prior finding in this item (pct-line
   only, so far).  Not a digit confusion, and not a phantom extra digit
   with no ink either: this crop deliberately includes a sliver of the
   preceding label text ("...dealt"/"...taken"/"...turns") so the
   production classifier's own label-bleed-drop step can strip it -- but
   the Tesseract GT reads that SAME raw crop directly, and sometimes
   hallucinates the label's trailing letter as a leading digit ('s'->'5',
   'n'->'1').  100 of 101 whole-field mismatches fit this exact shape,
   visually confirmed on several real crops.  See docs/known_issues.txt
   §34 and decisions.txt #89, and docs/takeaways.txt #82 for the
   generalized lesson.  NOT fixed -- would need the GT collector to run
   through (or otherwise account for) the same label-bleed-drop logic the
   production classifier already applies, not just trust a whitelisted
   Tesseract call to ignore what it isn't supposed to read.  Still no
   scripted/systematic sweep across the whole codebase -- three
   incidental findings in three different engines/corpora is itself a
   signal this class of bug is common enough to warrant one.

   PROGRESS (2026-07-12): the "stat_data.py clobber protection" bullet
   above is now DONE -- tests/generate_stat_inputs.py applies
   stat_gt_overrides.json unconditionally after collection (decisions.txt
   #95), regardless of GT source mode.  The "systematic audit" bullet
   remains open.

   PROGRESS (2026-07-12, same day): a FOURTH, distinct GT-corruption
   pattern found and fixed while rescoping the daily stat-cell test
   harness to v0_3_0+v0_1_1 only (decisions.txt #95) -- val-line, not pct
   like every prior finding here, and found by a NEW method: comparing
   v0_3_0's and v0_1_1's mismatch lists against EACH OTHER first (9 cells
   where both agreed on an answer that disagreed with cached Tesseract
   GT), then visually confirming those 9 specifically, rather than
   eyeballing every raw mismatch (takeaways.txt #86).  All 9 were dropped
   or misread digits.  Fixed via 9 new stat_gt_overrides.json entries.
   See docs/known_issues.txt §36.  Still not a scripted/systematic sweep
   -- a fourth incidental finding, now via a genuinely different (and
   cheaper) detection method than the first three.

21. stat_ocr_fft: '2's bottom-band stroke-thickness measurement likely
    conflates curve extent with bar thickness, not yet investigated

   STATUS: OPEN

   CONTEXT: 2026-07-10, debugs/debug_line_stroke_thickness_sweep.py's
   corpus sweep (built to derive a physically-grounded stroke-thickness
   buffer for the LINE-SPLIT SOBEL MODE's '7' isolation gate, and to flag
   outlier images along two variance axes -- centroid shift and stroke
   thickness -- for the separately-requested top-20 meaningful-image
   curation). measure_stroke_thickness() counts consecutive rows within a
   digit-specific row band whose foreground occupancy clears BAR_INK_FRAC
   (0.5) of the glyph's width.

   ANOMALY: '7' and '5' (both straight top bars) measured a tight,
   consistent thickness across the whole 87-image corpus (3.696+/-0.46px
   and 3.678+/-0.467px respectively -- std under 0.5px either way). '2'
   (bottom band, 0.60-1.0 of height) measured 5.472+/-1.846px -- roughly
   4x the variance of the other two, despite all three using the exact
   same measurement mechanism and BAR_INK_FRAC threshold. SUSPECTED
   (NOT CONFIRMED): '2's bottom band captures its curved foot/tail, not a
   straight bar the way '7'/'5's top bands do -- a curve's extent through
   a fixed-height row band is a fundamentally different (and more
   variable) quantity than a straight bar's thickness, which would explain
   the inflated variance without it being a corpus-quality or measurement
   bug.

   NOT DONE: visually inspecting a handful of real '2' glyphs' bottom-band
   masks (same "unit debug before/alongside integration" convention this
   project uses elsewhere, e.g. debugs/debug_gabor_features.py) to confirm
   whether the row-band is genuinely catching a curved foot rather than a
   flat bar; if confirmed, '2's row band and/or the ink-fraction threshold
   likely need their own dedicated tuning rather than reusing '7'/'5's
   convention as-is. This was NOT blocking for the '7'-isolation gate work
   that motivated the sweep (which only needed '7's own measurement to be
   sound, and it independently validated cleanly -- see docs/decisions.txt
   for the full write-up) -- filed here so '2's number isn't mistaken for
   an equally-trustworthy stroke-thickness figure without this caveat.

28. gfl2/stat_ocr_v0_3_0.py's classify() tree has no confidence-based
    abstention -- it always answers, even at its narrowest real margin

   STATUS: OPEN -- flagged directly as a significant design gap.

   CONTEXT: every leaf in classify() always returns a specific digit; the
   only '?' path is one defensive branch the real corpus never hits.
   Unlike gfl2/stat_ocr_v0_1_0.py (PROJ_CORR_MIN) and gfl2/stat_ocr_v0_2_0.py

   margin here is thin, don't guess."  Concretely: the '2'/'5' leaf's real
   corpus margin is exactly 1 unit, and synthetic perturbation testing
   found '2'/'5' failures dominate the engine's remaining fragility under
   stress, every one a CONFIDENT wrong answer (docs/takeaways.txt #69).

   ACTION: add a real margin/confidence check per leaf and return '?' when
   a glyph falls inside that margin, mirroring gfl2/stat_ocr_v0_1_0.py and
   gfl2/stat_ocr_v0_2_0.py's existing discipline.  Likely more durable than
   further per-leaf recalibration.

   PARTIAL PROGRESS: one leaf (the {2,3,5} split) gained a reachable
   abstention path -- see docs/decisions.txt #81.  No other leaf has any
   confidence gate; the general ACTION above remains open.
