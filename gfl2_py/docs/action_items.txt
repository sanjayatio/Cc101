2.  Run reports should carry an explicit, labelled timestamp

   STATUS: DONE (2026-07-02)

   Generated reports (debugs/pct_fft_predict.py's console summary and its
   tests/inputs/daily/pct_fft_ground_truth.py output, debugs/score_detect.py's
   report_*.txt, gfl2.stat_ocr --verify output, etc.) did not record when
   they were produced.  Without a timestamp, a stale report generated
   before a template rebuild was indistinguishable from a fresh one.

   CONVENTION CHOSEN: run START (when the script began), not run END.
   Rationale: the stated use case — telling whether a report predates a
   template/asset rebuild — is best served by comparing against that
   file's mtime, and START is simpler to capture once and thread through
   to every report-writing function without re-querying the clock per
   report.  Documented once in reference.txt §5.5 rather than per-script.

   IMPLEMENTED:
   - debugs/score_detect.py: run_start captured at top of main(), printed,
     and passed into _write_report()/_write_summary() as the first line
     of report_tesseract.txt, report_blob.txt, report_summary.txt.
   - gfl2/stat_ocr.py verify(): run_start captured on entry, printed as
     the first line of the --verify console summary block.
   - debugs/pct_fft_predict.py: run_start captured at top of main(),
     printed to console, and written into the docstring header of the
     generated tests/inputs/daily/pct_fft_ground_truth.py.
   - Format: ISO 8601 local time via datetime.now().isoformat(seconds),
     labelled "Generated: <timestamp>  (run start)" in every case.

6.  Systematically audit stat_ocr ground truth for other Tesseract-sourced
    mislabels; protect stat_data.py's manual corrections from silent clobber

   STATUS: OPEN

   CONTEXT: docs/known_issues.txt §15 found that tests/inputs/daily/
   stat_data.py's ground truth (and, via --build, assets/fonts/stat_val.py
   itself) contained 13 wrong val-line labels: Tesseract misread a specific
   '2' rendering as '3' widely enough across single/*.png that it survived
   both the eval-set GT and the production template.  The bug was found by
   incidental, non-systematic means — manually rendering and eyeballing
   crop pixels for entries containing digit '3', then confirming with a
   post-fix full-suite regression run (which is what actually caught the
   12th and 13th instances; manual inspection missed them).  There is no
   reason this is the only digit pair or column affected — it is simply the
   one a human happened to look at closely.

   RISK: ground truth for stat_ocr is generated by re-running blob (with
   Tesseract only as a fallback when blob returns '?'), so it structurally
   cannot catch a case where blob is confidently wrong.  Any other
   confident-but-wrong digit pair would be equally invisible to the
   existing test suite, however green it looks.

   ACTION (two related follow-ups, do either or both):
   - Systematic audit: rather than spot-checking one digit pair, script a
     broader cross-check — e.g. render every training/eval crop with its
     current label overlaid, or compare Tesseract's answer against an
     independently-sourced OCR pass, and scan for other digit pairs with a
     suspiciously small combined-score gap in _classify() (the '2'/'3' bug
     showed as a ~0.02 gap — see known_issues.txt §15).
   - stat_data.py clobber protection: tests/generate_stat_inputs.py
     regenerates tests/inputs/daily/stat_data.py from scratch on every run
     (full pipeline, no override applied — see reference.txt §5.3's new
     CAUTION note).  A future re-run would silently discard the 13 hand
     corrections now tracked in stat_gt_overrides.json.  Wire
     stat_gt_overrides.json into generate_stat_inputs.py's collection step
     (mirroring the fix already applied to gfl2/stat_ocr.py's and
     gfl2/stat_ocr_padded.py's --build paths and to build_templates()
     itself) so corrections survive a regen instead of requiring a manual
     re-apply step.

   PROGRESS (2026-07-05): one concrete instance of the systematic audit
   above was performed, for gfl2/stat_ocr_fft.py's pct-line '1'/'7' pair
   (docs/known_issues.txt §17's RESOLUTION) — a new per-failing-glyph

7.  Investigate fb_d_20260315_p1_r3 as a candidate structural/rendering
    outlier (stat_ocr_fft), and cross-check against gm_d_20250908 /
    fb_d_20251112 p2

   STATUS: DONE (2026-07-05, same day, follow-up) -- the fb_d_20260315_p1_r3
           investigation is resolved; the gm_d_20250908/fb_d_20251112
           cross-check below was NOT performed (see RESOLUTION).

   CONTEXT: docs/known_issues.txt §23.  After fixing §21 (PCT_STRIP_Y
   zero-slack clipping) and §22 (gabor_90 removal) in the same session,
   gfl2/stat_ocr_fft.py's corpus-wide result narrowed to 3 misclassified +
   3 unknown glyphs out of 10,341 -- and ALL 6 trace to one single row,
   fb_d_20260315_p1_r3, across all 4 stat columns.  Pixel-level dumps
   confirmed two distinct, real artifacts specific to this row: col1's
   '2' is genuinely under-inked (this cell's own gray.min()=143 vs
   gray.min()=70 for its sibling cells in the SAME row), and col2's '5'
   digits show a fragmented/noisy binarized loop (a spurious disconnected
   2px blob, a dropped-then-restored left wall).  col3/col4's '4'
   unknowns, by contrast, are clean crops with no fragmentation -- their
   '?' is the already-tracked §20 confidence-margin weakness, not part of
   whatever is affecting col1/col2.

   This is the same CATEGORY of finding as two already-documented
   structural outliers that turned out to be per-image/per-panel
   anomalies rather than generalizable pipeline weaknesses:
     - §10: fb_d_20251112 p2 -- all fields fail at blob extraction on
       that one panel.
     - §18: gm_d_20250908.png col3 cells truncate to one digit.
   Neither §10 nor §18 has been root-caused either (both are flagged, not
   confirmed structural) -- so this is also an opportunity to check
   whether all three share a common cause (e.g. a specific screenshot
   tool/compression setting, a specific game UI theme or scaling option)
   rather than being three coincidentally-unrelated one-off anomalies.

   CORROBORATING EVIDENCE (2026-07-05, same day): production's gfl2/
   stat_ocr.py -- a completely different classifier (1D projection
   correlation, not FFT/Gabor) -- was run against fb_d_20260315_p1_r3_col1
   directly (docs/known_issues.txt §17's PRODUCTION REBUILD entry) and
   also fails on it, reading '779' instead of '2.79': a parse/extraction
   failure (the leading digit AND the decimal point both go missing), a
   DIFFERENT failure mode than stat_ocr_fft's digit misclassification on
   the same cell.  Two structurally unrelated classifiers failing on the
   same single cell in two different ways is strong evidence this is a
   genuine per-cell/per-row rendering anomaly, not a weakness in either
   classifier's feature set.

   ACTION:
   - Confirm "this row" vs "this image": render/inspect OTHER rows in the
     same fb_d_20260315_p1 panel (rows other than r3) -- if they look
     normal, the anomaly is row-specific (e.g. a one-off compression
     artifact on that row's pixel band); if the whole image looks
     under-inked/fragmented, it's image-specific (e.g. a different
     screenshot source or save quality for that capture).
   - Check whether fb_d_20260315_p1_r3, fb_d_20251112 (§10), and
     gm_d_20250908 (§18) share any file-level property (compression
     level, color depth, source resolution before any resizing this
     pipeline does) that a normal image in single/*.png doesn't.
   - Only after the above: decide whether a pipeline-level mitigation is
     worth building (e.g. detecting and flagging low-contrast/fragmented
     cells before classification, similar in spirit to this project's
     existing '?' honesty convention) or whether documenting it as an
     accepted per-capture limitation is enough.

   RELATED, DEFERRED: an "endpoint count" topological feature (skeletonize
   + count degree-1 skeleton pixels, to categorically separate {'0','8'}
   from {'6','9'} the way hole-count already separates '5'/'8') was
   proposed while investigating this row, then explicitly deferred by
   user direction before any prototyping started.  The col2 fragmentation
   finding above is a concrete, demonstrated reason for caution: skeleton-
   izing a broken/noisy blob would manufacture spurious endpoints from the
   noise itself, not from real digit structure (the same risk that made
   native-resolution Hu moments unreliable — docs/takeaways.txt #39). If
   picked up later, validate via the real classifier's marginal-utility
   ablation (docs/takeaways.txt #46, #48), not a standalone shape metric,
   and validate on OTHER images first, not this row's already-known-
   fragmented crops.

   RESOLUTION (2026-07-05, same day, follow-up): docs/known_issues.txt
   §23's full RESOLUTION section has the complete story.  Summary: a new
   whole-cell debug tool (debugs/debug_outlier_cell_compare.py) compared
   the flagged cell against the same row in the image's OTHER panel
   (fb_d_20260315_p2_r3_col1, from the identical screenshot) -- clean,
   crisp text and a fully-rendered val, versus the flagged cell's visible
   ghosting/double-exposure artifact and blank val.  Root cause:
   mid-animation screenshot capture (the panel 1 row was caught mid-
   transition; panel 2's identical row had already finished rendering) --
   corrupted source pixels, not a classifier/cropping/labeling defect.
   Fixed via a new shared exclusion mechanism (stat_excluded_cells.json +
   gfl2.stat_ocr._load_excluded_cells/_collect_cells, docs/decisions.txt
   #56), applied to all three stat_ocr engines.  gfl2/stat_ocr_fft.py now
   reads 100.0% (10327/10327, 0 misclassified, 0 unknown) on the
   remaining corpus.

   NOT DONE: the gm_d_20250908 (§18) / fb_d_20251112 (§10) cross-check
   this item's title also called for was NOT performed -- neither has
