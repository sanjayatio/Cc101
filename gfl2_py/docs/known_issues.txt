1.  Blank scores when using Tesseract after new-buff asset saves (Windows)

   STATUS: MITIGATED
   WORKAROUND: use --score-pipeline blob (now the default in main.py).
               The blob/Hu pipeline is Tesseract-free and is unaffected.

   FIRST OBSERVED: Session processing gm_250818.png (June 2026).
   Rows 2, 3, 4, 8, 10 — every row whose PREVIOUS row triggered a
   buff_ocr._save_asset() call — produced blank score fields in the CSV.

   SYMPTOMS:
   - Score column empty in CSV for a repeatable subset of rows.
   - Affected rows are not random; they always follow a row where a new
     buff PNG was written to assets/buff/.
   - Not reproduced in the Linux sandbox — only on the user's Windows
     machine (Python 3.14, Tesseract from UB-Mannheim).

   CONFIRMATION VIA TRACE (GFL2_TRACE=1, gm_250818.png):
   - Clean rows:    _ocr_score ~0.154s (method 1 succeeds).
   - Affected rows: _ocr_score ~0.303s (method 1 fails, method 2
     also attempted and also fails).
   - The 0.303s rows correspond exactly to rows immediately following a
     new-buff asset save in the previous row.

   ASSUMPTIONS / DEDUCTIONS:
   - Writing a PNG file to assets/buff/ via cv2.imwrite() on Windows
     triggers filesystem activity (NTFS journal, antivirus scan, or
     page-cache pressure) that degrades Tesseract's ability to write
     or read its own temp files for the next OCR call.
   - The contamination is cross-row: row N's asset save affects row
     N+1's score OCR, not row N's own score (already computed at that
     point).
   - Both OCR methods (image_to_string and image_to_data) fail, ruling
     out a PSM-mode-specific issue.

   ATTEMPTS TO RESOLVE:
   a. Move _ocr_score before buff_ocr.translate in _parse_row.
      Result: FAILED. The contamination is cross-row (row N affects N+1),
      not within the same row.

   b. Batch ALL score and owner-name OCR calls before any buff_ocr calls
      in parse() — current implementation.
      Result: CONFIRMED CORRECT IN THEORY. Works in sandbox. Still failing
      on Windows; suspected cause: stale .pyc loading the old unbatched
      code despite compile_gfl2.py being run.

   MITIGATION (implemented):
   - Blob/Hu moment pipeline added to score_detect.py.
   - make_score_fn() factory exposes it for use in weekly_gunsmoke.parse().
   - --score-pipeline blob is now the default in main.py.
   - Benchmark on 10-crop ambiguity-ranked test set: 100% accuracy,
     ~4ms/row vs ~200ms/row for Tesseract.
   - Templates stored in assets/score_fonts/digit_templates.json; rebuild with
     python debugs/score_detect.py --build.

   ROOT CAUSE: Not fully diagnosed. Tesseract on Windows appears to share
   some process-level state (temp file handles, page-cache) with
   concurrent filesystem writes. The blob pipeline avoids Tesseract
   entirely for score extraction, bypassing the issue.

   REMAINING OPEN WORK (if root cause diagnosis is desired):
   - Check whether TESSDATA_PREFIX or TMP is set to a network/NTFS path.
   - Try setting TMPDIR/TMP/TEMP to a local path before running main.py.
   - Try pytesseract with timeout parameter to rule out silent hangs.
   - Print raw pytesseract return value in trace to distinguish "empty
     string" from "garbage that failed digit regex".


2.  Owner name OCR noise (minor)

   STATUS: ACCEPTED / Low priority

   SYMPTOM: Owner name occasionally has 1-2 leading noise characters
   (e.g. "j GreenMan" instead of "GreenMan"). Also sometimes has
   trailing " -" from the Decisive Battle badge text.

   ASSUMPTION: A small rank icon at the left edge of the name cell
   bleeds into the OCR crop region and is misread as a letter.

   CURRENT MITIGATION: _ALNUM_RE filter strips non-alphanumeric
   characters, which removes most noise. The leading "j" or "f" that
   passes the filter is alphabetic and not stripped.

   IDEA TO RESOLVE: Maintain a known-names allowlist. After OCR,
   fuzzy-match the result against known owner names and correct minor
   misreads. Alternatively, increase the name crop's x0 ratio slightly
   (~0.085 instead of 0.073) to skip the rank icon area.

5.  populate_doll_assets: single-panel images incorrectly split

   STATUS: RESOLVED

   FIRST OBSERVED: fb_d_060518.png and ~10 other fb_d_ files.

   SYMPTOM: Files parsed as 0 frames / 0 assets. Debug showed two
   panels: 380×997 and 760×997 — an unequal split of a 1140px-wide
   single-panel image.

   ROOT CAUSE: _split_panels() in daily_gunsmoke.py searched for the
   brightest column within the middle third of the top bar. A bright UI
   separator inside a single-panel layout (at x≈380, i.e. 33% of width)
   fell inside the old guard range (0.2–0.8) and triggered a spurious
   split. The resulting 380px sub-panel had SEARCH_X1=0.15 → 57px search
   width, which clipped the ~90px portrait frames below the 0.70
   squareness threshold.

   FIX:
   - _split_panels() guard tightened from 0.2–0.8 to 0.4–0.6. A genuine
     2-panel layout always splits ≈50/50; any split outside 40–60% is now
     treated as a single panel.
   - SEARCH_X1 raised from 0.15 to 0.25 as belt-and-suspenders for
     any panels narrower than the calibration image.

   FIRST OBSERVED: Session adding doll_name_ocr.py (June 2026).

   SYMPTOM: Three doll names are consistently misread by Tesseract and then
   stored as mislabelled templates in assets/doll_names/templates.json and
   as mislabelled portrait files in assets/dolls/:

      Tesseract reads    Correct name
      ────────────────   ────────────
      Sharkty            Sharkry
      soringfele         Springfield   (OCR garble; dist=3, borderline fuzzy)
      aiongjiN           QiongJiu      (OCR garble; dist too large for fuzzy)

   ROOT CAUSE: The projection classifier is built from OCR-labelled crops.
   When Tesseract misreads a name, the template is stored under the wrong

   correct name exists in assets/dolls/.

   FIX (per doll):
      1. Rename assets/dolls/_<wrong>.png → _<correct>.png
      2. In assets/doll_names/templates.json, rename the key accordingly.
      3. Re-run main.py — fuzzy correction and projection classifier
         will now produce the correct name.

   STATUS OF EACH:
      Sharkty → Sharkry     : dist=1 — fuzzy will fix once portrait renamed
      soringfele → Springfield : dist=3 — fuzzy will fix once portrait renamed
      aiongjiN → QiongJiu   : dist=7 — fuzzy CANNOT fix; portrait rename +

      Expected     Got      Root cause
      ─────────────────────────────────────────────────────────────────────
      '321108'  →  '32005'  n=5 beats n=6 because '8' at seg[5] is
                             tiebroken to '5' (gap=0.010 < AMBIG_THRESH).
                             If '8' were correct, n=6 avg would beat n=5.
      '25164'   →  '35164'  '2' primary score = 0.957, '3' = 0.981

     give more diverse '2', '5', '8' samples and reduce template bias.

     the minimum v_proj value in the middle third as a scalar discriminator.
     '8' has a pronounced waist (min ≈ 0.067) while '5' does not (≈ 0.084).


10. daily_gunsmoke header stats_row blob: high Tesseract fallback rate

   STATUS: OPEN — fix implemented; requires header_templates rebuild

   FIRST OBSERVED: Session migrating header OCR to blob pipeline (June 2026).

   SYMPTOM: stats_row/blob fires on 162/162 crops but 111/162 still fall
   through to stats_row/tess.  Root causes identified:

   (a) THRESH_BIN=180 causes '4'+'8' in the header font to merge into a
       single 24 px blob (classified as '?'), triggering the Tesseract fallback.
   (b) Comma thousand-separator blobs (h≈5-10 px) appeared as "digit" blobs,
       causing blob count ≠ expected digit count and '?' markers in output.
   (c) The original header_templates.json was built using THRESH_BIN=180, so
       templates were missing '4' and '8' (those crops were skipped at build
       time due to count mismatch) — even when blobs were separable.

   FIX IMPLEMENTED (June 2026):
   - daily_gunsmoke._read_stat_crop now uses HDR_THRESH=155 (not _binarize's 180)
     and HDR_BLOB_MIN_H=12 (not DOT_MAX_DIM=8).
   - build.py (unified builder) uses matching _binarize_hdr (155) and
     _find_header_blobs (min_h=12) so templates and inference are consistent.

   CROP POSITIONS UPDATED (June 2026, continued session):
   - STATS_ROW_Y0_FR changed from 1.50 → 1.25: old value placed sy0 inside the
     dark header bar (ends at y≈57); new value lands safely below it.
   - STATS_TAKEN_X changed from FR-relative to panel-width fraction (0.540, 0.645):
     taken failures dropped 15 → 0 across 163 panels.
   - STATS_DEALT_X changed to (0.223, 0.330): x0 anchored just past the trailing
     "t" of "Damage dealt"; extraction failures dropped 38 → 1 (one fb_d panel
     with an atypical dark-rendered label + UI bar element at the h=12 threshold).
   - STATS_TURNS_X changed to panel-width fraction (0.860, 0.940): turns works.
   - debug_header.py output moved to debugs/ folder.

   CURRENT STATE (after crop fixes, before template rebuild):
   - Blob extraction: 1/163 panels fail (fb_d_20250928[p2]).
   - Actual stats_row/tess count: ~15 (down from 17 old, up from goal of 1).
   - Discrepancy = classification fails on valid blob sets because
     header_templates.json was built at THRESH_BIN=180, not HDR_THRESH=155.

   ACTIVATION REQUIRED:
   Rebuild templates at the corrected threshold:
     python assets/builders/build.py single/
   Then re-run main.py — expect stats_row/tess to drop from ~15 toward 1.


9.  stat_ocr ib_d: '5'→'8' misclassification and K-suffix detection fragility

   STATUS: RESOLVED (June 2026 — all 15 integration tests pass, 49/49 suite)

   FIRST OBSERVED: Session improving stat_ocr ib_d accuracy (June 2026).

   ACCURACY BEFORE THIS SESSION (ib_d_20260111.png):
      pct  40/40  (100%)
      val  37/40  (92.5%)   ← '14503'→'14803', '3820K'→None, '1001K'→None

   FIXES APPLIED THIS SESSION (June 2026):
      - Inner-blob count discriminator: _count_inner_blobs() counts enclosed
        holes via RETR_CCOMP hierarchy.  '8'→2 holes, '5'→0 holes.
        _classify() uses this as a pre-filter (query holes > 0 → restrict
        templates to matching hole count) and reverse check (proj selects '8'
        but query has 0 holes → redirect to best zero-hole candidate).
        Stored as "inner_blobs" key in templates.json.
      - VAL_STRIP_Y raised from (0.44, 0.82) to (0.50, 0.82): eliminates
        pct-line fragment blobs that bleed into the top of the val strip and
        corrupt blob detection.
      - _filter_y_outliers applied per-strip in _read_line and build_templates
        as a secondary defence against residual noise blobs.
      - _features() 5-tuple unpack fixed to pass full 6-tuple to buckets in
        build_templates (was silently discarding inner_blobs during build).
      - K/M suffix detection: rightmost '?' in a val string with ≥ 4 items
        is treated as 'K'.
      - PROJ_VERY_LOW = 0.35: blocks Hu fallback for very-low-confidence
        glyphs (K at proj≈0.27) that previously misfired to '2'.
      - Partial results: _reconstruct_val returns strings with '?' markers
        instead of None; _v() in dg_output.py nullifies values containing '?'.
      - GT override file (stat_gt_overrides.json) corrects Tesseract GT errors.
      - COL2_FR / COL3_FR widened to prevent '%' horizontal clipping.

   ACTIVATION REQUIRED (completed by user):
      python -m gfl2.stat_ocr --build --images "single/*.png"
      Templates now include inner_blobs data.

   ADDITIONAL FIXES APPLIED (subsequent session, June 2026):
      - inner-blob pre-filter threshold raised to >=2 (was >0): single-loop digits
        (0,4,6,9) at NORM_W_VAL=8 unreliably show 1 hole; only 2 holes are
        categorical (identifies '8').
      - Single-candidate shortcut: when pre-filter narrows to one template and
        score ≥ PROJ_VERY_LOW, return it — prevents '8' falling to broken Hu.
      - v_primary mode for _reconstruct_pct: if v-projection alone scores ≥
        PROJ_CORR_MIN with gap ≥ 0.15, trust it over combined (fixes '3'→'2').
      - Clear-winner shortcut: combined ≥ 0.55 AND gap ≥ 0.10 → return best_c
        before Hu tiebreaker.  Fixes val '0' (combined ≈ 0.58–0.67, Hu broken).
      - _find_percent_x_start: aspect-ratio guard (w ≥ h*0.90) for merged '%'
        blobs narrower than PCT_MERGED_W=18 (fixes pct '04'→'0').
      - _reconstruct_pct: result.strip('.') removes leading/trailing dot noise.
      - _read_line: val strip uses _filter_y_outliers(threshold=8) to remove
        top-edge pct-line fragments (cy=5, gap=9 from median=14).

   FINAL ACCURACY (ib_d_20260111.png, after all fixes + --build):
      pct  40/40  (100%)
      val  40/40  (100%)   ← all previously-failing cases now pass
