1.  Blank scores when using Tesseract after new-buff asset saves (Windows)

   STATUS: MITIGATED
   WORKAROUND: use --score-pipeline blob (now the default in main.py).
               The blob/Hu pipeline is Tesseract-free and is unaffected.
               (Briefly non-functional 2026-07-02 due to §16; fixed same day.)

   FIRST OBSERVED: Session processing gm_250818.png (June 2026).
   Rows 2, 3, 4, 8, 10 — every row whose PREVIOUS row triggered a
   buff_ocr._save_asset() call — produced blank score fields in the CSV.

   SYMPTOMS:
   - Score column empty in CSV for a repeatable subset of rows.
   - Affected rows are not random; they always follow a row where a new
     buff PNG was written to assets/buff/.
   - Not reproduced in the Linux sandbox — only on the user's Windows
     machine (Python 3.14, Tesseract from UB-Mannheim).

   CONFIRMATION VIA TRACE (GFL2_TRACE=1, gm_250818.png):
   - Clean rows:    _ocr_score ~0.154s (method 1 succeeds).
   - Affected rows: _ocr_score ~0.303s (method 1 fails, method 2
     also attempted and also fails).
   - The 0.303s rows correspond exactly to rows immediately following a
     new-buff asset save in the previous row.

   ASSUMPTIONS / DEDUCTIONS:
   - Writing a PNG file to assets/buff/ via cv2.imwrite() on Windows
     triggers filesystem activity (NTFS journal, antivirus scan, or
     page-cache pressure) that degrades Tesseract's ability to write
     or read its own temp files for the next OCR call.
   - The contamination is cross-row: row N's asset save affects row
     N+1's score OCR, not row N's own score (already computed at that
     point).
   - Both OCR methods (image_to_string and image_to_data) fail, ruling
     out a PSM-mode-specific issue.

   ATTEMPTS TO RESOLVE:
   a. Move _ocr_score before buff_ocr.translate in _parse_row.
      Result: FAILED. The contamination is cross-row (row N affects N+1),
      not within the same row.

   b. Batch ALL score and owner-name OCR calls before any buff_ocr calls
      in parse() — current implementation.
      Result: CONFIRMED CORRECT IN THEORY. Works in sandbox. Still failing
      on Windows; suspected cause: stale .pyc loading the old unbatched
      code despite compile_gfl2.py being run.

   MITIGATION (implemented):
   - Blob/Hu moment pipeline added to score_detect.py.
   - make_score_fn() factory exposes it for use in weekly_gunsmoke.parse().
   - --score-pipeline blob is now the default in main.py.
   - Benchmark on 10-crop ambiguity-ranked test set: 100% accuracy,
     ~4ms/row vs ~200ms/row for Tesseract.
   - Templates stored in assets/fonts/score_digits.py; rebuild with
     python debugs/score_detect.py --build.

   ROOT CAUSE: Not fully diagnosed. Tesseract on Windows appears to share
   some process-level state (temp file handles, page-cache) with
   concurrent filesystem writes. The blob pipeline avoids Tesseract
   entirely for score extraction, bypassing the issue.

   REMAINING OPEN WORK (if root cause diagnosis is desired):
   - Check whether TESSDATA_PREFIX or TMP is set to a network/NTFS path.
   - Try setting TMPDIR/TMP/TEMP to a local path before running main.py.
   - Try pytesseract with timeout parameter to rule out silent hangs.
   - Print raw pytesseract return value in trace to distinguish "empty
     string" from "garbage that failed digit regex".

5.  populate_doll_assets: single-panel images incorrectly split

   STATUS: RESOLVED

   FIRST OBSERVED: fb_d_060518.png and ~10 other fb_d_ files.

   SYMPTOM: Files parsed as 0 frames / 0 assets. Debug showed two
   panels: 380×997 and 760×997 — an unequal split of a 1140px-wide
   single-panel image.

   ROOT CAUSE: _split_panels() in daily_gunsmoke.py searched for the
   brightest column within the middle third of the top bar. A bright UI
   separator inside a single-panel layout (at x≈380, i.e. 33% of width)
   fell inside the old guard range (0.2–0.8) and triggered a spurious
   split. The resulting 380px sub-panel had SEARCH_X1=0.15 → 57px search
   width, which clipped the ~90px portrait frames below the 0.70
   squareness threshold.

   FIX:
   - _split_panels() guard tightened from 0.2–0.8 to 0.4–0.6. A genuine
     2-panel layout always splits ≈50/50; any split outside 40–60% is now
     treated as a single panel.
   - SEARCH_X1 raised from 0.15 to 0.25 as belt-and-suspenders for
     any panels narrower than the calibration image.

15. NORM_W_PCT×NORM_H_PCT resize introduces within-class feature variation

   STATUS: OPEN / Accepted for projection classifier; impacts FFT+Gabor exploration.
           Padded-normalize fix IN PROGRESS — promising, not yet concluded
           (see EXPLORATION ATTEMPT below for what's left before it can replace
           the direct-stretch pipeline).

   Each digit blob is cropped to its tight bounding box and then resized to
   NORM_W_PCT×NORM_H_PCT (12×20).  Because original blob dimensions vary
   (e.g. '1' is ~5 px wide, '0' is ~11 px wide), the resize applies different
   horizontal stretch factors per digit instance.  This causes two problems:

   (a) Aspect-ratio distortion: the same character at different original widths
       maps to 12 px with different amounts of horizontal squash, creating
       within-class variation in any feature that is sensitive to stroke width
       or spatial frequency (FFT histogram, Gabor orientation fractions).

   (b) Boundary bleed: the tight bounding box occasionally includes 1-2 px of
       an adjacent stroke (from a neighbouring digit or the '.' separator).
       After resize to 12 px wide, those boundary pixels occupy a proportionally
       larger area, polluting the feature with foreign structure.

   OBSERVED IMPACT: After switching the FFT+Gabor debug pipeline from grayscale
   to binarized crops (matching stat_ocr runtime input), the '6' and '9' Gabor
   orientation fractions became nearly identical:
      '6': 0.327 / 0.236 / 0.244 / 0.193
      '9': 0.327 / 0.241 / 0.236 / 0.196
   The variation previously visible in grayscale was partly an artifact of
   smooth-edge interpolation masking the resize distortion.

   IDEA TO RESOLVE: Before classification, pad the tight-crop blob to a fixed
   aspect ratio (e.g. centre it in a blank canvas of MAX_W×NORM_H_PCT) before
   resizing.  This eliminates stretch variation without changing the target
   dimensions.  Applies to both the existing projection classifier and any
   future FFT/Gabor pipeline.

   NOTE: The projection classifier tolerates this variation because projection
   correlation is a 1D operation — horizontal distortion of a vertical
   projection does not change the column-sum profile significantly.  FFT and
   Gabor features operate in 2D and are more sensitive to this distortion.

   EXPLORATION ATTEMPT (July 2026) — result so far: encouraging, not conclusive.

   Tried the "pad, don't stretch" idea above: normalize by scaling each glyph
   crop to a fixed height (locking the aspect ratio) then centring it in the
   target NORM_W×NORM_H canvas with zero-padding on both sides, instead of
   directly cv2.resize()-ing to the fixed box.  Implemented as a full
   duplicate of gfl2/stat_ocr.py (originally debugs/stat_ocr_padded.py, own
   template files stat_pct_padded.py/stat_val_padded.py, own test file
   originally tests/test_stat_ocr_padded_explore.py) so the production
   pipeline and its 830-test baseline were never at risk during the
   experiment.  Later promoted to gfl2/stat_ocr_padded.py /
   tests/test_stat_ocr_padded.py — see decision 47's addendum in
   docs/decisions.txt.

   RESULT: rebuilt templates from single/*.png (3129/3250 cells), then ran
   the SAME ground truth (tests/inputs/daily/stat.json) through both engines:
      production (direct-stretch)        781/781 passed (100%)
      padded (aspect-preserving)          754/776 passed (97.2%), 22 failed
   Given this is a first pass with no threshold re-tuning at all, landing
   within 2.8% of production parity is a strong signal the approach is
   fundamentally sound — the remaining gap looks narrow and fixable rather
   than structural (see ROOT CAUSE below).

   ORIGINAL (WRONG) ROOT-CAUSE HYPOTHESIS: 19 of the 22 failures looked like
   the same confusion — every '3' in the val line misclassified as '2'
   (e.g. '383'→'283', '337'→'227', '330'→'220') — and were attributed to the
   padded canvas's 1-2px centring shift at NORM_W_VAL=8 making '3' and '2'
   project more alike than the direct-stretch representation did.

   UPDATE (2026-07-01): the held-out image set was refreshed for
   docs/action_items.txt #1 (tests/inputs/daily/stat.json replaced by
   tests/inputs/daily/stat_data.py).  The same apparent '3'→'2' confusion
   reappeared on a newly-added image (ib_d_20260114.png), which read at the
   time as confirmation the hypothesis was a property of the padded canvas
   rather than an artifact of the old sample.  It was not re-examined at the
   pixel level at that point — see RESOLUTION below for why that mattered.

   RESOLUTION (2026-07-03) — the hypothesis above was BACKWARDS:

   Checking the actual source-image pixels for all 13 flagged cells (via
   upscaled crop renders, not just OCR output) showed every one of them
   reads '2' in the screenshot, not '3'.  stat_data.py's ground truth
   ('337', '383', '394', ...) was simply wrong — generated by
   tests/generate_stat_inputs.py's "full pipeline" (blob, then Tesseract
   fallback only if blob returns '?'), which never triggers the Tesseract
   fallback when blob confidently (but wrongly) answers '3'.  The padded
   pipeline's '2' answer was correct all along; the "confusion" test was
   really a bad-ground-truth detector.

   Worse: PRODUCTION (gfl2/stat_ocr.py, direct-stretch, the pipeline
   main.py actually ships) was independently confirmed to make the exact
   same misread on the exact same crops — it was invisible only because the
   corrupted ground truth agreed with it.  Root cause: --build's Tesseract
   labelling step (_tess_label, PSM 6/4) misreads this specific glyph
   rendering as '3' widely enough across single/*.png (87 training images,
   not just the 16-image held-out set) that the '3' template itself is
   built partly from '2'-shaped samples.  Neither digit has an enclosed
   hole, so the existing inner-blob hole-count filter (§9) can't separate
   them, and on the confirmed-bad sample the combined score was '3'=0.750
   vs '2'=0.726 — a contamination-sized gap, not a decisive one.

   FIX APPLIED:
   - stat_gt_overrides.json extended with 13 corrected val labels (12 in
     the 16-image held-out set's tests/inputs/daily/stat_data.py, one more
     surfaced only via a post-fix regression check on the wider corpus —
     see AUDIT below).  gfl2/stat_ocr.py's and gfl2/stat_ocr_padded.py's
     --build paths now apply stat_gt_overrides.json before training
     (previously only --verify did this — a real gap, since it meant a
     known-bad Tesseract label could contaminate the template forever,
     surviving any number of future --build reruns).
   - Rebuilding templates with the corrected labels alone did NOT fix
     production's classification of the affected cells (confirmed: still
     0/11 correct) — the mislabeled Tesseract samples are common enough in
     the 87-image training corpus that correcting a dozen instances barely
     moves a template built from 1000+ samples per digit.
   - Added a categorical 2-vs-3 discriminator to _classify() in both
     gfl2/stat_ocr.py and gfl2/stat_ocr_padded.py (same insertion point
     as the §9 hole-count pre-filter): '2' always ends in a full-width flat
     bottom stroke, '3' always curls inward at the bottom.  Measured
     directly on confirmed samples: '2' bottom-row width = 0.875 of
     NORM_W_VAL, '3' <= 0.625 — a clean gap.  See _bottom_row_width_frac()
     and TWO_BOTTOM_FULL_MIN=0.80 / THREE_BOTTOM_CURL_MAX=0.70.  This fixed
     all 11 originally-flagged col2 cells (11/11) with zero regressions
     confirmed across 8 genuine-'3' samples, 184 pct-line 2/3 samples, and
     the full 1301-test suite.

   AUDIT PERFORMED: every val entry in stat_data.py containing digit '3' at
   any position (195 entries) was cross-checked; the systematic misread was
   confirmed confined to col2 (Stability) 3-digit and 2-digit values — 13
   entries total needed correction, 8 candidate "not flagged" col2 entries
   were visually confirmed as genuine '3's (no further corruption).  One of
   the 13 (gm_d_20250908.png p2_r3_col2, '33'→'32') was found only by the
   post-fix full-suite regression run, not the manual pixel audit — a
   reminder that eyeballing crops is fallible where the discriminator's
   categorical measurement is not.

   tests/test_stat_ocr_padded.py's _KNOWN_FAILING set now contains
   only the 2 genuinely-unrelated col4 cells whose stored ground truth is
   itself '?' (full pipeline could not resolve them either) — seeing a
   concrete digit there instead of a literal '?' is expected, not a defect.

   The broader §15 topic (resize-vs-pad normalization, FFT/Gabor 2D-feature
   sensitivity) remains OPEN/exploratory as before — this resolution only
   closes the specific '2'/'3' val-line finding that had been attributed to
   it.  gfl2/stat_ocr_padded.py and tests/test_stat_ocr_padded.py were later
   promoted from debugs/ to gfl2/ so the padded pipeline can be selected at
   runtime via `main.py --stat-ocr-engine padded` (see docs/decisions.txt
   decision 47's addendum) — production remains the default; this did not
   change the parity/no-promotion-of-default finding above.

   HEAD-TO-HEAD BENCHMARK (2026-07-03) — closes the "measure timing, not yet

14. stat_ocr: Hu moment tiebreaker should be disabled

   STATUS: OPEN

   OBSERVED: Timing reports show 117 val and 20 pct genuine Hu fallback calls
   per ~3300-cell run (after the logging bug fix in §_read_line that was
   previously inflating the count to 3296×).

   PROBLEM: The Hu tiebreaker is reached only when projection confidence falls
   below PROJ_CORR_MIN — the genuinely hard, ambiguous cases.  Hu moments have
   been shown during classifier development to be unreliable on exactly these
   cases (training data showed misclassifications that Hu made worse, not better).
   Keeping it risks silently wrong answers on ~137 cells per run.

   IDEA TO RESOLVE: In _classify(), replace the Phase 3 block with a plain
   return '?' when projection cannot reach PROJ_CORR_MIN.  The caller already
   handles '?' via Tesseract fallback for val, and the pct fallback chain.
   This makes the uncertainty explicit rather than masking it with an unreliable
   tiebreaker.

   BLOCKED ON: Validation cost.  Removing Hu will definitively increase Tesseract
   fallback count (those 137 cells currently get an answer from Hu; returning '?'
   instead routes them all to Tesseract).  Whether that is a net improvement
   depends on whether Hu's answers are more or less correct than Tesseract's —
   and Tesseract is not 100% reliable either, making ground-truth comparison
   time-consuming.


11. daily_gunsmoke: top-bottom panel stacking not supported

   STATUS: OPEN / Not yet observed in the wild

   The current panel-discovery logic (_find_all_frames + _group_frames_into_panels)
   clusters portrait frames by x-proximity, which correctly handles left-right
   side-by-side panels.  If a future screenshot stacks two reports vertically
   (top panel / bottom panel), the frames from both panels would share nearly
   the same x and be merged into one group, producing a single malformed report
   instead of two separate ones.

   IDEA TO RESOLVE: After x-clustering, check whether a group's y-span exceeds
   ~1.5× the expected 5-row height.  If so, split the group at the y-gap between
   rows 5 and 6 (the expected inter-panel gap would be larger than inter-row gaps).

13. Panel bounds computed from frame positions instead of brightness midpoint

   STATUS: RESOLVED (June 2026)

   FIRST OBSERVED: All single/gm_d_*.png images — 76 scores and 150 stats
   cells fell back to Tesseract.  Crops revealed the header OCR was reading
   empty dark regions, not the actual stat text.

   ROOT CAUSE: Commit 7649766 replaced _split_panels() (brightness-based
   midpoint) with _panel_bounds_from_groups(), which computed the x split
   as the midpoint between the leftmost portrait frame x-positions of adjacent
   groups.  Portrait frames sit at the LEFT EDGE of each panel, so the

   slice started at the wrong x, shifting all header/stats crops into dead
   background area.

   FIX: Restored _split_panels() for panel image slicing (correct bounds).
   Frame-based detection (_find_all_frames + _group_frames_into_panels) is
   retained for producing per-panel frame lists (passed to _extract_header and
   _extract_doll_rows), with frame coordinates translated to panel-local origin.
   This gives both correct panel slices and correct frame positions.

   DETECTION: test_daily_gunsmoke.py (added this session) would have caught
   this regression immediately had it existed before commit 7649766.
