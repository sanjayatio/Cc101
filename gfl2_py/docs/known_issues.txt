1.  Blank scores when using Tesseract after new-buff asset saves (Windows)

   STATUS: MITIGATED
   SCOPE: MAIN
   WORKAROUND: use --score-pipeline blob (now the default in main.py).
               The blob/Hu pipeline is Tesseract-free and is unaffected.
               (Briefly non-functional 2026-07-02 due to §16; fixed same day.)

   FIRST OBSERVED: Session processing gm_250818.png (June 2026).
   Rows 2, 3, 4, 8, 10 — every row whose PREVIOUS row triggered a
   buff_ocr._save_asset() call — produced blank score fields in the CSV.

   SYMPTOMS:
   - Score column empty in CSV for a repeatable subset of rows.
   - Affected rows are not random; they always follow a row where a new
     buff PNG was written to assets/buff/.
   - Not reproduced in the Linux sandbox — only on the user's Windows
     machine (Python 3.14, Tesseract from UB-Mannheim).

   CONFIRMATION VIA TRACE (GFL2_TRACE=1, gm_250818.png):
   - Clean rows:    _ocr_score ~0.154s (method 1 succeeds).
   - Affected rows: _ocr_score ~0.303s (method 1 fails, method 2
     also attempted and also fails).
   - The 0.303s rows correspond exactly to rows immediately following a
     new-buff asset save in the previous row.

   ASSUMPTIONS / DEDUCTIONS:
   - Writing a PNG file to assets/buff/ via cv2.imwrite() on Windows
     triggers filesystem activity (NTFS journal, antivirus scan, or
     page-cache pressure) that degrades Tesseract's ability to write
     or read its own temp files for the next OCR call.
   - The contamination is cross-row: row N's asset save affects row
     N+1's score OCR, not row N's own score (already computed at that
     point).
   - Both OCR methods (image_to_string and image_to_data) fail, ruling
     out a PSM-mode-specific issue.

   ATTEMPTS TO RESOLVE:
   a. Move _ocr_score before buff_ocr.translate in _parse_row.
      Result: FAILED. The contamination is cross-row (row N affects N+1),
      not within the same row.

   b. Batch ALL score and owner-name OCR calls before any buff_ocr calls
      in parse() — current implementation.
      Result: CONFIRMED CORRECT IN THEORY. Works in sandbox. Still failing
      on Windows; suspected cause: stale .pyc loading the old unbatched
      code despite compile_gfl2.py being run.

   MITIGATION (implemented):
   - Blob/Hu moment pipeline added to score_detect.py.
   - make_score_fn() factory exposes it for use in weekly_gunsmoke.parse().
   - --score-pipeline blob is now the default in main.py.
   - Benchmark on 10-crop ambiguity-ranked test set: 100% accuracy,
     ~4ms/row vs ~200ms/row for Tesseract.
   - Templates stored in assets/fonts/score_digits.py; rebuild with
     python debugs/score_detect.py --build.

   ROOT CAUSE: Not fully diagnosed. Tesseract on Windows appears to share
   some process-level state (temp file handles, page-cache) with
   concurrent filesystem writes. The blob pipeline avoids Tesseract
   entirely for score extraction, bypassing the issue.

   REMAINING OPEN WORK (if root cause diagnosis is desired):
   - Check whether TESSDATA_PREFIX or TMP is set to a network/NTFS path.
   - Try setting TMPDIR/TMP/TEMP to a local path before running main.py.
   - Try pytesseract with timeout parameter to rule out silent hangs.
   - Print raw pytesseract return value in trace to distinguish "empty
     string" from "garbage that failed digit regex".

5.  populate_doll_assets: single-panel images incorrectly split

   STATUS: RESOLVED
   SCOPE: MAIN

   FIRST OBSERVED: fb_d_060518.png and ~10 other fb_d_ files.

   SYMPTOM: Files parsed as 0 frames / 0 assets. Debug showed two
   panels: 380×997 and 760×997 — an unequal split of a 1140px-wide
   single-panel image.

   ROOT CAUSE: _split_panels() in daily_gunsmoke.py searched for the
   brightest column within the middle third of the top bar. A bright UI
   separator inside a single-panel layout (at x≈380, i.e. 33% of width)
   fell inside the old guard range (0.2–0.8) and triggered a spurious
   split. The resulting 380px sub-panel had SEARCH_X1=0.15 → 57px search
   width, which clipped the ~90px portrait frames below the 0.70
   squareness threshold.

   FIX:
   - _split_panels() guard tightened from 0.2–0.8 to 0.4–0.6. A genuine
     2-panel layout always splits ≈50/50; any split outside 40–60% is now
     treated as a single panel.
   - SEARCH_X1 raised from 0.15 to 0.25 as belt-and-suspenders for
     any panels narrower than the calibration image.


4.  Blob pipeline: '4'/'2' projection ambiguity (score pipeline)

   STATUS: RESOLVED (June 2026 — 12/12 test_score_pipeline.py pass)
   SCOPE: MAIN

   FIRST OBSERVED: gm_250818_10 (score 3745 → detected as 3725).

   SYMPTOM: The '4' digit in position 3 of score "3745" had a
   1D projection correlation of 0.958 for '2' and 0.951 for '4' —
   a gap of only 0.007. The pipeline returned '2' (wrong).

   ROOT CAUSE: The '4' template average was built from multiple
   screenshots at different resolutions (142px and 165px wide score
   crops). The normalized 20×30px representation averaged slightly
   differently across sizes, reducing template fidelity for this digit.

   RESOLUTION: Better '4' samples in the template library (more diverse
   resolution mix) closed the gap. 100% accuracy confirmed on the full
   test set (test_score_pipeline.py: 12 pass, 14 skipped for missing crops).
   No code change required.

   NOTE: The analogous '4'/'2' ambiguity in stat_ocr.py (Daily Gunsmoke
   stat cells) was also resolved by adding horizontal projection; see §6.

   IF RECURRENCE: Add more '4' samples via score_detect.py --build.

   ORIGINAL SYMPTOM: stats_row/blob fires on 162/162 crops but 111/162 still

   - HDR_THRESH=155 (down from 180): separates '4' and '8' blobs that merged.
   - HDR_BLOB_MIN_H=12: excludes comma-separator noise blobs (h≈5-10 px).

   - _reconstruct_val safety net: if 'M' somehow misclassifies back to '?',

15. NORM_W_PCT×NORM_H_PCT resize introduces within-class feature variation

   STATUS: OPEN / Accepted for projection classifier; impacts FFT+Gabor exploration.
   SCOPE: MIXED -- see note below (the resize/padding root cause affects production's projection classifier AND the promoted padded pipeline [MAIN]; most of this entry's later exploration -- Gabor calibration, paren/ring/loop/vstroke/hbar, wedge, the two-agent classifier -- only ever affected gfl2/stat_ocr_fft.py [EXPLORE])
           Padded-normalize fix IN PROGRESS — promising, not yet concluded
           (see EXPLORATION ATTEMPT below for what's left before it can replace
           the direct-stretch pipeline).

   Each digit blob is cropped to its tight bounding box and then resized to
   NORM_W_PCT×NORM_H_PCT (12×20).  Because original blob dimensions vary
   (e.g. '1' is ~5 px wide, '0' is ~11 px wide), the resize applies different
   horizontal stretch factors per digit instance.  This causes two problems:

   (a) Aspect-ratio distortion: the same character at different original widths
       maps to 12 px with different amounts of horizontal squash, creating
       within-class variation in any feature that is sensitive to stroke width
       or spatial frequency (FFT histogram, Gabor orientation fractions).

   (b) Boundary bleed: the tight bounding box occasionally includes 1-2 px of
       an adjacent stroke (from a neighbouring digit or the '.' separator).
       After resize to 12 px wide, those boundary pixels occupy a proportionally
       larger area, polluting the feature with foreign structure.

   OBSERVED IMPACT: After switching the FFT+Gabor debug pipeline from grayscale
   to binarized crops (matching stat_ocr runtime input), the '6' and '9' Gabor
   orientation fractions became nearly identical:
      '6': 0.327 / 0.236 / 0.244 / 0.193
      '9': 0.327 / 0.241 / 0.236 / 0.196
   The variation previously visible in grayscale was partly an artifact of
   smooth-edge interpolation masking the resize distortion.

   IDEA TO RESOLVE: Before classification, pad the tight-crop blob to a fixed
   aspect ratio (e.g. centre it in a blank canvas of MAX_W×NORM_H_PCT) before
   resizing.  This eliminates stretch variation without changing the target
   dimensions.  Applies to both the existing projection classifier and any
   future FFT/Gabor pipeline.

   NOTE: The projection classifier tolerates this variation because projection
   correlation is a 1D operation — horizontal distortion of a vertical
   projection does not change the column-sum profile significantly.  FFT and
   Gabor features operate in 2D and are more sensitive to this distortion.

   EXPLORATION ATTEMPT (July 2026) — result so far: encouraging, not conclusive.

   Tried the "pad, don't stretch" idea above: normalize by scaling each glyph
   crop to a fixed height (locking the aspect ratio) then centring it in the
   target NORM_W×NORM_H canvas with zero-padding on both sides, instead of
   directly cv2.resize()-ing to the fixed box.  Implemented as a full
   duplicate of gfl2/stat_ocr.py (originally debugs/stat_ocr_padded.py, own
   template files stat_pct_padded.py/stat_val_padded.py, own test file
   originally tests/test_stat_ocr_padded_explore.py) so the production
   pipeline and its 830-test baseline were never at risk during the
   experiment.  Later promoted to gfl2/stat_ocr_padded.py /
   tests/test_stat_ocr_padded.py — see decision 47's addendum in
   docs/decisions.txt.

   RESULT: rebuilt templates from single/*.png (3129/3250 cells), then ran
   the SAME ground truth (tests/inputs/daily/stat.json) through both engines:
      production (direct-stretch)        781/781 passed (100%)
      padded (aspect-preserving)          754/776 passed (97.2%), 22 failed
   Given this is a first pass with no threshold re-tuning at all, landing
   within 2.8% of production parity is a strong signal the approach is
   fundamentally sound — the remaining gap looks narrow and fixable rather
   than structural (see ROOT CAUSE below).

   ORIGINAL (WRONG) ROOT-CAUSE HYPOTHESIS: 19 of the 22 failures looked like
   the same confusion — every '3' in the val line misclassified as '2'
   (e.g. '383'→'283', '337'→'227', '330'→'220') — and were attributed to the
   padded canvas's 1-2px centring shift at NORM_W_VAL=8 making '3' and '2'
   project more alike than the direct-stretch representation did.

   UPDATE (2026-07-01): the held-out image set was refreshed for
   docs/action_items.txt #1 (tests/inputs/daily/stat.json replaced by
   tests/inputs/daily/stat_data.py).  The same apparent '3'→'2' confusion
   reappeared on a newly-added image (ib_d_20260114.png), which read at the
   time as confirmation the hypothesis was a property of the padded canvas
   rather than an artifact of the old sample.  It was not re-examined at the
   pixel level at that point — see RESOLUTION below for why that mattered.

   RESOLUTION (2026-07-03) — the hypothesis above was BACKWARDS:

   Checking the actual source-image pixels for all 13 flagged cells (via
   upscaled crop renders, not just OCR output) showed every one of them
   reads '2' in the screenshot, not '3'.  stat_data.py's ground truth
   ('337', '383', '394', ...) was simply wrong — generated by
   tests/generate_stat_inputs.py's "full pipeline" (blob, then Tesseract
   fallback only if blob returns '?'), which never triggers the Tesseract
   fallback when blob confidently (but wrongly) answers '3'.  The padded
   pipeline's '2' answer was correct all along; the "confusion" test was
   really a bad-ground-truth detector.

   Worse: PRODUCTION (gfl2/stat_ocr.py, direct-stretch, the pipeline
   main.py actually ships) was independently confirmed to make the exact
   same misread on the exact same crops — it was invisible only because the
   corrupted ground truth agreed with it.  Root cause: --build's Tesseract
   labelling step (_tess_label, PSM 6/4) misreads this specific glyph
   rendering as '3' widely enough across single/*.png (87 training images,
   not just the 16-image held-out set) that the '3' template itself is
   built partly from '2'-shaped samples.  Neither digit has an enclosed
   hole, so the existing inner-blob hole-count filter (§9) can't separate
   them, and on the confirmed-bad sample the combined score was '3'=0.750
   vs '2'=0.726 — a contamination-sized gap, not a decisive one.

   FIX APPLIED:
   - stat_gt_overrides.json extended with 13 corrected val labels (12 in
     the 16-image held-out set's tests/inputs/daily/stat_data.py, one more
     surfaced only via a post-fix regression check on the wider corpus —
     see AUDIT below).  gfl2/stat_ocr.py's and gfl2/stat_ocr_padded.py's
     --build paths now apply stat_gt_overrides.json before training
     (previously only --verify did this — a real gap, since it meant a
     known-bad Tesseract label could contaminate the template forever,
     surviving any number of future --build reruns).
   - Rebuilding templates with the corrected labels alone did NOT fix
     production's classification of the affected cells (confirmed: still
     0/11 correct) — the mislabeled Tesseract samples are common enough in
     the 87-image training corpus that correcting a dozen instances barely
     moves a template built from 1000+ samples per digit.
   - Added a categorical 2-vs-3 discriminator to _classify() in both
     gfl2/stat_ocr.py and gfl2/stat_ocr_padded.py (same insertion point
     as the §9 hole-count pre-filter): '2' always ends in a full-width flat
     bottom stroke, '3' always curls inward at the bottom.  Measured
     directly on confirmed samples: '2' bottom-row width = 0.875 of
     NORM_W_VAL, '3' <= 0.625 — a clean gap.  See _bottom_row_width_frac()
     and TWO_BOTTOM_FULL_MIN=0.80 / THREE_BOTTOM_CURL_MAX=0.70.  This fixed
     all 11 originally-flagged col2 cells (11/11) with zero regressions
     confirmed across 8 genuine-'3' samples, 184 pct-line 2/3 samples, and
     the full 1301-test suite.

   AUDIT PERFORMED: every val entry in stat_data.py containing digit '3' at
   any position (195 entries) was cross-checked; the systematic misread was
   confirmed confined to col2 (Stability) 3-digit and 2-digit values — 13
   entries total needed correction, 8 candidate "not flagged" col2 entries
   were visually confirmed as genuine '3's (no further corruption).  One of
   the 13 (gm_d_20250908.png p2_r3_col2, '33'→'32') was found only by the
   post-fix full-suite regression run, not the manual pixel audit — a
   reminder that eyeballing crops is fallible where the discriminator's
   categorical measurement is not.

   tests/test_stat_ocr_padded.py's _KNOWN_FAILING set now contains
   only the 2 genuinely-unrelated col4 cells whose stored ground truth is
   itself '?' (full pipeline could not resolve them either) — seeing a
   concrete digit there instead of a literal '?' is expected, not a defect.

   The broader §15 topic (resize-vs-pad normalization, FFT/Gabor 2D-feature
   sensitivity) remains OPEN/exploratory as before — this resolution only
   closes the specific '2'/'3' val-line finding that had been attributed to
   it.  gfl2/stat_ocr_padded.py and tests/test_stat_ocr_padded.py were later
   promoted from debugs/ to gfl2/ so the padded pipeline can be selected at

   WEDGE FILTER TRIED (2026-07-04) — the candidate idea from the paragraph
   above, implemented as a classic Fourier "ring/wedge" texture feature:
   debug_pct_classify.py's compute_features() now also sums the 2D FFT
   magnitude spectrum (DC excluded) into 8 angular sectors over [0°,180°)
   (folded there because a real image's magnitude spectrum is
   centrosymmetric, |F(u,v)|==|F(-u,-v)|) and appends the 8 sector
   fractions to the feature vector (68 -> 76 dims).  pct_fft_predict.py's
   _extract_pct_digit_glyphs() and debug_pct_classify.py's compute_features
   are the only feature-producing call sites, so both picked it up
   automatically.  Added a per-digit accuracy/confusion printout to
   pct_fft_predict.py (previously only aggregate accuracy was reported) to
   actually measure the effect on '6' vs '9' rather than eyeballing feature
   means.

   BEFORE TRUSTING THE FEATURE: checked whether a wedge filter could even
   work in principle.  For any real-valued image f, its exact 180°-rotation
   g(x,y)=f(-x,-y) has FFT G(u,v)=F(-u,-v); by the Hermitian symmetry of
   real signals, F(-u,-v)=conj(F(u,v)), so |G(u,v)|==|F(u,v)| at every
   frequency bin -- the magnitude spectrum of a 180°-rotated image is
   IDENTICAL to the original's, not merely similar.  If '9' renders as an
   exact 180° rotation of '6' in this font, no feature built purely from
   FFT magnitude -- wedge-binned or the existing 64-bin histogram -- can
   distinguish them even in principle.  Printing the raw per-digit wedge
   fractions confirmed this in practice: '6' and '9' differ by <=0.02 in
   every one of the 8 sectors (e.g. 0.106 vs 0.113, 0.251 vs 0.232), the
   same order of noise as the earlier Gabor near-collision, versus >0.1
   gaps between genuinely distinct digits (e.g. '1' vs '0' at 0°: 0.336 vs
   0.148).  Any non-zero gap at all comes only from real-world imperfection
   in the rotation (cropping, anti-aliasing), not from a real shape
   difference the feature can exploit.

   PAREN + RING FEATURES ADDED (2026-07-04) -- BREAKS THE '6'/'9' COLLISION.
   Two new feature blocks, proposed as a direct response to this section's
   own conclusion that resolving '6'/'9' needs something spatially local and
   chirality-sensitive rather than another global FFT-magnitude aggregate:

   1. PAREN: a whole-glyph normalized-cross-correlation against two
      hand-drawn curve templates, '(' (bulges left) and ')' (bulges right,
      its mirror image) — see gfl2/stat_ocr_fft.py's _paren_templates().

      itself, so this is NOT subject to the Hermitian-symmetry proof that

   PER-ORIENTATION GABOR F-RATIO: A MEASUREMENT THAT LOOKED STRONG BUT
   WASN'T -- asked whether 135deg(\) could be dropped as "not obviously
   useful" (only 45deg(/) seemed clearly valuable).  First check: standalone
   per-dimension F-ratio measured 0deg=3.88, 45deg=5.41, 90deg=2.24,
   135deg=5.03 -- 135deg looked like the SECOND-strongest of the four, and
   was initially kept on that basis.  That was wrong.  The 4 Gabor fractions
   are computed to sum to 1 (each is `resp[i] / sum(resp)`), so they are NOT
   independent measurements -- a high standalone F-ratio for one bin can be
   nothing more than a mechanical echo of another bin (0deg, dominated by
   the near-pure-vertical strokes of '1'/'7') absorbing less share, rather
   than 135deg carrying real, independent discriminative information.
   Confirmed by looking at the actual per-digit means (8493 training
   glyphs): 135deg is lowest for '1' (0.110) and '7' (0.108) and highest
   for loop-heavy '3'/'6'/'8'/'9' (~0.19-0.21) -- a real, physically
   explicable pattern (a closed curve's tangent sweeps through every
   orientation as you trace it, so curvier digits accumulate more
   incidental 135deg-oriented content than straight-stroke digits do) but
   NOT evidence that 135deg is independently useful for classification once
   the other 3 orientations already exist.

   The decisive check was a MARGINAL-UTILITY ablation, not another
   standalone F-ratio: gabor{0,45,90} (3d) vs gabor{0,45,90,135} (4d),
   held-out set, nothing else in the feature vector.  Adding 135deg back
   made '9' recognition WORSE (55/188 -> 46/188 correct) while leaving '7'
   unchanged and only marginally helping '1' (324/345 -> 345/345, already
   near-perfect via 0deg alone) -- the opposite of what "second-strongest
   orientation" implied.  Re-tested inside the FULL active feature set
   (hist+gabor+paren+ring): there, keeping vs dropping 135deg is close to a
   wash (99.2% vs 99.7% accuracy, '6' identical 117/142, '9' 153/188 vs
   154/188) -- paren has already captured most of the '6'/'9' signal, so
   135deg's earlier-measured harm mostly disappears, but it adds no real
   value either.  DECISION: dropped 135deg (N_ORIENT 4->3, kernels built
   for i in range(3) over the same 45deg step so 0/45/90deg are unchanged)
   for a simpler, slightly cheaper vector rather than kept on a misleading
   metric.  See docs/takeaways.txt for the general lesson this produced.

   TWO-AGENT CLASSIFIER (2026-07-04) -- BY FAR THE BEST RESULT IN THIS
   EXPLORATION.  Prompted by a direct question: since the histogram measures
   something fundamentally different from gabor/paren/ring (a global
   magnitude-value distribution vs. oriented/shape/radial-frequency
   content), why should combining them as ONE feature vector cause either
   to hurt the other?  It shouldn't, and it didn't have to -- the earlier
   regression (full-vector z-normalization collapsing '6'/'9') was an
   artifact of the combination method (flat concatenation forced into one
   shared Euclidean distance), not a real conflict between the two feature
   types.

   Restructured _classify() into two independent agents instead of one
   nearest-centroid lookup over the full vector:
     Agent A (gpr): gabor+paren+ring (13d), unnormalized, its own margin
       gate (CONF_A_DEFAULT=0.15, the original threshold).
     Agent B (hist): the 64-bin histogram (64d), z-score normalized using
       ITS OWN training mean/std (not shared with A), its own INDEPENDENTLY
       tuned margin gate (CONF_B_DEFAULT=0.05).
     Dispute rule: try A first; if confident, use it (A is the strong
       classifier, ~97% standalone).  If A is unsure, ask B; if B is
       confident, use B.  If neither is confident, '?'.

   FIRST ATTEMPT AT COMBINING THEM WAS ALSO WRONG, INSTRUCTIVELY: initially
   reused Agent A's 0.15 threshold for Agent B too.  Result: B answered
   ZERO cases A didn't already answer (a perfect subset, 598 agreements + 3
   disputes = exactly B's standalone-confident count) -- looked like
   genuine redundancy.  It wasn't.  A and B's margins live in unrelated,
   differently-scaled distance spaces (13d raw vs 64d z-normalized); 0.15
   was simply miscalibrated for B.  Lowering CONF_B alone (not touching A
   at all) to 0.05 revealed B resolving 48 of the 61 cases A couldn't, at
   91.7% accuracy -- real, previously invisible complementary coverage.
   This is the same family of mistake as the Gabor-135 F-ratio lesson
   (docs/takeaways.txt #46), applied to margin thresholds instead of raw
   feature values: don't assume a threshold, hyperparameter, or scale
   tuned for one distribution transfers to a differently-shaped one --
   check independently.

   STANDALONE ABLATION (held-out glyphs, 71-train/16-held-out split):
      config                          answered   accuracy   '6'         '9'
      gabor+paren+ring alone (A only)   96.9%      97.5%    130/142(92%) 166/188(88%)

   GENERAL LESSON: when two feature blocks answer genuinely different
   questions about the same input, don't force them into one shared
   distance metric and hope normalization sorts it out -- let each be its
   own classifier with its own scale and its own independently-tuned
   confidence threshold, and combine only at the decision level (try the
   strong one first, consult the other only when unsure).  See
   docs/takeaways.txt for the generalized version of this lesson.

   PAIR TIEBREAK (2026-07-04, DISABLED BY DEFAULT -- opt-in) -- investigated
   the two-agent system's remaining error concentration: per-digit
   breakdown showed '4' carrying 23 of 52 total held-out errors, ALL
   misclassified as '7', never anything else.  Started from a structural
   hypothesis: '4' and '7' both fit '-'(gabor_90) and '/'(gabor_45) by
   construction (top bar + diagonal descender), so no line-based feature
   can ever cleanly separate them -- the vertical stroke ('|', gabor_0)
   that intuitively should distinguish them turned out to have the WORST
   4-vs-7 separability of all 13 Agent A dimensions (0.41, vs 2.66 for
   gabor_45 -- gabor_45 was independently confirmed NOT the culprit: it's
   below-average noise for both digits and one of the BETTER discriminators
   for this exact pair, the opposite of the original hunch).

   Traced the actual 23 error cases (not aggregate class statistics) via
   per-dimension contribution to the wrong-direction distance difference:
   paren_( dominates by >4x over every other dimension combined (-0.01325
   vs the next largest at -0.00044).  Cross-checked against the per-digit
   noise table: '4's within-class std for paren_( is 0.073 vs '7's 0.011 --
   6x larger than any other dimension for '4' specifically.  Some '4'
   renderings pick up much more '('-curve correlation than others (likely
   corner/serif rendering variance), and that instability is what
   occasionally tips borderline cases toward '7'.

   TWO DEAD ENDS BEFORE THE FIX THAT WORKED:
   1. Globally excluding paren_( from every comparison against the '4'
      centroid: fixes '4' completely (197/197) but makes '4' systematically
      closer to EVERY other centroid too (fewer dimensions to accumulate
      distance from mechanically shrinks apparent distance) -- opened a
      new, larger '9'->'4' confusion (26-40 cases depending on whether raw
      or RMS-normalized distance was used), net accuracy regression
      (96.6-97.3% vs 97.5% baseline).  '9' is the digit this whole
      exploration fought hardest to fix; this was not an acceptable trade.
   2. A universal "narrow candidates via the 3 line features first, then
      refine" cascade (direct test of "iterative filtering" as a general
      architecture): line-only top-3 recall is 97.5%, and top_k=3 did
      improve '4' (135->148 correct) and even '9' slightly (165->171) --
      but broke '3' (217->188 correct, 29 newly unresolved) and '0'
      (mildly, +5 more confused with '8').  Root cause confirmed a
      symmetry the digit groupings themselves predicted: '3' never
      appeared under any line feature in a manual '|'/'-'/'/' grouping
      exercise, only under "rings" -- a hard line-based cutoff will
      periodically exclude the correct candidate for digits whose real
      signal isn't in lines at all.  Confirms a UNIVERSAL cascade is a
      dead end: if arc content can leak into line-dominant glyphs (4, 7),
      line content leaks into arc-dominant ones (0, 3) just as easily.

   THE FIX: scope the override to trigger ONLY when the flat classifier's
   own top-2 nearest centroids are exactly {'4','7'} -- 219 of 1982
   held-out glyphs.  For those, and ONLY those, re-decide using the
   remaining 12 dims (excluding paren_().  Implemented as
   PAIR_TIEBREAK_RULES in gfl2/stat_ocr_fft.py: a dict from a frozenset
   pair to which dimension(s) to exclude, checked against Agent A's own
   top-2 before falling through to the normal confidence gate.

   RESULT: every digit OTHER than '4' is provably byte-for-byte identical
   to the flat baseline (the override never fires for them).  '4' improves
   from 135/197 correct (23 misclassified as '7', 39 unresolved) to
   188/197 (0 misclassified, 9 unresolved).  Overall held-out: answered
   96.9%->98.4%, accuracy 97.5%->98.7%.  Cell-level --build+--verify on the
   87-image corpus: 90.1% -> 93.2% pct accuracy, timing 1151us -> 1349us/
   cell (~17% slower -- every glyph now needs the top-2 candidate check,
   not just the margin-gated winner).

   committed): the first version normalized every heatmap/overlay
   independently PER CELL (per-glyph min-max for Gabor; a flat fixed

   GABOR_0 REMOVED, VRUN + LOOP_TOP/LOOP_BOT ADDED (2026-07-05) -- LARGE
   accuracy jump, with one new confusion pattern flagged but NOT
   root-caused.  Two independent threads from a review of the two-agent
   classifier's remaining weak dimensions:

   1. gabor_0 (vertical orientation) was checked against its assumed job
      (differentiate '4' from '7', since '4' allegedly has a vertical
      stroke and '7' doesn't).  Measured mean4=0.402 vs mean7=0.390 --
      statistically indistinguishable (d'=0.71, the worst of the three
      orientations, confirming the "opposite of the original hunch" finding
      already on record above).  A real pair-tiebreak test went further:
      excluding gabor_0 from the {'4','7'} reduced dimension set changed
      ZERO of 1069 real decisions -- not just weak, fully redundant.
      Root cause: Gabor's mean-abs-response is a diffuse, whole-image
      aggregate that cannot distinguish "one genuine unbroken thin stroke"
      from "some vertical-ish edge content somewhere in the glyph" (curve
      tangent points, corners, etc. all contribute equally).

      Replacement (_vrun_feature in gfl2/stat_ocr_fft.py): a spatial
      isolated-run detector.  For each pixel, compute the width of the
      horizontal foreground segment it belongs to (via a "distance since
      last background" cummax trick, applied left-to-right and right-to-
      left); a pixel only counts toward the vertical run if that segment
      width is <= MAX_STROKE_W.  The longest such run in any single column,
      normalized by height, is the feature.

      TWO CALIBRATION BUGS caught before this worked, both from the same
      root cause (a sentinel value that implicitly assumes a boundary
      exists where none does):
        a. Segment-width computation initially used a -1 "no background
           found" sentinel (matching the historical paren/loop template
           convention) -- this gives a solid-white 12x20 crop a "width" of
           ~1 near the image edges (a false free pass), so a totally
           degenerate all-foreground crop scored 1.0, identical to a real
           stroke.  Fixed with a -width sentinel: "no real background found
           in this row" now correctly reports a width far exceeding any
           real threshold, rejecting the degenerate case (0.000).
        b. The right-side run computation (mirroring left-to-right logic
           for right-to-left) initially mixed a POSITIONAL array index with
           a VALUE-remapped index (w-1-x) across the array reversal --
           produced silently wrong results, including NEGATIVE "widths",
           caught by a regression test on a hand-built 2px-wide bar (which
           should read width=2 but read -4/-6).  Fixed by applying the
           identical left-to-right function to the horizontally-reversed
           array, then flipping the result back -- no index remapping.
      Both bugs were caught by deliberately constructed synthetic
      edge cases (solid white, filled ellipse, outline ellipse, a hand-
      built thin bar) BEFORE trusting any corpus-wide number -- see
      debugs/ scratch methodology; worth the same discipline next time a
      "distance since X" vectorized trick is written.

      THRESHOLD CALIBRATION: an initial guess of MAX_STROKE_W=2 was found
      too tight AFTER the isolation logic was already correct -- it
      rejected nearly all of even '1's genuine stroke pixels (a digit that
      is unambiguously just a vertical line scored 0.05, not the highest of
      all ten digits the way it obviously should).  Measuring the corpus's
      OWN segment-width histogram for '1'/'4'/'7' showed a median width of
      4-5px, not 1-3px as guessed -- MAX_STROKE_W=6 was chosen from that
      measurement, not another guess.  At that threshold '1' correctly
      becomes the top scorer (mean=0.700, both direction and magnitude
      correct) while degenerate crops stay low (solid_white=0.000,
      filled/outline ellipse=0.050-0.200).  '4'-vs-'7' d'=-5.31, F-ratio
      14738 (vs gabor_0's 0.71) -- note '7' still scores HIGHER than '4'
      even at the correct threshold; this is NOT the same artifact as the
      threshold-too-tight case (confirmed by re-deriving it from properly
      calibrated, isolation-correct measurements) -- it appears to be a
      genuine property of this font (in this rendering, '7's descender
      reads as a longer isolated straight run than '4's vertical segment).

      An FFT/frequency-domain formulation was also tried and rejected, on
      CONFIDENCE grounds, not raw speed -- see the two-part investigation:
      a naive wall-clock comparison first (FFT loses when the transform
      cost is charged per-feature: 45us vs 17us at this glyph size), then
      re-run under the correct amortized-cost model (the transform is
      already paid for elsewhere in compute_features(), so only the
      marginal cost of reusing vs not reusing it should count).  Even
      giving FFT every benefit of the doubt: sharing the existing axis-0
      transform forces CIRCULAR convolution (no room to zero-pad without
      changing the transform size), and circular wraparound corrupts
      exactly the boundary information run-length depends on (best d'~1.4,
      capped by degenerate saturation).  A properly zero-padded (linear,
      non-circular) version matches spatial's confidence (d'~3.1) but
      needs its OWN separate transform, so it isn't actually free either.
      No configuration wins or ties at zero marginal cost -- spatial is the
      right call here regardless of how the transform-cost accounting is
      framed.

   2. paren_(/paren_) (this section's PAREN + RING FEATURES ADDED entry
      above) span the FULL glyph height, which is why they help '6' (clean
      '(' preference) but land near-neutral on '9' -- '9's loop only
      occupies the upper ~35% of the glyph, so a full-height arc dilutes
      against the tail below it.  A parameter sweep over the SAME kind of
      half-ellipse arc, varying centroid (cy) and radii (rx, ry) instead of
      the fixed full-height span, found a config that peaks cleanly on '9':
      cy=0.35h, ry=0.20h, rx=0.80w, side='open' -- mean=0.318 vs the next-
      highest competitor at 0.093 (gap 0.225), corpus-wide.  loop_bot is

14. stat_ocr: Hu moment tiebreaker should be disabled

   STATUS: OPEN
   SCOPE: MAIN

   OBSERVED: Timing reports show 117 val and 20 pct genuine Hu fallback calls
   per ~3300-cell run (after the logging bug fix in §_read_line that was
   previously inflating the count to 3296×).

   PROBLEM: The Hu tiebreaker is reached only when projection confidence falls
   below PROJ_CORR_MIN — the genuinely hard, ambiguous cases.  Hu moments have
   been shown during classifier development to be unreliable on exactly these
   cases (training data showed misclassifications that Hu made worse, not better).
   Keeping it risks silently wrong answers on ~137 cells per run.

   IDEA TO RESOLVE: In _classify(), replace the Phase 3 block with a plain
   return '?' when projection cannot reach PROJ_CORR_MIN.  The caller already
   handles '?' via Tesseract fallback for val, and the pct fallback chain.
   This makes the uncertainty explicit rather than masking it with an unreliable
   tiebreaker.

   BLOCKED ON: Validation cost.  Removing Hu will definitively increase Tesseract
   fallback count (those 137 cells currently get an answer from Hu; returning '?'
   instead routes them all to Tesseract).  Whether that is a net improvement
   depends on whether Hu's answers are more or less correct than Tesseract's —
   and Tesseract is not 100% reliable either, making ground-truth comparison
   time-consuming.


11. daily_gunsmoke: top-bottom panel stacking not supported

   STATUS: OPEN / Not yet observed in the wild
   SCOPE: MAIN

   The current panel-discovery logic (_find_all_frames + _group_frames_into_panels)
   clusters portrait frames by x-proximity, which correctly handles left-right
   side-by-side panels.  If a future screenshot stacks two reports vertically
   (top panel / bottom panel), the frames from both panels would share nearly
   the same x and be merged into one group, producing a single malformed report
   instead of two separate ones.

   IDEA TO RESOLVE: After x-clustering, check whether a group's y-span exceeds
   ~1.5× the expected 5-row height.  If so, split the group at the y-gap between
   rows 5 and 6 (the expected inter-panel gap would be larger than inter-row gaps).

   DESIGN ITERATION SUMMARY (vstroke) -- four rejected designs before the
   promoted one, each a real, measured dead end, not a guess:
     1. Fixed, centered, background-flanked-on-both-sides kernel, full
        glyph height: '1' only narrowly beat '7' (+0.083 gap); a fixed

     centroids the flat path uses (no separate training, no rebuild) --
     the generalization of PAIR_TIEBREAK_RULES's own reduced-dimension
     technique into the primary decision path.
