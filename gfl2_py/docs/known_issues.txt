1.  Blank scores when using Tesseract after new-buff asset saves (Windows)

   STATUS: MITIGATED
   SCOPE: MAIN
   WORKAROUND: use --score-pipeline blob (now the default in main.py).
               The blob/Hu pipeline is Tesseract-free and is unaffected.
               (Briefly non-functional 2026-07-02 due to §16; fixed same day.)

   FIRST OBSERVED: Session processing gm_250818.png (June 2026).
   Rows 2, 3, 4, 8, 10 — every row whose PREVIOUS row triggered a
   buff_ocr._save_asset() call — produced blank score fields in the CSV.

   SYMPTOMS:
   - Score column empty in CSV for a repeatable subset of rows.
   - Affected rows are not random; they always follow a row where a new
     buff PNG was written to assets/buff/.
   - Not reproduced in the Linux sandbox — only on the user's Windows
     machine (Python 3.14, Tesseract from UB-Mannheim).

   CONFIRMATION VIA TRACE (GFL2_TRACE=1, gm_250818.png):
   - Clean rows:    _ocr_score ~0.154s (method 1 succeeds).
   - Affected rows: _ocr_score ~0.303s (method 1 fails, method 2
     also attempted and also fails).
   - The 0.303s rows correspond exactly to rows immediately following a
     new-buff asset save in the previous row.

   ASSUMPTIONS / DEDUCTIONS:
   - Writing a PNG file to assets/buff/ via cv2.imwrite() on Windows
     triggers filesystem activity (NTFS journal, antivirus scan, or
     page-cache pressure) that degrades Tesseract's ability to write
     or read its own temp files for the next OCR call.
   - The contamination is cross-row: row N's asset save affects row
     N+1's score OCR, not row N's own score (already computed at that
     point).
   - Both OCR methods (image_to_string and image_to_data) fail, ruling
     out a PSM-mode-specific issue.

   ATTEMPTS TO RESOLVE:
   a. Move _ocr_score before buff_ocr.translate in _parse_row.
      Result: FAILED. The contamination is cross-row (row N affects N+1),
      not within the same row.

   b. Batch ALL score and owner-name OCR calls before any buff_ocr calls
      in parse() — current implementation.
      Result: CONFIRMED CORRECT IN THEORY. Works in sandbox. Still failing
      on Windows; suspected cause: stale .pyc loading the old unbatched
      code despite compile_gfl2.py being run.

   MITIGATION (implemented):
   - Blob/Hu moment pipeline added to score_detect.py.
   - make_score_fn() factory exposes it for use in weekly_gunsmoke.parse().
   - --score-pipeline blob is now the default in main.py.
   - Benchmark on 10-crop ambiguity-ranked test set: 100% accuracy,
     ~4ms/row vs ~200ms/row for Tesseract.
   - Templates stored in assets/fonts/score_digits.py; rebuild with
     python debugs/score_detect.py --build.

   ROOT CAUSE: Not fully diagnosed. Tesseract on Windows appears to share
   some process-level state (temp file handles, page-cache) with
   concurrent filesystem writes. The blob pipeline avoids Tesseract
   entirely for score extraction, bypassing the issue.

   REMAINING OPEN WORK (if root cause diagnosis is desired):
   - Check whether TESSDATA_PREFIX or TMP is set to a network/NTFS path.
   - Try setting TMPDIR/TMP/TEMP to a local path before running main.py.
   - Try pytesseract with timeout parameter to rule out silent hangs.
   - Print raw pytesseract return value in trace to distinguish "empty
     string" from "garbage that failed digit regex".

5.  populate_doll_assets: single-panel images incorrectly split

   STATUS: RESOLVED
   SCOPE: MAIN

   FIRST OBSERVED: fb_d_060518.png and ~10 other fb_d_ files.

   SYMPTOM: Files parsed as 0 frames / 0 assets. Debug showed two
   panels: 380×997 and 760×997 — an unequal split of a 1140px-wide
   single-panel image.

   ROOT CAUSE: _split_panels() in daily_gunsmoke.py searched for the
   brightest column within the middle third of the top bar. A bright UI
   separator inside a single-panel layout (at x≈380, i.e. 33% of width)
   fell inside the old guard range (0.2–0.8) and triggered a spurious
   split. The resulting 380px sub-panel had SEARCH_X1=0.15 → 57px search
   width, which clipped the ~90px portrait frames below the 0.70
   squareness threshold.

   FIX:
   - _split_panels() guard tightened from 0.2–0.8 to 0.4–0.6. A genuine
     2-panel layout always splits ≈50/50; any split outside 40–60% is now
     treated as a single panel.
   - SEARCH_X1 raised from 0.15 to 0.25 as belt-and-suspenders for
     any panels narrower than the calibration image.

   - HDR_BLOB_MIN_H=12: excludes comma-separator noise blobs (h≈5-10 px).

15. NORM_W_PCT×NORM_H_PCT resize introduces within-class feature variation

   STATUS: MITIGATED for production/padded (accepted parity, see PARITY
   below). The downstream FFT/Gabor exploration this originally motivated
   was superseded by gfl2/stat_ocr_fft.py's later evolution -- see
   §17-§31 for where that classifier ended up.
   SCOPE: MIXED -- the resize/pad root cause and the production/padded
   parity benchmark below are MAIN (gfl2/stat_ocr.py,
   gfl2/stat_ocr_padded.py); the FFT/Gabor feature-exploration history is
   EXPLORE (gfl2/stat_ocr_fft.py only).

   ROOT CAUSE: each digit blob is cropped to its tight bounding box then
   resized to NORM_W_PCT×NORM_H_PCT (12x20). Because original blob widths
   vary ('1' ~5px, '0' ~11px), the resize applies a different horizontal
   stretch factor per instance -- causing (a) aspect-ratio distortion
   that pollutes any feature sensitive to stroke width/spatial frequency,
   and (b) boundary bleed from an adjacent stroke occupying
   proportionally more of the fixed canvas. Production's 1D projection
   classifier tolerates this fine (1D correlation isn't sensitive to
   horizontal stretch), but 2D features (FFT histogram, Gabor) are.

   PARITY (docs/decisions.txt #47): an aspect-preserving "pad, don't
   stretch" alternative (gfl2/stat_ocr_padded.py) was built and
   benchmarked head-to-head against production across the full
   single/*.png corpus -- essential parity in both accuracy (<=0.25
   points either way) and speed (<1% difference). No measurable case for
   migrating production off direct-stretch; padded remains a validated,
   parked alternative, selectable via `main.py --stat-ocr-engine padded`.

   '2'/'3' GROUND-TRUTH CORRUPTION (RESOLVED, 2026-07-03): an apparent
   '3'->'2' val-line misclassification in the padded pipeline turned out
   to be BACKWARDS -- the stored ground truth was wrong (Tesseract's
   --build labelling misread a specific '2' rendering as '3' widely
   enough across the 87-image training corpus to contaminate
   assets/fonts/stat_val.py itself), and production made the exact same
   misread, invisibly, because the corrupted ground truth agreed with it.
   Fixed via stat_gt_overrides.json (now applied by --build as well as
   --verify -- a --verify-only override could never stop --build from
   re-contaminating the template) plus a categorical '2'-vs-'3'
   bottom-row-width discriminator (_bottom_row_width_frac(), decisions.txt
   #46) added to both gfl2/stat_ocr.py and gfl2/stat_ocr_padded.py.

   FFT/GABOR EXPLORATION (EXPLORE-scope, SUPERSEDED): the padded-normalize
   fix was reconnected to a parallel FFT+Gabor nearest-centroid classifier
   exploration (gfl2/stat_ocr_fft.py, decisions.txt #49) that went through
   many iterations -- a wedge (angular-FFT) feature added then removed, a
   paren/ring feature pair added (finally breaking a persistent '6'/'9'
   collision that every prior FFT-magnitude-only feature was
   mathematically incapable of resolving, by construction: rot180
   symmetry), a Gabor 135deg orientation checked and dropped after a
   standalone F-ratio metric was found misleading, a two-independent-agent
   classifier restructure (gabor+paren+ring vs. the histogram, combined at
   the decision level rather than one shared distance metric), a '4'/'7'
   pair-tiebreak override, a from-scratch Gabor kernel calibration tool
   (debugs/calibrate_gabor.py, built after two feature-space-proxy scoring
   attempts were tried and found untrustworthy), a validated-but-parked
   multi-scale Gabor bank prototype, a per-digit debug visualization table
   (which caught its own per-cell-normalization bug along the way), and
   finally replacing gabor_0 with a purpose-built isolated vertical-run
   feature (vrun) plus loop_top/loop_bot curve templates targeting
   '9'/'6'. Net effect over this whole arc: cell-level pct accuracy
   43.2% -> 97.2%.

   See docs/decisions.txt #49 (and its six addenda) for the full
   decision-by-decision record. This entire feature set was itself
   superseded by later work -- gfl2/stat_ocr_fft.py's classifier
   moved on to a hierarchical/branching design (§25) and most of these
   specific features (vrun, wedge, the flat two-agent classifier) are no
   longer what runs by default. See §17-§31 for where the classifier
   ended up, and §31/decisions.txt #75 for the simpler successor engine
   (gfl2/stat_ocr_dp.py) this whole arc eventually led to.


14. stat_ocr: Hu moment tiebreaker should be disabled

   STATUS: OPEN
   SCOPE: MAIN

   OBSERVED: Timing reports show 117 val and 20 pct genuine Hu fallback calls
   per ~3300-cell run (after the logging bug fix in §_read_line that was
   previously inflating the count to 3296×).

   PROBLEM: The Hu tiebreaker is reached only when projection confidence falls
   below PROJ_CORR_MIN — the genuinely hard, ambiguous cases.  Hu moments have
   been shown during classifier development to be unreliable on exactly these
   cases (training data showed misclassifications that Hu made worse, not better).
   Keeping it risks silently wrong answers on ~137 cells per run.

   IDEA TO RESOLVE: In _classify(), replace the Phase 3 block with a plain
   return '?' when projection cannot reach PROJ_CORR_MIN.  The caller already
   handles '?' via Tesseract fallback for val, and the pct fallback chain.
   This makes the uncertainty explicit rather than masking it with an unreliable
   tiebreaker.

   BLOCKED ON: Validation cost.  Removing Hu will definitively increase Tesseract
   fallback count (those 137 cells currently get an answer from Hu; returning '?'
   instead routes them all to Tesseract).  Whether that is a net improvement
   depends on whether Hu's answers are more or less correct than Tesseract's —
   and Tesseract is not 100% reliable either, making ground-truth comparison
   time-consuming.


11. daily_gunsmoke: top-bottom panel stacking not supported

   STATUS: OPEN / Not yet observed in the wild
   SCOPE: MAIN

   The current panel-discovery logic (_find_all_frames + _group_frames_into_panels)
   clusters portrait frames by x-proximity, which correctly handles left-right
   side-by-side panels.  If a future screenshot stacks two reports vertically
   (top panel / bottom panel), the frames from both panels would share nearly
   the same x and be merged into one group, producing a single malformed report
   instead of two separate ones.

   IDEA TO RESOLVE: After x-clustering, check whether a group's y-span exceeds
   ~1.5× the expected 5-row height.  If so, split the group at the y-gap between
   rows 5 and 6 (the expected inter-panel gap would be larger than inter-row gaps).

12. Daily Gunsmoke header score: adjacent digit pair merges at THRESH_VAL=150

   STATUS: RESOLVED (June 2026 — test_daily_gunsmoke.py 3/3 pass)
   SCOPE: MAIN

   FIRST OBSERVED: gm_d_20250929.png panel 1 — score read as '835' instead
   of '4635'.

   SYMPTOMS:
   - Panel 1 score wrong; panel 2 ('3876') correct in the same image.
   - Same image also exposed the panel-bounds regression (§13): no test
     covered the full daily GS parse path end-to-end before this session.

   ROOT CAUSE (two-layer):
   (a) At THRESH_VAL=150 the '4' and '6' digit strokes are adjacent enough
       to merge into a single 27×19 px blob, classified as '8'.
   (b) At threshold 160 the blobs separate cleanly (4 blobs), but the '6'
       blob scores 0.833 for '5' vs 0.798 for '6' — '5' wins because the
       score_digits.py templates were built from a different font/size and
       the thinner strokes at 160 make '6' look more like '5' in projection

   DESIGN ITERATION SUMMARY (vstroke) -- four rejected designs before the
   promoted one, each a real, measured dead end, not a guess:
     1. Fixed, centered, background-flanked-on-both-sides kernel, full
        glyph height: '1' only narrowly beat '7' (+0.083 gap); a fixed
        ink-column width silently assumes a stroke thickness.
     2. Sliding-in-x-only, single-sided, full-height, with a bottom
        "don't care" band: '1'/'7' gap widened to +0.334, but exposed (a)
        a hard reachability limit -- a single-sided kernel's ink region

        "don't care" band lived -- forcing the entire height except the
        bottom few rows to read as background fails regardless of side.

        also slides vertically can dodge '4's crossbar by positioning
        itself below it. Fixed '4' (0.057->0.620) but reopened a DIFFERENT
        false-positive: a short window free to move in both axes can find
        a locally-straight-looking patch inside a curved digit's stroke

   FINDING 2 -- A WHOLE-GLYPH GABOR CANNOT FUNCTION AS A LINE DETECTOR AT
   THIS RESOLUTION: extensive retuning was attempted for a genuine 90deg
   (horizontal-line) detector targeting {2,4,5,7}:
     - A naive (lambd,sigma,gamma,ksize) sweep against the whole corpus
       found its best-scoring candidate at gamma=1.0 (isotropic, i.e. NOT
       a line detector at all) -- gamma<0.3 (genuine elongation) scored
       NEGATIVE separation even after widening ksize and padding the
       glyph canvas 12x20->20x20. Root cause, confirmed analytically: the
       envelope-containment constraint (sigma <= gamma*half_ksize/margin)
       forces sigma so small at low gamma that the kernel's thickness axis
       undershoots the corpus's real ~2-4px stroke width, so it responds
       to binarization noise rather than genuine stroke content.
     - Rotating the glyph 45deg and reusing the SHIPPED (already
       clipping-free) 45deg kernel scored better than building a 90deg
       kernel from scratch (+0.294 vs -0.101 to -0.613 across the 2x2
       combinations tested) -- confirmed analytically why: at 45deg, the
       elongated axis's variance is split/averaged across BOTH pixel axes
       (var_pixel = 0.5*(sigma^2+(sigma/gamma)^2)) instead of landing
       fully on one axis, so the same (sigma,gamma) clips less severely at
       45deg than at 0/90deg -- a real discretization effect, not a
       tuning artifact.
     - EVEN SO, every configuration failed a direct visual check: the
       response heatmap's peak consistently landed on a rounded blob at a
       stroke JUNCTION or a curve's flank, never tracing a line's length.
       Decisive tell: '1' (the single visually cleanest, unbroken line in
       the whole digit set) scored LOWER than curvy non-target digits
       ('8','9') in every configuration tested, including a brute-force
       search restricted to gamma<=0.5 against '4' alone (10 top
       candidates, all converging on the same junction-blob pattern,
       score ~1264-1277 but visually not tracing '4's crossbar). A metric
       that ranks the actual line below several non-lines is not
       measuring "line-ness," whatever the aggregate number says.

   debug_sobel45_pct_glyphs.py and debugs/debug_sobel90_pct_glyphs.py,
   probe whether a plain Sobel operator -- convolved with itself via
   repeated FFT-domain multiplication (raising the kernel's frequency
   response to the n-th power before one inverse FFT, mathematically
   equivalent to re-convolving the spatial result n times) -- can
   segregate digit groups the way this project's Gabor/vstroke/hbar
   features already do. Both re-isolate glyphs from assets/fonts/
   glyph_daily_pct.png via a plain threshold + cv2.findContours pass

   debugs/build_glyph_reference.py), pad each into ONE consistent canvas

   (measured fresh every run: 15x20 for this corpus -- never a
   hardcoded constant), then iterate the convolution for n=1,2,3.

   45DEG ATTEMPT -- confirmed real, but swamped by resolution artifacts
   already documented for Gabor: a synthetic thin-stroke control test
   (built BEFORE trusting any real-glyph result, per this project's own
   "calibrate on synthetic cases first" discipline -- known_issues.txt
   §15's vrun entry) confirmed the 3x3 45deg kernel is genuinely
   orientation-selective, not a kernel bug: mean|response| = 0deg=76.5,
   45deg=247.4, 90deg=144.1, 135deg=12.8 (thin 2px-wide synthetic
   strokes). But on real pct-line glyphs it strongly detected '7's
   HORIZONTAL top bar while only lightly catching '7's diagonal
   descender (which doesn't render at a clean 45deg in this font), and
   by the 2nd iterated convolution the diagonal response had vanished
   while the horizontal one survived. Root cause: the SAME two effects
   already on record for Gabor's 135deg orientation (§15's PAIR TIEBREAK
   / Gabor-135 entry) -- pixel-level staircasing of any stroke at this
   resolution introduces incidental 0deg/90deg content, and a closed
   curve's tangent sweeps through every orientation somewhere along its
   boundary, so curvy digits pick up real (not spurious) 45deg content
   too. A morphological-open pre-processing step was tried next, hoping
   to suppress that small incidental structure while preserving real
   strokes (motivated by direct feedback: repeated LINEAR convolution
   was hoped to behave "akin to morphology open," but doesn't -- it's
   frequency-selective, not size-selective, with no mechanism to prefer
   large coherent structure over small incidental structure). A 2x2
   rectangular structuring element over-eroded these ~2px-wide strokes
   before the Sobel step ever ran (confirmed by inspecting the binary
   mask before/after cv2.MORPH_OPEN directly) and was dropped by
   explicit direction rather than re-tuned.

   90DEG PIVOT -- targets the SAME group hbar_top/hbar_bottom already
   target (§19: "targeting '2'/'4'/'5'/'7'"), matching '7's reliably-
   detected horizontal bar instead of chasing the off-angle diagonal.
   Tried both the classic 3x3 Sobel-Y and OpenCV's own generalized 5x5
   Sobel-Y (verified via cv2.getDerivKernels(dx=0, dy=1, ksize=5): outer
   product of binomial-smoothing [1,4,6,4,1] and central-difference
   [-1,-2,0,2,1] vectors -- not hand-guessed). MEAN response across the
   whole glyph does NOT separate {2,4,5,7} from {0,6,8,9} at either

   CONCEPTUALLY WORSE, not merely tied. §24 already established gabor_45
   does not perform real line detection at this glyph resolution --
   every "winning" kernel configuration in that investigation visually
   matched a junction/curve blob, never actually traced a line's length;

   THE STUBBING QUESTION, ANSWERED PRECISELY: val was already a real
   no-op (`_reconstruct_val` always returns None) -- the question was
   what happens when `daily_gunsmoke.py`'s `_extract_stat_cell()` sees
   that None. Traced directly: it only checks `is not None` on both
   pct/val, so a None val triggers the SAME existing Tesseract psm6/
   psm4 fallback that already exists for a genuine blob-classifier miss
   -- no new fallback logic was needed, and `dg_output.py`'s `_v()`
   checks `None` before its `'?' in v` test, so it flows safely through
   to JS `null`. Verified end-to-end: `python main.py <img> --pattern
   daily_gunsmoke --stat-ocr-engine dp` produced BYTE-IDENTICAL output to
   the production engine on the same real fixture.

   THE COST THIS EXPOSED: because dp's val is ALWAYS None (not just
   occasionally, the way a genuine blob miss is), the pre-existing
   fallback fired on EVERY cell, every time -- turning a ~0.4s image into
   a 15-19s one (~40 cells x ~300-600ms of Tesseract each), for zero
   accuracy benefit over just leaving val null. This wasn't a flaw in the
   no-op itself (confirmed instant: `stat_cell/blob` stayed at
   ~0.5-0.9ms) -- it was the ALWAYS-ON fallback treating "engine doesn't
   implement this" identically to "engine tried and failed," when only
   the second case actually calls for an expensive last resort.

   FINDING A -- 7 of 8 were Tesseract ground-truth mislabels, not

   FINDING B -- the 8th (ib_d_20251020_p1_r4_col4, expected '0', dp
   returned '0010') is a genuine, newly-discovered engine bug, unrelated
   to Finding A: gfl2/stat_ocr_dp.py's adaptive per-(strip_height,
   ink_color_group) binarization threshold is cached and shared across an
   entire run -- true both of --verify's corpus scan AND real production
   (main.py's _process_daily_folder creates ONE stat_engine outside its
   per-image loop, reused across every image in the folder -- the exact
   same sharing pattern). Confirmed directly: a fresh, single-image-only
   engine (matching main.py's single-image invocation) reads this cell
   correctly ('0'); the SAME cell through a full-corpus shared-cache run
   reads '0010' -- purely a function of what other images were processed
   earlier in the same run, not of the cell's own pixels.

   Traced exactly: the shared (31, 'rest') threshold cache had been
   seeded by an earlier image at t=124 (vs. this cell's own natural
   ~117-121) -- permissive enough that a 2x2-pixel noise speck at the
   strip's far right edge crossed the ink threshold. That speck became
   the RIGHTMOST blob, and gfl2.stat_ocr._find_percent_x_start anchors
   its whole '%'-sign detection off the rightmost blob -- with the anchor
   hijacked by noise, it returned pct_x=None (detected no '%' at all), so
   the real '%' sign's own three sub-shapes (two circles + slash) were
   all misclassified as digits instead of skipped, producing '0' (real)
   + '0'+'1'+'0' (the '%' sign, misread) = "0010".

   noise-speck floor (smallest genuine blob found anywhere in
   single/*.png, scanned with fresh per-cell thresholds to avoid
   measuring the bug itself, is a 3x3=9-area '.' dot -- nothing real is
   ever smaller). _find_percent_x_start now drops any blob below this
   floor BEFORE picking its rightmost-blob anchor. Applied to gfl2/
   stat_ocr.py directly and ported by hand to gfl2/stat_ocr_padded.py's
   own duplicate copy (decision 47's policy -- confirmed, as always, that
   this doesn't propagate automatically). gfl2/stat_ocr_fft.py and gfl2/
   stat_ocr_dp.py both import the function directly and received the fix
   for free.
